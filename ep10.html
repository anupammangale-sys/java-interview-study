The cost of a change

Everyone can recite SOLID. Almost nobody can show what it buys. So here is one checkout system written twice, five real requirements sent at both versions, and the actual cost of each change measured with git diff and a stopwatch. The headline number is not the one the textbooks promise: the clean version is 52 percent more code. What it buys is something else entirely, and that is the whole episode.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 The class that does everything

  • What does "one reason to change" actually mean? Give an example.
  • A marketing person asks for different wording in an email. Which file should that touch?
  • Is a class with 20 methods breaking the single responsibility principle?
  • How is single responsibility different from tight coupling?

What it is. The single responsibility principle says a class should have one reason to change. Not one method. Not one line. One reason.

A reason to change is a person or a team who can walk up to you and ask for something different. Finance can change the fee. Marketing can change the email. The platform team can move the database. Each of those is a reason. If all three land in the same file, that file has three reasons to change, and the principle is broken.

What it looks like when it is broken. Here is the checkout method that this whole episode is built on. It works. It has been in production for two years. Read what it does, in order:

tangled/OrderService.java103 lines, 6 files
public void checkout(Order order, String method) {

    // 1. is this order allowed at all
    if (order.amountPaise() <= 0) throw ...
    if (method.equals("card"))            // card has a limit
    else if (method.equals("netbanking"))  // netbanking has a floor

    // 2. what the payment provider charges us
    if (method.equals("card")) fee = amount * 0.0195 + 300;
    else if (method.equals("netbanking")) fee = 1200;

    // 3. actually take the money
    if (method.equals("card")) // call the card gateway
    else if (method.equals("netbanking")) // call the bank portal

    // 4. store it
    Database db = Database.connect("jdbc:postgresql://prod-db:5432/orders");
    db.savePayment(order.id(), method, fee);

    // 5. tell the customer
    Smtp smtp = Smtp.connect("smtp.company.internal");
    smtp.send(order.customerEmail(), "Order confirmed", "Thank you...");

    // 6. audit trail
    System.out.println("[audit] " + order.id() + " paid by " + method);
}

Six jobs. Six reasons to change. This is not a made up example written to look bad: it is what code turns into when a feature ships on time and every later change gets added to the method that was already there.

The measurement. Marketing asked for different wording in the confirmation email. Nothing to do with payments. Here is the real diff, taken from both versions of the same system:

VersionFile that changedLines
tangledOrderService.java, which also holds the fee rules, the card gateway call and the database connection3 added, 1 removed
cleanEmailNotifier.java, which holds nothing else 3 added, 2 removed

Look at the line counts. They are the same. Single responsibility did not save a single keystroke here. What it changed is which file a person had to open. In the tangled version, a wording change from marketing meant opening the payment logic, which means a code review by the payments team, and a small chance of breaking how money moves because of a sentence about a discount.

The trap: this is not the same as tight coupling. Interviewers ask this to separate people who memorised the list from people who have used it.

  • Too many responsibilities means one class does several unrelated jobs. The fix is to split it. Our OrderService has this problem.
  • Tight coupling means one class depends on the exact details of another, so changing one forces you to change the other. The fix is to put an interface between them, or to stop the dependency existing. Our OrderService also has this problem, separately, because it names Database and Smtp directly.

They travel together, but they are different faults with different fixes. You can have a class that does one job and is still tightly coupled to a specific database driver. You can have a class that is loosely coupled to everything and still does six jobs.

Common wrong answers

"A class should do only one thing." Too vague to act on, and it leads people to write classes with one method each. The test is who can ask you to change it, not how many things it appears to do.

"Small classes are good, big classes are bad." Size is a symptom, not the rule. A 400 line class that only the tax team ever changes is fine. A 30 line class that three teams keep editing is not.

Follow-up questions

What counts as "one reason to change"? It sounds subjective.

It is subjective, and pretending otherwise is how people get lost. The version that actually works in practice is: a reason to change is a group of people who can ask for a change independently of the others. Robert Martin, who wrote the principle, later restated it exactly this way, because the original wording confused everyone.

So test it by naming the humans. In our checkout method: finance owns the fee percentages. Marketing owns the email text. The platform team owns which database it connects to. Compliance owns what goes in the audit line. Four groups of people, one file. Any one of them can force a change that the other three did not ask for and must now review.

If you cannot name two different groups, you probably do not have two responsibilities, and splitting the class will just create more files with no benefit. That is the failure mode people hit when they apply this principle by feel.

Is a class with 20 methods automatically breaking this principle?

No, and this is worth saying clearly in an interview because it shows you are not just counting things.

java.lang.String has over 60 public methods. It is not a violation. Every one of those methods exists for the same reason: to do something with a sequence of characters. There is one group of people who would ever change it, and one concept it serves. Splitting String into StringSearcher, StringTrimmer and StringJoiner would make the code worse and harder to find your way around.

Now compare a 3 method class: saveUser(), sendWelcomeEmail(), chargeSubscription(). Three methods, three teams, three reasons to change. That small class is the violation, and the 60 method one is not.

So the honest answer is: method count tells you nothing on its own. It is a hint worth looking at, in the same way a large file is a hint. The actual test is whether the reasons to change are the same reason.

How do I tell this principle apart from tight coupling in an interview?

Use this sentence: one is about how much a class does, the other is about how much a class knows.

Too many responsibilities is about how much it does. Our checkout method validates, prices, charges, saves, emails and audits. Too much doing. You fix it by moving work out into other classes.

Tight coupling is about how much it knows. Our checkout method knows the exact class name Database, and the exact connection string, and that email is sent over SMTP. Too much knowing. You fix it by replacing the specific knowledge with a general promise, which in Java means an interface, and having someone else supply the specific thing at start up.

A worked example of the difference. Suppose you split the email sending out into an EmailSender class, and OrderService now calls new EmailSender().send(...). You have genuinely fixed the responsibility problem, because the marketing wording now lives in its own file. You have not fixed the coupling, because OrderService still names the concrete EmailSender and still cannot be tested without a mail server. Two faults, two fixes, and doing one does not do the other.

If splitting classes is free, why not split everything as far as possible?

Because it is not free, and this episode measured the price. The clean version of this system is 157 lines across 13 files against 103 lines across 6 files. That is 52 percent more code and more than double the number of files, for identical behaviour.

Every extra file is a thing to name, a thing to find, and a jump for whoever is reading the code later. Follow one request through the clean version and you visit Main, CheckoutService, CardPayment, PostgresOrderRepository and EmailNotifier. Follow it through the tangled version and you scroll down one method. For a reader who just wants to know what happens, the tangled version is genuinely easier.

The trade is that the tangled version is easier to read once and harder to change safely, and code gets changed far more often than it gets read from scratch. That is the actual argument, and it is a trade rather than a free win. Saying this out loud in an interview is worth more than reciting the principle, because it shows you have paid the cost and decided it was worth it.

02 Adding UPI without touching what works

  • "Support a new payment method without changing existing code." How?
  • The clean version wrote more lines for the same feature. Why is that still better?
  • You still edited one existing file. Is that a violation?
  • How do you decide what to make extensible before you know the future?

What it is. Open for extension, closed for modification. New behaviour should arrive as new code, not as edits inside code that already works.

The scenario, which is asked almost word for word. "Next month we need to support UPI. Card and netbanking are live and must not break. How do you build this?"

Here is what actually happened when UPI was added to both versions of the system. These are real diffs, not estimates:

git diff --no-index --statadding UPI
tangled
  Main.java         | 2 +-
  OrderService.java | 9 +++++++++
  2 files changed, 10 insertions(+), 1 deletion(-)

clean
  Main.java         |  4 ++--
  UpiPayment.java   | 16 ++++++++++++++++
  2 files changed, 18 insertions(+), 2 deletions(-)

The clean version wrote more code. Eighteen lines against ten. If the argument for this principle were "you write less", the measurement just lost it.

So measure the thing that actually matters. Not how many lines were written, but how many lines of working, tested code had to be opened and edited:

New lines writtenLines of existing logic modified Existing files left byte identical
tangled109, in three separate places inside the method that also opens the database and sends the email3 of 5
clean18012 of 13

In the clean version, CardPayment.java and NetBankingPayment.java were never opened. Not edited carefully, not reviewed: never opened. They came out of the change byte for byte identical, which was checked with cmp rather than trusted. Card payments cannot have been broken by this change, and that is a fact about the diff, not a promise from a developer.

In the tangled version, nine new lines went into three different places inside a method that also moves money and writes to production. Each of those is somewhere a mistake could reach card payments.

This is the sentence to say in an interview: "It is not about writing less code. It is about not editing code that already works. Adding UPI touched zero lines of the card logic."

What made this possible

One interface, PaymentMethod, with the four things every payment method must be able to do: give its name, check the order, work out the fee, take the money. UPI is a new file that implements it. CheckoutService looks the method up by name and calls it, and has no idea UPI exists.

Common wrong answers

"It means you never edit an existing file." You edited Main.java. That is fine, and pretending otherwise makes the principle impossible to follow. Wiring has to change when there is something new to wire. What must not change is the logic.

"You need an abstract class for everything just in case." This is how codebases end up with an interface per class and one implementation each. You make something extensible when you have a real reason to think it will be extended, and a payment method list is about as safe a bet as exists.

Follow-up questions

You still edited Main.java. Is that not a modification?

It is, and it is the right answer to give rather than dodge.

Something, somewhere, has to learn that UPI exists. There is no design where a new class appears on disk and starts being used with nothing anywhere pointing at it. The goal is not zero edits. The goal is that the edit lands in a place that holds wiring and no logic, so that getting it wrong cannot break how money moves.

Main.java in the clean version is exactly that place. It has one job: to build the real objects and hand them to each other. It is called the composition root, which is just a name for the one place that knows which real classes are in use. If you break it, the application will not start, which is the loudest and safest way to fail.

And in a Spring application, even that edit usually disappears. You annotate UpiPayment with @Component, ask for a List<PaymentMethod> in the constructor, and Spring finds every implementation on the classpath and passes them all in. Now adding UPI really is one new file and no edits anywhere. That is not magic: Spring is doing the job that Main.java was doing by hand.

How do I know what to make extensible before I know what is coming?

You mostly do not, and guessing is expensive. The useful rule is to wait for the second one.

When there is one payment method, write it directly. When the second arrives, you now know something real: this is an axis the business actually changes along. That is the moment to pull out the interface, and you can do it with confidence because you have two concrete examples to design against, not one example and your imagination. When the third arrives, it costs almost nothing.

Designing for change you have not seen produces the opposite failure, which is just as common and harder to unpick. You end up with AbstractPaymentStrategyFactory and one implementation, because you guessed at an axis of change that never moved, and now everyone pays the reading cost forever for flexibility nobody uses.

The exception is when the business has already told you. If someone says "we will be adding wallets and UPI next quarter", that is not a guess, that is a requirement with a date on it, and you build for it now.

If the clean version is 52 percent more code, how do I justify it to a manager?

Not by naming the principle. Managers do not buy principles, they buy outcomes, and this is a genuinely good interview answer because it shows you can operate outside your own team.

Use the numbers this episode produced. "Adding a payment method to the current code means editing nine lines inside the method that also charges cards and writes to the production database. Every one of those is a place a mistake reaches live payments, so every change needs the payments team to review it and a full regression pass. In the other shape, the same feature is one new file and zero lines of existing payment code touched, so the review is smaller and the blast radius is provably nothing."

Then add the honest cost, because leaving it out is how you lose trust: "It is about 50 percent more code and roughly twice the files. It is more to read the first time. We get that back the second and third time we change it."

And be willing to say when it is not worth it. A script that runs once, a proof of concept, an integration nobody will extend: leave it tangled. The trade only pays off where change is actually coming.

Is this the same as the strategy pattern?

Very close, and the difference is worth being precise about because interviewers sometimes push on it.

Open for extension is the goal: new behaviour should arrive as new code. Strategy is one way of reaching that goal: define an interface for a job that can be done several ways, write one class per way, and pick between them at run time. That is exactly what PaymentMethod, CardPayment and UpiPayment are. So yes, this design is the strategy pattern, and it is being used to reach the goal.

But the goal has other routes. You can reach it with a lookup table of small functions rather than classes. You can reach it by having new behaviour arrive as a plugin the program discovers on the classpath, which is what Java's ServiceLoader does. You can reach it with rules held in a database instead of in code, so new behaviour is a row rather than a deployment. All of those are open for extension, and none of them are the strategy pattern.

So the accurate phrasing is: every use of strategy serves this principle, but not every way of serving this principle is strategy.

03 The subclass that breaks a promise

  • What promise does a parent class make, and how does a subclass break it?
  • Why is the gift card refund a design fault and not a bug?
  • Explain the rectangle and square example, and what it is really showing.
  • Can a subclass throw an exception the parent never threw?

What it is. If your code works with a parent type, it must keep working when it is handed any subclass, without knowing which one it got. That is the whole rule.

A parent class makes a promise. A subclass is allowed to keep that promise differently. It is not allowed to break it.

The scenario. Refunds get added. There is a Refundable parent whose promise is simple: call refund(amount) and that amount goes back to the customer. Card and netbanking implement it. Then gift cards arrive.

A gift card behaves like a card in almost every way, so someone extends CardRefund to save the duplication. But the business rule is that gift card money is never returned. So the only thing refund can do is fail:

proofs/LiskovProof.javathe same test, three subclasses
class GiftCardRefund extends CardRefund {
    // the parent promised: give me an amount, I return it
    long refund(long amountPaise) {
        throw new UnsupportedOperationException("gift cards are not refundable");
    }
}

// one test, written once, against the promise the parent made
card         contract holds? true
netbanking   contract holds? true
gift card    contract holds? false

Why this is worse than it looks. The damage is not a tidy exception at the top of the program. Real code that was written against the parent type does not know anything is unusual, so it goes ahead and does half the job. Here is a refund batch, run twice:

a refund batch written against the parent typereal output
all subclasses keeping the promise:
  refunded Rs 500.00 by card
  refunded Rs 500.00 by netbanking
  refunded Rs 500.00 by card
batch finished, 3 of 3, total Rs 1500.00

one gift card in the middle:
  refunded Rs 500.00 by card
  STOPPED: gift cards are not refundable
batch died after 1 of 3. Rs 500.00 already left the account and the rest
never ran.

Money moved. Then the batch died. The remaining customers were not refunded and nothing was rolled back. Nobody wrote a bug. Every individual class is correct on its own. The batch code is reasonable. The fault is that a subclass was allowed to say it was a CardRefund while not being able to do what a CardRefund does.

What should have happened. Gift cards are not a kind of refundable payment. They are a payment method that happens to share some code with cards. So do not inherit from CardRefund. Have GiftCard implement the payment interface and simply not implement Refundable at all. Then the refund batch cannot be handed one, because the types will not allow it, and the compiler catches it instead of production. That is chapter four, and it is the same fix.

Common wrong answers

"It means inheritance is bad." It means inheritance carries a promise that most people do not notice they are making. Used where the promise genuinely holds, it is fine.

"It is about matching method signatures." The compiler already forces signatures to match. This principle is about the part the compiler cannot see: what the method actually does, and what the caller was entitled to assume.

"Just catch the exception in the batch." Now every caller of every subclass has to know which subclasses might fail, which is exactly the knowledge the parent type existed to hide.

Follow-up questions

What exactly is "the promise"? It is not written down anywhere.

It is usually not written down, which is why this is the principle people break without noticing. It has three parts, and each has a plain English version worth memorising.

What the method demands before you call it. A subclass may accept more than the parent did, never less. If the parent accepts any positive amount and the subclass rejects anything under 100 rupees, code written for the parent will start failing. This is the one that bites most often in real systems, because it looks like harmless extra validation.

What the method guarantees when it finishes. A subclass must deliver at least what the parent promised, and may deliver more. If the parent guarantees the money is returned and the subclass returns nothing, the guarantee is broken. That is our gift card.

What stays true about the object throughout. If a Refundable is supposed to keep a running total of everything refunded, every subclass has to keep that true too, including any new methods it adds.

Short version for an interview: a subclass may ask for less and give more. It may never ask for more or give less.

Explain the rectangle and square example properly.

This is the textbook example and it does get asked, so here it is in full.

A Rectangle has setWidth and setHeight. A square is a rectangle in school geometry, so someone writes Square extends Rectangle. A square must keep its sides equal, so setWidth(5) has to set the height to 5 as well, and the other way round. Every method exists, every signature matches, it compiles.

Now here is ordinary code written against Rectangle, by someone who has never heard of Square:

r.setWidth(5); r.setHeight(4); assert r.area() == 20;

With a rectangle, the area is 20. With a square, setHeight(4) also set the width to 4, so the area is 16. The test fails, and it fails inside code that did nothing wrong.

What it is really showing, and this is the part people miss: the problem is not geometry. It is that Rectangle's promise includes "width and height can be set independently", because it offers two separate setters. A square cannot keep that promise. In geometry a square is a rectangle. In code, a square is not a substitute for a mutable rectangle, because being a subtype is about honouring behaviour, not about matching a real world category.

Two things worth adding if you have time. First, if Rectangle were immutable, with no setters and width and height fixed at construction, the problem disappears entirely, because there is no promise about setting them independently. Second, this is exactly the same fault as our gift card: a subclass advertised a capability it could not deliver. The rectangle just does it quietly with a wrong number instead of loudly with an exception, which makes it worse.

Can a subclass throw an exception the parent never threw?

Java's rules and this principle's rules are different here, and knowing that difference is a good answer.

What Java enforces. An overriding method cannot add new checked exceptions to the throws clause. The compiler stops you. But it places no restriction at all on unchecked exceptions, which is why throw new UnsupportedOperationException(...) in our gift card compiled without a murmur.

What the principle asks for. A subclass may throw an exception the parent already declared, or a more specific subclass of one. Throwing something genuinely new breaks the promise, because callers were written against the parent and had no reason to handle it.

The practical line: if the parent says "this can fail with PaymentDeclinedException", a subclass may throw that or something more specific like InsufficientFundsException, and callers already cope. If the subclass throws UnsupportedOperationException for an operation the parent said always works, that is not an error case, it is an admission that the class should not have been a subclass.

Useful thing to know: this fault is common enough that the Java standard library ships with it. List.of(1,2,3) gives you a List, and calling add on it throws UnsupportedOperationException. It is a genuine violation, the library authors know it, and they accepted it because splitting List into mutable and immutable types after decades of use would break the world. It is a good example to raise, because it shows the principle is a guide with real trade-offs rather than a law.

How would I catch this in a real codebase before it reaches production?

Write the test once, against the parent type, and run it against every subclass. That is what the demo in this chapter does, and it is the practical form of the principle.

Concretely: write a test class that takes a Refundable as input and checks the promise. Call refund with a valid amount, check that amount came back. Then have a test for each subclass that feeds its own instance into that same shared test. In JUnit this is a parameterised test, and the parameters are every implementation you have.

The moment somebody adds a subclass that cannot keep the promise, they have to either make their subclass pass the shared test or delete their subclass from the list. Deleting it from the list is a visible, deliberate act that shows up in code review, which is exactly what you want. Right now the gift card slipped in because nothing forced anyone to state that it was different.

A second, cheaper habit: be suspicious of any override whose body is only a throw. It is almost never a legitimate use of inheritance, and it is easy to grep for.

04 The interface nobody can implement

  • What is a fat interface, and what does it cost?
  • Why can the compiler not help you when every class implements every method?
  • How small should an interface be?
  • Is this not the same as the single responsibility principle?

What it is. No class should be forced to implement methods it cannot honestly do. Several small interfaces beat one big one.

How it happens. Nobody sets out to write a bad interface. Over two years, PaymentMethod gained refunds, then scheduled payments, then split payments. Every addition was reasonable on the day. Now it has five methods, and not every payment method can do all five.

The classes that cannot do something still have to write the method, because the interface says so. The only thing those methods can do is throw. This program calls every method on every class and counts:

proofs/FatInterfaceProof.javaclick any cell
charge
refund
schedule
split
card
upi
cash

Pick a cell above to see what that method actually does.

Twelve method implementations had to be written. Seven do something. Five exist only to throw, which is 41 percent. That is measured by the program, not counted by hand.

Why the compiler could not save you. This is the part worth understanding, and it is what makes the fix satisfying. The compiler was perfectly happy, and it had to be: every class really does implement every method. You told the type system that a card, a UPI handle and cash on delivery are all the same kind of thing. It believed you. So when a "split the bill" feature loops over them, this happens at run time:

split the bill, on the fat interfacereal output
card: split across 3
upi:  CRASH at run time, UnsupportedOperationException: upi cannot split one order across payers
cash: CRASH at run time, UnsupportedOperationException: cash cannot be split

The fix, and the payoff. Split the one interface into four small ones: PaymentMethod for what everything can do, then Refundable, Schedulable and Splittable. Each class implements only what it can really do. UpiPayment implements PaymentMethod and Refundable, and says nothing about the other two.

Now write the exact same mistake as before, handing a UPI payment to the split feature, and run the compiler:

javac proofs/segregated/*.javareal compiler output
Bad.java:5: error: incompatible types: UpiPayment cannot be converted to Splittable
        System.out.println(SplitTheBill.run(new UpiPayment(), 3, 50000));
                                            ^
1 error

The bug moved from production to the compiler. Same mistake, same intent, caught before the code could ever run. And in the segregated version the number of methods that exist only to throw is zero, because no class is forced to claim something it cannot do.

That is the whole argument, and it is a much better one than "small interfaces are tidier". You are moving a class of error from run time to compile time.

Common wrong answers

"It means one method per interface." No. It means one capability per interface. PaymentMethod keeps two methods, name and charge, because nothing that can be charged lacks a name. Splitting those apart would buy nothing.

"Give the interface default methods that throw, so classes do not have to write them." This is worse, not better. You have hidden the problem instead of fixing it: the compiler still cannot tell that UPI is not splittable, and now the throwing method is invisible in the class that has it.

Follow-up questions

How small should an interface be? Where do you stop?

The test is not size, it is whether the methods are always true together. If you can name a real class that can do one of the methods but not another, they belong in different interfaces.

Walk through our five. Can something be charged but not named? No, everything that takes money has a name, so those two stay together. Can something be charged but not refunded? Yes, cash on delivery, so refund moves out. Can something be refunded but not scheduled? Yes, UPI, so schedule moves out. Can something be scheduled but not split? Yes, so split moves out. That is how we got to four interfaces, and each split was justified by an actual class, not by a feeling.

The stopping point is when you cannot name a class that would want one method without the other. Going further gives you an interface per method and a class declaration that is six lines of implements, which is real cost for no gain.

Worth knowing: an interface with exactly one method has a bonus in Java, because it can be written as a lambda. That is a nudge towards small interfaces, not a rule.

Is this not just the single responsibility principle again?

They are close relatives, and interviewers ask this specifically because the sloppy answer is "they are basically the same".

Single responsibility is about the class that does the work. It protects the person who has to change the code. The question it answers is "how many different groups of people can force me to edit this file?"

Interface segregation is about the contract. It protects the person who has to use the code, and the classes that have to implement it. The question it answers is "am I being forced to depend on, or promise, things I do not need?"

Here is a case that separates them cleanly. Suppose UpiPayment is a perfect single responsibility class: it does exactly one job, payments over UPI, and only the payments team ever changes it. It fully satisfies the first principle. It still has two methods that only throw, because the interface it was handed demanded them. That is an interface segregation problem living inside a class with a single responsibility, and the fix is to change the interface, not the class.

Short version: one is about how much a class does, the other is about how much a contract demands.

What about default methods? Java 8 added them for exactly this kind of thing.

Default methods let an interface supply a body, so classes that do not care are not forced to write one. They are genuinely useful, and they are also the most common way people make this problem worse while believing they have solved it.

The bad use. Give PaymentMethod a default splitAcross that throws UnsupportedOperationException. Now UpiPayment is shorter and cleaner to read. Nothing else improved. The compiler still believes UPI is splittable, the split feature still crashes at run time, and the crash is now harder to find because the throwing method is not written anywhere in the class that has it.

The good use. Default methods are for behaviour that is genuinely correct for every implementer, usually written in terms of the other methods. For example a default chargeInRupees(long rupees) that calls charge(rupees * 100). Every payment method can do that, the body is real, and nothing throws. The other good use is the one they were added for: putting a new method on an existing interface without breaking every class that already implements it, which is how Collection.stream() arrived without breaking the world.

The test: if the default body throws, you are hiding a design problem. If the default body does real work that is right for everyone, you are using the feature properly.

Does having four interfaces not make the calling code more complicated?

It makes the calling code more specific, which turns out to be the opposite of complicated in practice.

Look at the signature. Before: run(PaymentMethod method, int people, long amount). After: run(Splittable method, int people, long amount). The second one is shorter to understand, because it tells you exactly what the function needs. You no longer have to read the body to find out that it only calls one of the five methods.

It also removes a whole category of question from the reader's mind. With the fat interface, anyone maintaining that function has to wonder which payment methods are safe to pass in, and the only way to find out is to read every implementation. With Splittable, the compiler answers it.

Where it does add real cost: a class that can do everything now has a longer declaration, implements PaymentMethod, Refundable, Schedulable, Splittable. That is a genuine readability cost and it is fair to admit it. It is also a line you read once and a compile error you avoid forever.

05 Code that builds its own dependencies

  • Why can the tangled checkout not be unit tested?
  • What is the difference between dependency inversion, dependency injection and inversion of control?
  • Who should own the interface, the caller or the implementation?
  • Does every class need an interface?

What it is. Code that makes decisions should depend on promises, not on specific classes. And it should be handed what it needs rather than building it itself.

Our tangled checkout does the opposite. It writes Database.connect("jdbc:postgresql://prod-db:5432/orders") in the middle of the payment logic. Nobody can change that from outside. To find out whether that matters, both versions were handed the same job: write a test for checkout.

The tangled test cannot check the fee. Not because the fee is hard to calculate, but because the number went into a database and was never handed back to anyone who could look at it. The only thing the test can assert is that nothing threw, which is barely a test at all.

The clean test checks the fee, the method, the order id, the email address and the gateway reference, because it handed in fake objects that wrote everything down. The fakes are nine lines each.

The part that gets skipped

The tangled test is not just slow. Every time anyone runs the test suite it writes a real row into whatever that connection string points at, and sends a real email to whatever address the test used. Teams work around this with a test database and a fake mail server, which is real infrastructure that has to be built, paid for and kept working. All of that exists to make up for one line that names a class directly.

The two halves, and the words for them. Interviewers ask people to tell these apart, and most cannot, so it is worth being precise:

NameWhat it isIn our code
Dependency inversionThe principle. Important code should depend on an interface, not on a specific class. CheckoutService names OrderRepository, never PostgresOrderRepository
Dependency injectionThe technique. The specific thing is handed in from outside, usually through the constructor. new CheckoutService(methods, repo, mail, audit)
Inversion of controlThe broader idea. Something else decides when and how your code runs. Spring building the objects and calling you, instead of your main driving everything

Where Spring comes in. Nothing in the clean version mentions Spring, and that is the point. All Spring does is take over the job that Main.java was doing by hand: build the real objects and pass them to whoever asked for them. Put @Component on PostgresOrderRepository and ask for an OrderRepository in the constructor, and Spring supplies it. Your test does not use Spring at all, it just calls the constructor with fakes, which is why the clean test runs in microseconds.

Code written this way is testable before and without a framework. If you need Spring to test a class, the class was not really inverted, it was just annotated.

Common wrong answers

"Dependency inversion means using Spring." Spring is one way of doing the injection. The principle is about which types your code names, and you can follow it perfectly with a constructor and no framework, which is exactly what this episode did.

"It means every class needs an interface." It means every class you want to swap or fake needs one. An interface with one implementation that nobody will ever fake is cost with no benefit.

"Field injection is fine, it is less typing." Fields marked @Autowired cannot be set from a plain test without reflection, so the class stops being testable without the framework. Constructor injection also lets the fields be final, and makes it obvious when a class has grown too many dependencies, because the constructor gets embarrassing.

Follow-up questions

Who should own the interface, the code that uses it or the code that implements it?

The code that uses it. This is the detail that makes the word "inversion" mean something, and most people miss it.

Normally the low level thing defines what it offers and the high level thing takes what it is given. A database library ships a class, and your business code adapts to it. The arrow of dependency points from your important code down to the detail.

The inversion is that your business code declares what it needs, in its own words, and the detail bends to fit. Our OrderRepository has one method, savePayment(orderId, method, feePaise). That is written in the language of orders and payments, not in the language of databases: there is no connection, no transaction, no SQL in the signature. Then PostgresOrderRepository is written to satisfy it.

Practically this means the interface belongs beside the code that uses it, not in a package with the database code. A good check: if you can read the interface and not be able to tell whether it is backed by Postgres, a file or an in memory map, you have got it right. If the interface mentions ResultSet, you have just moved the coupling behind a new name.

Does everything need an interface? That seems like a lot of files.

No, and over-applying this is one of the most common ways codebases get worse while following the rules. This episode measured the cost: the clean version is 52 percent more code and more than double the files. That cost is real and you should only pay it where you get something back.

You want an interface when at least one of these is true. There is genuinely more than one implementation, as with our payment methods. You need to fake it in a test, as with the database and the mailer. It crosses a boundary you do not control, such as a third party service, so it can be swapped when they change. Or you want to keep two parts of the system from knowing about each other.

You do not want one for a value object like Order. A record with three fields has nothing to swap and nothing to fake. You do not want one for a pure function with no external dependencies. And you do not want UserServiceImpl implementing UserService where there will only ever be one of them and it needs no faking, which is a naming convention pretending to be a design.

The honest test is: can you name the second implementation, or the fake you would write in a test? If you cannot name either, do not add the interface. You can always add it later, and adding it later is cheap.

What is the difference between a fake, a mock and a stub?

People use these words loosely, so being precise is a small, easy win in an interview. All three are stand-ins for a real dependency. They differ in what they do.

A stub returns canned answers and nothing more. "When asked for the exchange rate, always say 83." It exists to get the test past a dependency it does not care about.

A fake has a real, working implementation that is just not suitable for production. An in memory map standing in for a database is the classic. Our FakeRepository is a fake: it really does store what it was given, and the test reads it back afterwards.

A mock is about the conversation rather than the data. It records which methods were called, with what, how many times, and the test asserts on that. "Assert that send was called exactly once with this address." Libraries like Mockito build these for you.

Rough guidance worth saying: prefer checking the outcome over checking the conversation. Tests that assert on the outcome survive refactoring, because they only care about the result. Tests that assert every call made break when you reorganise the code even though nothing is actually wrong. Mocks earn their keep when the call is the outcome, such as proving that a payment gateway was charged exactly once and not twice.

Our constructor now has four parameters. Is that a smell?

Four is fine. It becomes a smell somewhere around seven or eight, and the useful part is what it is telling you.

A long constructor is not a problem with constructor injection. It is constructor injection reporting a problem that was already there. A class that needs nine collaborators is doing too much, and that is a single responsibility problem showing up in a place you cannot ignore. With field injection the same class needs the same nine things and nothing ever tells you, which is the real reason to avoid field injection.

So when the constructor gets embarrassing, do not reach for a way to hide it. Ask which of those nine things belong together. Often three or four of them are one concept that wants to be its own class. In our system, if checkout later needed a fraud checker, a rate limiter and a currency converter, those three might become one OrderChecks collaborator rather than three more parameters.

Say the number out loud in an interview: "I start paying attention around five or six, and I treat it as a hint that the class has grown, not as a reason to switch to field injection."

06 The quick round

  • Someone describes a scenario. Which principle are they asking about?
  • Which patterns naturally serve which principles?
  • When is SOLID not worth following?
  • Which principle do you break most often, and why?

The real skill. In an interview nobody asks "what is the L in SOLID". They describe a situation and wait to see whether you can name what is wrong with it. Often more than one answer is defensible, and saying so is a strong signal.

Work through these. Read the scenario, decide, then check.

A class called ReportService generates a PDF, writes it to disk, and emails it to a list of people. The finance team keeps asking for layout changes and the platform team wants to move file storage to S3.

Pick an answer.

Which patterns serve which principles. Interviewers like this question because it joins two topics they have already asked about. Each pattern below is explained in full, so you do not need anything else to answer it.

PatternWhat it isWhich principle it serves
Strategy One interface for a job that can be done several ways, one class per way, chosen at run time. Our PaymentMethod with card, netbanking and UPI. Open for extension. A new way is a new class, and no existing one is edited.
Factory A method or class whose job is to decide which concrete class to build, so callers ask for what they want rather than naming a class. Dependency inversion. The caller stops naming concrete classes, so the concrete classes can change without touching it.
Observer One thing happens and several unrelated parties are told about it, without the thing that happened knowing who they are. An order is placed, and email and audit both hear about it. Single responsibility. The checkout stops owning the email and the audit line; it only announces that a payment happened.
Decorator Adding behaviour by wrapping an object in another object with the same interface, rather than by subclassing. Wrap a payment method in one that also logs, and the wrapper looks exactly like a payment method. Open for extension, and it avoids the Liskov trap, because a wrapper keeps the interface's promise instead of overriding a parent's.
Adapter Making something you cannot change fit an interface you own, by writing a small class in between that translates. Dependency inversion. Your code keeps its own interface and the third party class bends to fit it, rather than the other way round.

The honest summary of the whole episode. This is the answer that separates people who have read about SOLID from people who have used it:

SOLID did not make this system shorter. It made it 52 percent longer, in 2.2 times the files. What it changed is where a change lands: in a new file instead of inside working code, and in the file that owns the concern instead of the file that owns everything. Adding a payment method went from editing nine lines of live payment logic to editing none. A test went from 301 milliseconds, one weak assertion and a real database, to 158 microseconds, five real assertions and nothing connected.

That is a trade, not a free win, and it only pays where the code is going to change.

Common wrong answers

Reciting the five names and their definitions. Everyone can do this. It proves nothing, and the interviewer's next question is always a scenario anyway.

"You should always follow all five." A one off migration script, a proof of concept, a piece of code with a known deletion date: leave them simple. Applying all five everywhere is how you get twelve files that could have been one.

"SOLID makes code simpler." It does not, and the numbers in this episode say so. It makes code cheaper to change. Claiming otherwise to an interviewer who has maintained a heavily abstracted codebase will not go well.

Follow-up questions

When would you deliberately not follow these principles?

Have real examples ready, because this question is checking whether you have judgement or just rules.

Code with a known end date. A migration script that runs once and gets deleted. Making it extensible is work spent on a future that will not arrive.

Before you know the second case. With one payment method, the interface is a guess. With two, it is informed. Waiting costs you one small refactor and saves you from designing the wrong abstraction, which is much more expensive to unpick.

Where the indirection would hide something that must stay obvious. In code where the order of operations is the whole point, such as a tricky transaction or a piece of concurrency, spreading it over six files to satisfy a principle can make it genuinely harder to get right. Being able to read the sequence top to bottom has value.

Very hot code. Rare, and you should say it is rare, but layers of interfaces in an extremely tight loop can matter. Measure before claiming it, because modern JVMs remove most of that cost.

The framing to use: these principles buy you cheap change. Where change is not coming, you are paying for something you will not use.

Which one do you break most often?

This is a character question as much as a technical one. A confident, specific answer beats a modest vague one.

A good honest answer is single responsibility, because it is the one that degrades quietly. Nobody adds a sixth job to a class on purpose. It happens one small, reasonable addition at a time, each of which is easier to put where the related code already lives than to justify a new file for. Six months later the class has six reasons to change and no single commit did anything wrong.

Then say what you do about it, which is the part they are actually listening for. A useful habit: when a change means opening a file for a reason that has nothing to do with why you last opened it, that is the signal to split. Not a line count, not a method count. The reason you are there.

Liskov is a good second answer, because it is the one people break without noticing at all. An override that only throws, or a subclass that quietly tightens what it will accept, gets through review easily because each looks locally sensible.

How do these five relate to each other? Are they independent?

They are not independent, and noticing that is a strong answer because most people present them as a flat list of five unrelated rules.

Liskov and interface segregation are two sides of the same coin. Both are about classes claiming capabilities they do not have. Our gift card broke Liskov by inheriting a refund it could not do. Our UPI broke interface segregation by implementing a split it could not do. Same fault, one through inheritance and one through an interface, and the same fix: stop claiming it.

Open for extension usually needs dependency inversion to work. You cannot add UPI as a new file if CheckoutService names CardPayment directly. It has to name the interface first. Extension is the goal, inversion is what makes it reachable.

Single responsibility makes all the others cheaper. A class doing one job has a small interface, so segregation is easy. It has few collaborators, so inversion is easy. It has one behaviour to promise, so substitution is easy. Get this one right and the others mostly follow.

A compact way to say it: single responsibility is about splitting things up, and the other four are about how the split pieces should talk to each other.

The interviewer says my design is over engineered. How do I respond?

Do not defend it by naming principles. That is the answer they are expecting and it confirms their point.

Agree with the cost first, out loud and specifically. "You are right that it is more code. About 50 percent more here, and roughly twice the files." Naming the cost yourself shows you know what you spent, and it takes the argument away from them.

Then say what you bought and why you thought it was worth it, in terms of the change that is coming. "I split it here because payment methods are an axis the business changes several times a year. I did not split the order record or the fee formula, because nothing suggests those will change independently."

Then offer the smaller version, which is the part that turns a disagreement into a conversation. "If we only ever expect two payment methods, an if-else is genuinely better and I would write that instead." An interviewer probing for over engineering is usually checking whether you can scale a design down, not whether you can defend it. Being able to name the simpler design you rejected, and the condition under which you would pick it, is the answer.
