The service is frozen and memory is fine

Episode 1 was about memory. This one is about the other half: what to do when the application is stuck, or slow, or burning all the CPU, and the memory graph is perfectly flat. Everything on this page was produced by running the code and capturing the real output.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 What a thread is doing

  • Name the thread states and what each one means.
  • What is the difference between BLOCKED and WAITING?
  • A thread is RUNNABLE. Does that mean it is using the CPU right now?
  • Which states are normal in a healthy application, and which are a warning sign?

A thread dump is a photo of every thread in your application and what each one was doing at that moment. To read it, you need to know the handful of states a thread can be in.

Most people can list the states. Very few can say what the difference between two of them actually means, and that is the follow-up that gets asked.

The difference that gets asked

BLOCKED means the thread wants a lock and another thread is holding it. It did not choose to wait. It was stopped at the door.

WAITING means the thread chose to wait. It called something like wait(), join(), or it is waiting for a result that has not arrived yet. It will sit there until somebody wakes it up.

Put simply: BLOCKED is "I want in and I cannot get in". WAITING is "wake me when you are ready".

That distinction matters because lots of BLOCKED threads is nearly always a problem, while lots of WAITING threads is completely normal. An idle thread pool is full of WAITING threads and that is exactly how it should look.

The trap in RUNNABLE. RUNNABLE does not mean "using the CPU right now". It means "not waiting for anything Java knows about". A thread reading from a socket shows as RUNNABLE even though it is doing nothing but waiting for the network, because Java hands that wait to the operating system and stops tracking it.

So a dump full of RUNNABLE threads does not prove your CPU is busy. To know that, you need the cpu= number, which is in Chapter 4.

"BLOCKED and WAITING are basically the same." They lead to completely different fixes. BLOCKED means a lock is being held too long, so you look at who holds it. WAITING usually means something upstream is slow or never replies, so you look at timeouts.

"RUNNABLE means the thread is running." It means it is not waiting on anything Java is tracking. It could be sitting on a network read doing nothing at all.

Follow-up questions

What is the difference between WAITING and TIMED_WAITING?

Only whether there is a time limit.

WAITING comes from calling something with no timeout: object.wait(), thread.join(), or waiting for a result with no deadline. The thread will sit there forever unless something wakes it.

TIMED_WAITING comes from the same calls with a number attached: Thread.sleep(1000), wait(5000), join(2000), or waiting for a result with a deadline. The thread gives up on its own eventually.

This looks like a trivia question and it is not. In a real incident, a pool of threads stuck in WAITING is much worse news than the same pool in TIMED_WAITING, because nothing will ever release them by itself. Somebody wrote a call with no timeout, and now the service needs a restart to recover.

That is why "always set a timeout" is such a common piece of advice. It converts a permanent freeze into a temporary slowdown.

If a thread is stuck reading from the network, which state is it in?

RUNNABLE, which surprises almost everybody, and it is a favourite follow-up.

The reason is where the waiting happens. Java tracks waiting that Java itself controls: locks, sleeps, waits on objects. But when you read from a socket, Java hands the request to the operating system and asks it to wake the thread up when data arrives. Java is no longer managing that wait, so it has nothing to report, and the thread stays marked RUNNABLE.

The practical effect is a very confusing dump. You see fifty RUNNABLE threads and assume the CPU is on fire. Then you check and the CPU is at 2 percent, because all fifty are sitting on a socket read waiting for a service that is not answering.

How to tell the two apart: look at the top line of the stack. If it says something like socketRead0 or a similar network method, the thread is waiting for the network, not using the CPU. And check the cpu= number in the dump, which will be near zero for a thread that is really just waiting.

What does it mean when many threads share the same stack trace?

It is the single most useful pattern in the whole file, and it is how you find problems quickly instead of reading hundreds of threads one by one.

Threads in a pool are normally spread across different work, so their stacks differ. When twenty, fifty or two hundred of them show the same name pattern and the same stack trace in the same state, they are all stuck on the same thing. That shared line is your problem.

What it usually means depends on the state. All stuck in WAITING or TIMED_WAITING on the same call means something they all depend on is slow or not answering, like a database or a downstream service. All stuck in BLOCKED on the same lock means one piece of code is holding a lock far too long and everything else is queueing behind it.

Practical tip that works on any dump: rather than reading it top to bottom, count the states first, then look at whichever group is biggest. That one group usually explains the whole incident.

02 Taking a dump, and reading one entry

  • Three ways to take a thread dump.
  • How is taking a thread dump different from taking a memory snapshot?
  • Why do you take more than one?
  • Read out every field in a single thread entry and say what it means.

Three ways, and you should know all three because different interviewers name different ones.

# 1. The modern one. Works everywhere.
jcmd <pid> Thread.print > dump.txt

# 2. The classic. Same output, older tool.
jstack <pid> > dump.txt

# 3. No tools installed? Send the signal.
kill -3 <pid>      # Linux. Output goes to the application log, not to a file.

That third one is worth remembering. On a stripped down container with no JDK tools installed, kill -3 still works. It does not kill anything, despite the name. It asks Java to print a thread dump, and Java prints it into its own log output.

The big difference from Episode 1. A memory snapshot freezes your whole application for as long as it takes to write, which can be tens of seconds on a large heap. A thread dump is cheap. It pauses things for a few milliseconds and the file is a few hundred kilobytes.

So the safety rule is the opposite way round. You should not take memory snapshots casually, but you absolutely should take thread dumps freely. If an interviewer asks whether it is safe on production, the answer is yes, and knowing the difference between the two shows you understand both.

Always take three

One dump is a single photo. It tells you where threads are, but not whether they are moving.

Take three dumps, about ten seconds apart. Then compare them.

  • If a thread is on the same line in all three, it is genuinely stuck.
  • If it moves between them, it is working, just slowly, and you are looking at the wrong problem.

This single habit separates people who have actually done this from people who have read about it. Say it in an interview without being asked.

Reading one entry

Here is a real thread entry, copied from an actual dump taken while the demo was running. Click any highlighted part to see what it means.

daemon prio=5 os_prio=0 tid=0x000002741dce2a60 nid=24068 java.lang.Thread.State: at java.lang.Thread.run(java.base@24.0.2/Thread.java:1447)
click a highlighted part
One thread, eight pieces of information

Most people read only the state and the stack. The two numbers that actually solve a CPU incident are cpu= and elapsed=, and almost nobody looks at them.

"I would take a thread dump and read it." Too vague, and it is what everyone says. Say how many you would take and how far apart, and say what you would compare between them.

Follow-up questions

The container has no jstack or jcmd. Now what?

This is common, because production images are often built on a runtime that ships without the developer tools to keep the image small.

First option: kill -3 <pid>. This works with no tools at all. It does not stop the program. Java catches that signal and prints a full thread dump into its standard output, which means it lands in your container logs. So you take the dump and then read it with your normal log viewer.

Second option: get a shell with the tools. In Kubernetes you can attach a temporary debug container that shares the same process space, and run jcmd from there against the running program.

Third option: expose it from the application. If you run Spring Boot, the built in monitoring endpoints include one that returns a thread dump over HTTP. It has to be enabled and protected, but when it is, you can fetch a dump without touching the container at all.

The good habit is deciding this before an incident, not during one. Being able to say that in an interview is worth more than naming the commands.

Does taking a thread dump slow the application down?

Barely, and being confident about this is a good signal because it shows you have done it on a live system.

To take the dump, Java has to briefly bring all threads to a stopping point so it can read them consistently. That pause is typically a few milliseconds. For a few hundred threads you will not see it in your latency graphs.

Compare that with a memory snapshot, which has to walk the entire heap and write it to disk, freezing the application for seconds on a big heap.

The honest caveat: if you have a very large number of threads, say tens of thousands, the pause grows and becomes noticeable. But at that point the thread count is itself the bug you are looking for.

So the practical answer is: take thread dumps freely, take memory snapshots carefully.

Why does the dump show two different numbers for the same thread?

Because they come from two different places, and knowing which is which saves you real time during an incident.

One is Java's own internal number for the thread. The other is the number the operating system uses for it. They are completely different numbering systems and they do not match.

The operating system number is the important one, because that is what system tools report. When a monitoring tool tells you a particular thread is eating the CPU, it gives you the operating system number, and you then have to find that same number in the dump.

The awkward part on Linux is that the dump traditionally prints that number in hexadecimal, while the system tools print it in ordinary decimal. So the classic recipe involves converting one to the other before you can match them up. Newer Java versions also print a plain decimal number in square brackets, which removes that step when it is available.

Chapter 4 walks through this properly with the real numbers.

03 Deadlock

  • What is a deadlock, in one sentence?
  • What four things must all be true for one to happen?
  • How do you find one in a thread dump?
  • How do you prevent them?
  • Can you recover from one without restarting?

A deadlock is two or more threads each holding something the other one needs, and neither will let go. Nothing moves again, ever.

The classic version is two locks taken in opposite order.

The code that causes it

Thread A:                        Thread B:
  synchronized (ACCOUNT_A) {       synchronized (ACCOUNT_B) {
      synchronized (ACCOUNT_B) {       synchronized (ACCOUNT_A) {
          ...                              ...

Read the order. A takes account A then wants account B. B takes account B then wants account A. If they interleave badly, both stop forever.

Notice how ordinary this looks. Nobody writes this on purpose. It happens because two methods in different files each lock two things, and nobody checked that they do it in the same order.

Finding it in the dump

This is the good news, and the reason this question is popular. Java finds deadlocks for you. It checks for the circle and writes the answer at the bottom of the dump.

This is the real output from running the demo:

Found one Java-level deadlock:
=============================
"transfer-A-to-B":
  waiting to lock monitor 0x0000021f910ad680 (object 0x0000000710a40628),
  which is held by "transfer-B-to-A"

"transfer-B-to-A":
  waiting to lock monitor 0x0000021f4bd5ef90 (object 0x0000000710a40618),
  which is held by "transfer-A-to-B"

...

Found 1 deadlock.

It names both threads and tells you which one holds what. Read it as a sentence: A is waiting for something B holds, and B is waiting for something A holds. That is the circle.

The one line answer for an interview. "Take a thread dump and search for the words Found one Java-level deadlock. Java detects the cycle itself and names both threads and both locks. Then I look at the two stack traces it prints to find which lines took the locks in the wrong order."

And here is the individual thread entry, also real. Note the two lines under the stack:

"transfer-A-to-B" #26 [12416] ... waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
	at DeadlockDemo.lambda$main$0(DeadlockDemo.java:21)
	- waiting to lock <0x0000000710a40628>
	- locked <0x0000000710a40618>

Those two lines are the whole story in miniature. This thread has one lock and wants another. Find the other thread with those same two numbers the other way round, and you have your pair.

Preventing them

  1. Always take locks in the same order. This is the real fix and it removes the circle completely. If every piece of code locks account A before account B, no circle can form. When the objects have no natural order, sort by something stable like their id.
  2. Hold one lock at a time. If you never hold two at once, you cannot deadlock. Often possible with a bit of restructuring.
  3. Use a lock with a timeout. ReentrantLock lets you try to take a lock and give up after a while. This turns a permanent freeze into a failed request you can retry, which is much easier to live with.
  4. Do not hold a lock while calling something slow. Never make a network call or a database call while holding a lock. It multiplies how long everyone else waits.

"You can detect deadlocks by looking for BLOCKED threads." Not on its own. BLOCKED threads are very common and usually harmless, because locks are held briefly all the time. A deadlock is specifically a circle, and Java reports it explicitly.

"You fix it by adding a timeout." A timeout stops the freeze, but the ordering bug is still there and will keep firing. Fix the lock order, and use the timeout as a safety net.

Follow-up questions

What four conditions are needed for a deadlock?

All four have to be true at once. Break any one and it cannot happen.

1. Only one at a time. The resource cannot be shared. A lock is a lock, so only one thread can hold it.

2. Hold and wait. A thread is holding something while asking for something else. This is the one you attack by holding only one lock at a time.

3. No taking it away. You cannot force a thread to give up a lock it already has. Java will not do it for you.

4. A circle. A is waiting for B, and B is waiting back for A, possibly through a longer chain.

In practice you break number 4, because it is by far the easiest. Locking everything in the same consistent order makes a circle impossible, and it costs nothing at runtime.

Worth saying out loud in an interview: the reason consistent lock ordering is the standard advice is precisely that it kills condition four, and condition four is the only one you can remove without changing what your code does.

Can you recover from a deadlock without restarting?

With plain synchronized locks, no. There is no way to force a thread to release one, and no way to interrupt a thread that is blocked waiting for one. Those threads are gone for the life of the process. If enough of your pool ends up there, the service needs a restart.

This is exactly why people move to ReentrantLock in code where deadlock is a real risk. It gives you two ways out that synchronized does not have. You can try to take the lock with a time limit and give up if you do not get it. And you can take it in a way that lets the thread be interrupted, so you can cancel it from outside.

Neither of those fixes the underlying ordering bug. What they do is turn "the service is dead until someone restarts it at 3am" into "some requests failed and were retried". That is a very different incident.

So the honest interview answer is: recovery is a restart, prevention is consistent lock ordering, and a timeout is what stops it becoming an outage while you fix the real cause.

Can a deadlock involve a database instead of Java locks?

Yes, and it is far more common in real systems than the two lock Java example everybody learns.

Databases take locks on rows. Two transactions updating the same two rows in opposite order deadlock in exactly the same way. Transaction one locks the customer row then wants the order row, transaction two does the reverse.

The important difference is who notices. Java cannot see database locks at all. Your thread dump will show the threads as RUNNABLE or waiting on a socket read, because from Java's point of view they are just waiting for a slow query. There will be no "Found one Java-level deadlock" line, because as far as Java is concerned nothing is wrong.

Most databases detect this themselves, pick one transaction as the loser, and fail it with a deadlock error. So the evidence appears in your application logs as a failed query, not in the thread dump.

That is a strong thing to say in an interview, because it shows you know the limits of the tool. A thread dump only knows about locks inside this one Java process. Database locks, file locks, and locks held by another service are all invisible to it.

04 CPU at 100 percent

  • Walk through finding which thread is burning the CPU.
  • Which two numbers in the dump identify the busy thread on their own?
  • Why do you convert a number to hexadecimal in the classic method?
  • Why take more than one dump for this?

The setup is always the same. CPU is pinned, the service is slow, memory is fine. You have hundreds of threads and you need to find the one doing it.

The short way, using the dump alone

This works on any operating system and almost nobody mentions it, which makes it a strong answer.

Every thread entry carries two numbers. cpu= is how much processor time that thread has used in its whole life. elapsed= is how long the thread has existed. Compare them.

Here are two entries from the same real dump, taken while one thread was spinning:

"report-builder" ... cpu=5500.00ms  elapsed=5.76s  runnable
   java.lang.Thread.State: RUNNABLE
	at HotCpuDemo.spin(HotCpuDemo.java:34)

"worker-1" ... cpu=0.00ms  elapsed=5.76s  waiting on condition
   java.lang.Thread.State: TIMED_WAITING (sleeping)
	at java.lang.Thread.sleepNanos0(Native Method)

Read those numbers. report-builder used 5.5 seconds of processor time in 5.76 seconds of real time. That is about 95 percent of one core, continuously, since it started. worker-1 existed for exactly as long and used none at all.

You have your culprit, and the very next line names the method and the line number.

Say this in the interview. "Before anything else I would compare cpu= against elapsed= in the dump. A thread whose processor time is close to its lifetime is spinning, and the stack underneath it names the exact line." It is faster than the classic method and it works even when you cannot get a shell on the machine.

The classic way, which interviewers expect

This is the recipe most people are taught, and it is what a Linux focused interviewer wants to hear.

# 1. Show individual threads instead of the whole program, sorted by CPU
top -H -p <pid>

# 2. Take the busy thread id, say 24068, and convert it to hexadecimal
printf '%x\n' 24068        # gives 5e04

# 3. Take a thread dump
jstack <pid> > dump.txt

# 4. Find that thread in the dump
grep -A 20 'nid=0x5e04' dump.txt

Why the conversion? Because the two tools disagree about how to print the same number. The system tool prints thread ids as ordinary decimal. The thread dump has traditionally printed them in hexadecimal, which is a different way of writing the same value. Step two just translates between the two so you can match them.

Newer Java versions also print a plain decimal id in square brackets at the start of each entry, like [24068] in the real output above. Where that is present you can skip the conversion and search for the decimal number directly.

On Windows, for practising. There is no top -H. Use the short way instead and read cpu= straight from the dump, which is exactly how the numbers above were produced. The demo files and the dumps for this episode were all captured on Windows this way.

Take three, again

One dump can mislead you badly here. A thread that happens to be running at the instant you take the photo looks guilty and is completely innocent.

Take three dumps ten seconds apart. The real culprit is on the same line in all three, and its cpu= number climbs sharply between them. An innocent thread will have moved on and its processor time will barely change.

"I would look for RUNNABLE threads." Not enough on its own. A thread waiting on the network also shows as RUNNABLE while using no processor time at all. You need cpu=, or the system tool, to tell those apart.

"I would restart the service." It will come back. Whatever loop was spinning will spin again on the next request that triggers it.

Follow-up questions

CPU is high but every thread shows low cpu time. What now?

Then no single thread is the problem, and you should suspect one of three things.

Garbage collection. The threads that clean up memory are usually not shown in the ordinary part of a thread dump, so their work is invisible there. If cleanup is running constantly, the processor is busy but your application threads look idle. Check how much time is going into cleanup. This connects straight back to Episode 1, because a memory leak eventually shows up as a CPU problem.

Lots of threads each doing a little. Five hundred threads at 1 percent each still adds up to five whole cores. No individual entry looks alarming. The tell is a very high thread count and a request rate that does not justify it.

Something outside Java. Another process on the same machine, or a library written in C doing work that Java cannot see. Check whether the processor time even belongs to your program before digging further.

The general lesson worth saying out loud: a thread dump only shows you Java threads doing Java things. When the numbers do not add up, the cause is usually something the dump cannot see.

How do you tell a spinning loop from genuinely heavy work?

Both show high processor time, so the numbers alone will not separate them. The difference is in the stack, and in whether it changes.

A spinning loop stays still. Take three dumps and it is on the same few lines every time, usually inside a small loop, often a retry that never gives up or a check that never becomes true. The line numbers barely move.

Real work moves. Three dumps show three different places, because the thread is progressing through actual work: parsing, then calculating, then writing.

The other signal is what the code is doing. A loop that checks a condition over and over with no pause is a bug, because it burns a whole core doing nothing. A loop that is sorting a large list is just slow, which is a different conversation about the algorithm.

Practical follow-up: if it is genuinely heavy work, the fix is not a thread dump problem at all. It is either doing less work, doing it somewhere else, or doing it once and caching the answer.

Why not just attach a debugger to the running service?

Because a debugger changes the thing you are trying to measure, and on production it is dangerous.

Setting a breakpoint stops threads. On a live service that means requests pile up behind the pause, and you can turn a slow service into a completely dead one in seconds. Some debugger features also slow the whole program down noticeably even when nothing is paused.

There is also a security angle worth mentioning. The port a debugger connects to allows running arbitrary code inside your application, so leaving it open on a production machine is a serious hole.

Thread dumps are the right tool precisely because they are passive. You take a photo and the application carries on. That is why the answer to "how do you debug a stuck production service" is dumps and monitoring, not a debugger, and saying so shows production judgement.

05 When a dump is not enough

  • When does a thread dump stop being the right tool?
  • What is a profiler doing that a dump is not?
  • What is Java Flight Recorder and when would you turn it on?
  • What is a flame graph showing you?

A thread dump is a photo. It is perfect for things that are stuck, because a stuck thread looks the same in every photo you take.

It is bad at things that are fast and frequent. If a method takes two milliseconds but runs a million times an hour, you will almost never catch it in a photo. You need something that records continuously instead.

Slow and you do not know whyFlame graphShows where the time actually goes, ranked.

What a profiler does differently

A profiler takes the same kind of photo, but hundreds of times a second, and adds up the results. If a method appears in 30 percent of those samples, it is using roughly 30 percent of your processor time.

That is the whole idea. A thread dump asks "what is happening right now". A profiler asks "where does the time actually go", and only the second question can be answered by sampling repeatedly.

The commonly used one for Java is async-profiler. It is popular because it can be attached to a program that is already running, it costs very little performance, and unlike some older tools it does not distort the answer by only sampling at convenient moments.

What a flame graph shows

A flame graph is how profiler output is usually drawn. It is simpler than it looks.

  • Each box is a method.
  • A box sits on top of the method that called it, so height is just call depth.
  • Width is the only thing that matters. A wide box means that method was on the stack in a large share of the samples.
  • Colours usually mean nothing at all.

So you read it by looking for wide plateaus, not tall towers. A tall narrow spike is deep call nesting, which is normal. A wide flat box is where your time is going.

Java Flight Recorder

Flight Recorder is a recorder built into Java itself. Instead of you turning up after the problem and taking a photo, it is already running and writing down what happened.

You turn it on when the problem is intermittent: slow every few hours, or only at 3am, or only under a load you cannot reproduce. It records events like slow methods, cleanup pauses, lock contention and file access, then you open the file afterwards and look at the window when things went wrong.

# start a recording on a program that is already running
jcmd <pid> JFR.start name=diag duration=120s filename=/tmp/rec.jfr

The reason people like it is cost. Its default settings are designed to be safe to leave on in production, so you can have the evidence ready before the incident rather than trying to reproduce it afterwards.

"I would use a profiler." Fine for a slowness problem, wrong for a freeze. If threads are stuck, a profiler tells you almost nothing, because nothing is consuming time. Match the tool to the symptom, and say why you chose it.

Follow-up questions

Is it safe to run a profiler on production?

It depends entirely on which tool and which settings, and giving a nuanced answer here scores well.

Flight Recorder on its default settings is designed for this. The overhead is small, usually quoted at around one percent, and it exists precisely so you can leave it running on real systems. This is the safe default answer.

async-profiler at a sensible sampling rate is also generally fine. It samples rather than instrumenting every call, so the cost is bounded and predictable. Most teams are comfortable attaching it to one instance during an incident.

The dangerous kind is a profiler that rewrites your code to count every method call. That can slow an application down by a large factor and change its behaviour, so timing sensitive bugs may vanish or appear. Never do that on production.

The good practical answer is to profile one instance rather than all of them, take it out of the pool first if you can, and prefer sampling over instrumenting. That way even a surprise is contained to a single machine.

What would you use for a service that is slow only at 3am?

Flight Recorder, and the reasoning matters more than the name.

You cannot take a thread dump at 3am unless someone is awake and watching, and by the time an alert wakes you the moment has often passed. You also cannot reproduce it, because whatever causes it is tied to real conditions: a batch job, a backup, a scheduled report, a traffic pattern.

So you need something that is already recording when it happens. Start a recording that runs continuously, or configure it to always keep the last hour, and then pull the file the next morning and look at the window that matters.

What to look for in that window, in order: unusually long cleanup pauses, threads blocked on the same lock, slow database calls, and any scheduled job that lines up with the timing.

The strong extra sentence: 3am is a very big clue by itself. Something scheduled is usually running. Before reaching for any tool at all, look at what is on the schedule, because backups, batch jobs and nightly reports explain a surprising share of these.

How do you know whether the problem is your code or something you call?

Look at what the threads are doing, and in particular at whether they are using the processor or waiting.

If threads are waiting, in WAITING or TIMED_WAITING, with almost no processor time used, and their stacks end in a network or database call, the slowness is not yours. You are waiting on something else. Your fix is timeouts, retries, a circuit breaker, or a conversation with whoever owns that service.

If threads are using real processor time, with high cpu numbers and stacks inside your own classes, the slowness is yours. Your fix is in the code.

The number that settles it quickly is the same one from Chapter 4. Compare processor time used against how long the thread has existed. Waiting threads use almost none, no matter how slow the request feels.

Worth adding: this is also how you answer the blame question in a real incident. "Our threads are idle and waiting on their endpoint" is a fact from the dump, not an opinion, and it moves the conversation on quickly.

06 Pool starvation

  • What is thread pool starvation?
  • Why does the service look frozen when memory and CPU are both fine?
  • What does it look like in a thread dump?
  • What is the actual fix, and what is only a workaround?

This is the most common freeze in real services, and it is the one people are least prepared for, because nothing looks wrong. Memory is flat. CPU is near zero. And the service answers nothing.

A thread pool has a fixed number of threads. Requests arrive, a free thread picks one up, and when it finishes it goes back and takes the next. Simple, until every thread is stuck on something slow at the same time. Then there is nobody left to pick up the next request, and everything queues behind them.

Watch it happen

Four threads. Requests keep arriving. In the first mode the slow call has no timeout, so threads never come back. In the second it gives up after a while, so threads keep cycling.

What it looks like in a dump

This is real output from the demo. Three threads in the pool, ten jobs submitted, and every thread stuck in exactly the same place:

"pool-1-thread-1" ... cpu=0.00ms elapsed=6.74s  waiting on condition
   java.lang.Thread.State: TIMED_WAITING (sleeping)
	at PoolStarvationDemo.callSlowService(...)

"pool-1-thread-2" ... cpu=0.00ms elapsed=6.74s  waiting on condition
   java.lang.Thread.State: TIMED_WAITING (sleeping)
	at PoolStarvationDemo.callSlowService(...)

"pool-1-thread-3" ... cpu=0.00ms elapsed=6.74s  waiting on condition
   java.lang.Thread.State: TIMED_WAITING (sleeping)
	at PoolStarvationDemo.callSlowService(...)

The program also reported: pool threads = 3, jobs running = 3, jobs waiting = 7.

Three signs together, and once you have seen them you cannot miss them again:

  1. Same name pattern, because they are all from one pool.
  2. Same stack trace, because they are all stuck on the same call.
  3. Processor time near zero, because they are waiting, not working.

The sentence that shows you have seen this before. "Memory flat, processor near zero, service not responding: I would take a thread dump and count how many threads share the same stack. If a whole pool is sitting on one call, the service is not broken, it is waiting for something that never answers."

The fix, and the workaround

People reach for the wrong one, so be clear about which is which.

The workaround is a bigger pool. If every thread is stuck forever, doubling the pool just means twice as many stuck threads and a slightly later freeze. It buys minutes.

The fix is a timeout on the slow call. A thread that gives up after two seconds comes back and serves someone else. The service gets slower under stress instead of dying, which is what you want.

Then two more things that turn a slowdown into something manageable:

  • Give the queue a maximum size, and decide what happens when it is full. Rejecting a request quickly is much better than accepting it and never answering. An unlimited queue also grows until memory runs out, which turns this into an Episode 1 problem as well.
  • Keep separate pools for separate things. If your slow reporting calls and your fast customer requests share one pool, reports will starve customers. Separate pools mean a failure in one does not take the other down.

"Increase the pool size." The most common answer and mostly wrong. If the calls never return, more threads means more stuck threads.

"Memory and CPU are fine, so the application is fine." This is exactly the case where both look perfect and the service is completely dead. Thread exhaustion is invisible on the two graphs everybody watches.

Follow-up questions

How do you pick the right pool size?

It depends entirely on what the threads spend their time doing, and saying that first is the answer.

For work that uses the processor, like calculations or parsing, the useful size is close to the number of cores you have. More threads than cores does not make the work finish faster, it just means the machine spends time switching between them instead of doing work.

For work that waits, like calling a database or another service, you can have many more threads than cores, because most are idle at any moment. The right number depends on how long each call takes and how many you need to handle at once.

The rough reasoning goes: if a call takes 100 milliseconds and you need to handle 200 requests a second, you need about 20 threads busy at any time, so a pool of 20 to 30 is sensible.

The more important point, and the one worth landing: do not tune the number until you have set the timeouts. Pool size only matters when threads come back. If they never come back, no size is big enough.

Do virtual threads make this problem go away?

They remove one version of it and leave the more important one, so the honest answer is "partly, and here is what is left".

Virtual threads are cheap enough that you can have a very large number of them, so you stop being limited by having only a few hundred threads available. Blocking on a slow call no longer wastes a scarce resource in the same way. That genuinely removes the classic starvation shape where a small fixed pool fills up.

What does not go away is the downstream service being slow. If a service takes 30 seconds, your users still wait 30 seconds. You have simply moved the queue from your thread pool to somewhere else. And you can now pile up so many waiting calls that you overwhelm the slow service completely, making it worse.

So you still need timeouts, and you still need a limit on how many calls you send to one dependency at a time. The tool for that becomes something like a bulkhead or a circuit breaker rather than the pool size itself.

The nuance that lands well: virtual threads fix the resource problem, not the dependency problem. Anyone who says they remove the need for timeouts has not run them in production.

Why is a queue with no size limit dangerous?

Because it hides the problem until it becomes a much worse one, and it connects the two episodes together.

With no limit, work that cannot be handled just accumulates. From the outside the service looks like it is accepting everything, which feels like coping. In reality every request is being accepted and then answered far too late or not at all, and the caller has usually given up long before you get to it.

Then there is the memory. Every queued item is an object being held, so an unlimited queue is also an unlimited amount of memory. Under sustained pressure it becomes an out of memory error, which means a thread problem turns into a memory crash and the real cause gets buried.

With a size limit you get a decision point instead. When the queue is full you can reject quickly, which tells the caller immediately so it can retry or fail cleanly, and it keeps memory bounded. Rejecting fast is a much better user experience than accepting and never answering.

The general principle worth saying: an unlimited queue is not backpressure, it is a delayed outage. Real backpressure means telling the caller to slow down, and you cannot do that if you always say yes.

G Word list

Every term on this page that you might not already know.

thread dump
A photo of every thread in your application and what each one was doing at that moment.
thread state
What a thread is currently doing: running, waiting for a lock, waiting for something else, or finished.
lock
A way of making sure only one thread at a time can touch something. In a dump these are called monitors.
monitor
The dump's word for the lock attached to an object. "Waiting for monitor entry" means waiting to get a lock.
deadlock
Two or more threads each holding something the other needs, so none of them can ever continue.
nid
The number the operating system uses for a thread. On Linux the dump usually prints it in hexadecimal, which is why you convert.
hexadecimal
Another way of writing numbers, using 0 to 9 and then a to f. The value 24068 is written 5e04.
thread pool
A fixed set of reusable threads that take jobs from a queue, so you do not create a new thread per request.
pool starvation
When every thread in a pool is stuck on something slow, so no thread is left to handle new work.
timeout
A time limit on a call. Without one, a slow dependency can hold a thread forever.
profiler
A tool that samples what your program is doing hundreds of times a second and adds it up, to show where time actually goes.
flame graph
The usual picture of profiler output. Each box is a method, width means share of time. Look for wide boxes, not tall ones.
Java Flight Recorder
A recorder built into Java that writes down what happened, so you can look at a problem after it occurred. Often shortened to JFR.
async-profiler
A widely used profiler for Java that can attach to a running program and costs very little performance.
virtual threads
A newer kind of thread introduced in Java 21 that is cheap enough to have very many of. Covered properly in a later episode.
pid
Process id. The number the operating system uses for your running program. You pass it to the tools.
