Where Java memory goes, and how to prove it

Six chapters on where Java keeps things in memory, the six different ways it runs out, how to take a memory snapshot safely, how to read that snapshot, the nine common mistakes that cause leaks, and how to say all of it out loud in an interview.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 Where memory goes

  • Name the five places Java keeps things in memory.
  • Which of those five does the -Xmx setting control?
  • Where does a local int live? Where does a String object live?
  • Where are static variables kept?
  • Why can a server be killed for using too much memory when the heap looks fine?

Java does not keep everything in one big pile. It splits memory into five separate places. Each place holds different things, and each one runs out in its own way.

If you cannot name these five places, you cannot fix a memory problem. You can only guess. That is what the interviewer is checking.

A small example

public void greet() {
    int count = 5;                    // stays on the stack
    String name = "Anupam";           // the label is on the stack, the text is on the heap
    Employee e = new Employee(name);  // the label is on the stack, the object is on the heap
}

Three variables, but only one of them sits fully on the stack. count is a plain number declared inside a method, so it lives in the stack.

name and e work differently. Think of them as labels that point at something. The label sits on the stack. The thing it points at sits on the heap.

When the method finishes, the stack part is thrown away at once. The objects on the heap are not. They stay until Java is sure nothing else is still pointing at them.

How this gets asked

  • "Explain how Java uses memory."
  • "What is the difference between heap and stack?"
  • "Where are static variables kept?"
  • "What is Metaspace and why did it replace PermGen?"

Common wrong answer: "Static variables and the text pool are in Metaspace."

This sounds right, which is exactly why it gets used to catch people out. Both are on the heap. The text pool moved to the heap in Java 7, and static variables sit on the heap too.

Box 2 holds a description of your classes. Their shape, their method code. It does not hold the actual data your classes point at.

Common wrong answer: "Stack holds numbers, heap holds objects."

Nearly right, but the missing part matters. Only numbers declared inside a method go on the stack. A number that is a field of an object lives on the heap, inside that object.

Follow-up questions

The heap has a size limit. What about thread stacks?

They are extra memory on top. Every thread gets its own stack when it starts, and each one is about 1 MB by default.

So a server running 1,000 threads is using roughly 1 GB of memory that -Xmx knows nothing about. If you set -Xmx2g and expect the program to use 2 GB in total, you are wrong by however many threads you are running.

This is also why a thread leak does not show up as heap growth. The thread objects on the heap are tiny. The expensive part is the 1 MB of workspace behind each one, and that is outside the heap.

Why does this matter on a real server?

Because when your server decides you have used too much memory, it looks at the whole program. Your monitoring graph usually only shows the heap. Those are two different numbers.

So this happens. The heap sits at 60 percent, your dashboard is green, and the program keeps getting shut down anyway. The memory was never in the heap. It was in thread stacks, class info, direct memory, or a library written in C.

When Linux shuts a program down for using too much memory, the program stops instantly with the number 137. Java gets no warning and no chance to react, so there is no error message, no memory snapshot, and nothing useful in your logs. Just a server that restarted.

The fix is to stop staring at the heap graph and compare it against the total memory the program is using. If the total is much bigger than the heap, your problem is in boxes 2 to 5.

So is box 2, the class info, unlimited?

By default, more or less yes. It keeps growing until the machine runs out. That is a trap, not a feature.

This box grows when classes are loaded. Most applications load their classes once at startup and then stop, so it stays flat and nobody thinks about it.

It goes wrong when something creates new classes while the program is running. Some libraries do this. Some scripting tools do this. And redeploying your app onto a server that is already running does it every single time.

So set a limit with -XX:MaxMetaspaceSize. Not because you want it to fail, but because you want it to fail with a clear message that names the problem, instead of Linux silently killing your server with no clues at all.

Why does the stack give StackOverflowError instead of OutOfMemoryError?

Because two different things ran out.

Each thread's stack is a fixed size. Every method call adds a small block to it, and finishing the method removes that block. If your calls go too deep, there is no room to add another block, and you get StackOverflowError.

The heap is a shared pool that can grow up to the -Xmx limit. When it cannot fit a new object even after cleaning up, you get OutOfMemoryError.

Useful tell in real life: StackOverflowError is almost always a bug in your code, usually a method that calls itself forever. OutOfMemoryError is almost always about how much data you are holding, and for how long. Making the stack bigger to fix a StackOverflowError normally just delays the same bug.

02 Six ways it fails

  • Name the six different OutOfMemoryError messages and what each one means.
  • For which of them does making the heap bigger do nothing at all?
  • What does "GC overhead limit exceeded" mean?
  • What is the difference between a Java memory error and the number 137?
  • You gave the server 4 GB. Why did Java only use 1 GB of it?

OutOfMemoryError is not one error. It is six different errors sharing a name. The words after the colon tell you which one you have, and those words are the answer.

Most people read "OutOfMemoryError", stop reading, and give the same answer every time: make the heap bigger. For half of these, that does nothing at all.

MessageWhat it means
Java heap spaceThe heap really is full. Either you are holding things you should have let go, or the heap is too small for the work.
GC overhead limit exceededJava is spending almost all its time cleaning up and getting almost nothing back. It is stuck, not full. Nearly always a leak.
MetaspaceToo many classes loaded, and the old ones cannot be thrown away. Usually caused by redeploying onto a running server.
unable to create new native threadYou hit the limit on how many threads you are allowed. Nothing to do with the heap.
Direct buffer memoryMemory Java asked the computer for directly is not being given back.
Requested array size exceeds VM limitSomeone tried to create an array that is far too big to be sensible.

Look at rows 3 and 4. If you answer "increase -Xmx" for either of those, you have told the interviewer you have never actually fixed one. -Xmx sets the heap size. Neither of those problems is in the heap.

Two programs, two very different failures

// Number 1: Java heap space
List<byte[]> list = new ArrayList<>();
while (true) {
    list.add(new byte[1024 * 1024]);   // 1 MB each, kept forever
}

// Number 4: unable to create new native thread
while (true) {
    new Thread(() -> sleepForever()).start();   // heap barely moves
}

The first one fills the heap. The second barely touches it. Each Thread object is tiny, but each thread needs about 1 MB of workspace outside the heap, and the computer says no somewhere around a few thousand. Same error name. Completely different fix.

Work out the diagnosis yourself

Pick what you would actually see on a real server, and follow it to the answer. This is the skill being tested, not the table.

Diagnosis

Pick what you saw

Each one leads somewhere different. Two of the six are not heap problems at all.

The number 137, and why it is different

This one catches almost everybody, because most companies now run Java inside containers.

One more thing worth knowing. Modern Java looks at the container limit and, by default, only takes 25 percent of it for the heap. So people give a server 4 GB, assume Java will use it, and quietly get a 1 GB heap.

"Increase the heap size." Right for one case out of six, and even then it only buys time.

"Restart the service." A fine first move, but call it what it is. If you stop there, you have described a workaround, not a fix.

Follow-up questions

Heap is at 60 percent but the server died. Where do you look?

Outside the heap. The heap is not your problem, so stop looking at it.

First compare the heap size against the total memory the whole program is using. That gap is what you are hunting. Then check the other four places, most likely first:

  • Thread stacks. Count your threads. A few thousand threads at about 1 MB each is gigabytes.
  • Class info. Is it growing? Steady growth means classes keep being loaded and never released.
  • Direct memory. Common with networking libraries. Check whether buffers are being given back.
  • Libraries written in C. Compression, encryption and image libraries can allocate memory outside Java entirely.

This command prints a breakdown of all of them at once, if you started the program with memory tracking turned on:

jcmd <pid> VM.native_memory summary
How would you spot a thread leak?

Three ways, easiest first.

1. Watch the thread count. The simplest, and you should already be graphing it. A healthy service starts up, reaches a number, and stays there. A leak climbs slowly and never comes back down.

2. Take a thread snapshot. Run jstack <pid> and count. A leak is obvious, because you see hundreds or thousands of threads with the same name and the same list of method calls, all sitting idle. That repeated list tells you exactly which code created them.

3. Know the usual cause. Someone created a thread pool or an HTTP client inside a method instead of once at startup. So every request builds a new pool and nothing ever shuts it down. Look for pools or clients being built anywhere other than startup or configuration.

It ends as unable to create new native thread, or as the server being killed for total memory. Either way, the heap graph looks perfectly healthy the whole time, because that memory is not in the heap.

You gave the server 4 GB. Why is the heap only 1 GB?

Because Java takes 25 percent of the container limit by default, and 25 percent of 4 GB is 1 GB. Java read the limit correctly and then deliberately took a quarter of it.

That default exists because Java knows it needs room for the other four boxes: thread stacks, class info, fast code and direct memory. It is just far more cautious than most services need.

So set it yourself. For a container running nothing but Java, 65 to 75 percent is normal, leaving the rest for everything else:

-XX:MaxRAMPercentage=70.0

Use the percentage setting rather than a fixed -Xmx. Then the same build still behaves correctly when someone changes the server's memory limit later. Hard coding -Xmx3g into an image that later runs on a 2 GB server is how you get killed on startup.

What does "GC overhead limit exceeded" actually mean?

It is a safety net. Java gives up and throws this when it has spent more than 98 percent of its time cleaning up memory while getting back less than 2 percent of the heap, several times in a row.

The useful part is what that tells you. The heap is not quite full, so Java can technically still create objects. But almost everything in there is still being pointed at, so cleaning up returns nothing. Your application is doing basically no real work, and everything has gone slow.

This is a better error than plain "Java heap space", because it appears earlier and it is much stronger evidence of a real leak. A heap that is simply too small fills up and fails cleanly. A heap where you keep holding more and more produces this stuck pattern first.

You can switch the safety net off, which is almost always the wrong move. It turns a clear early warning into a slow silent death.

03 Making a leak, taking a snapshot

  • What is a memory leak in Java, in one sentence?
  • What are the starting points Java uses to decide what to keep?
  • Three ways to take a memory snapshot, and when you would use each.
  • What do you do before taking a snapshot on a live server, and why?

Start with the idea that makes everything else make sense.

A memory leak in Java means you are still holding on to something you no longer need.

Nothing is lost. The object is easy to find, and that is exactly the problem. Java looks at it, sees that your code is still pointing at it, and correctly refuses to throw it away. Java is not broken. You are holding the reference.

Java decides what to keep by starting from a few fixed starting points and following every link. Those starting points are static variables, the methods currently running, and the threads that are alive. Anything it can reach from there is kept. Anything it cannot reach is thrown away.

The most common leak in real systems

public class LeakDemo {
    // static, so it is a starting point. Everything inside is kept forever.
    private static final Map<String, byte[]> CACHE = new HashMap<>();

    public static void main(String[] args) {
        int i = 0;
        while (true) {
            CACHE.put("order-" + i, new byte[64 * 1024]);
            i++;
        }
    }
}

Someone needed a cache, used a HashMap, made it static so it was easy to reach from anywhere, and never wrote the code that removes anything. Run it with a small heap and it dies in about 30 seconds:

java -Xmx128m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./dumps LeakDemo.java

The heap climbs from 38 MB to 123 MB, then fails with OutOfMemoryError: Java heap space and leaves a 131 MB snapshot file behind.

Watch it happen

The first version keeps every object forever. The second removes the oldest one whenever it goes over its limit. Same speed, same heap size. The only difference is how long things are kept.

Taking the snapshot

A memory snapshot, usually called a heap dump, is a photo of every object in memory at one moment. There are three ways to get one.

# 1. Leave this on in production. It costs nothing until it is needed.
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps

# 2. On demand, from a running program. This is the modern tool.
jcmd <pid> GC.heap_dump /dumps/app.hprof

# 3. The older tool. Some interviewers still name it, so know it too.
jmap -dump:live,format=b,file=/dumps/app.hprof <pid>

The safety rule. While the snapshot is being taken, your whole application freezes. The bigger the heap, the longer the freeze. In the demo above, a 131 MB snapshot took less than a tenth of a second, but only because the heap was tiny. On a real server with an 8 GB heap, this can freeze everything for ten to thirty seconds.

So never take a snapshot on a server that is handling live traffic. Take that server out of the pool first, then take the snapshot. Saying this without being asked is worth more than any definition on this page.

"I would run jmap on the production server." Right tool, dangerous habit. Without taking it out of the pool first, you just caused an outage while investigating an outage.

"I would look for large objects." Too vague. Large objects are usually not the problem. What is holding them is.

Follow-up questions

What does the "live" option change, and what does it cost?

It tells Java to include only objects that are still being pointed at. To work that out, Java has to do a full cleanup first.

The benefit is a much clearer snapshot. Without it, you also capture every dead object that has not been cleaned up yet, and on a busy server that can be most of the file. Your list then fills up with rubbish that is not your problem. With it, everything in the file is genuinely being held by something, which is exactly what you are looking for.

The cost is that the full cleanup freezes the application too, on top of the freeze for the snapshot itself. So you pay twice.

Simple rule: use it when you are hunting a leak, which is nearly always.

How do you get a snapshot if the server already crashed?

You have to plan for it in advance. Afterwards there is nothing left to collect.

Write the file somewhere that outlives the server. Pointing -XX:HeapDumpPath at the container's own disk is useless, because the file disappears with the container. Point it at attached storage instead.

Give it time to finish. Writing a multi gigabyte file takes a while. If your health check fails during the write and something restarts the container, you get half a file that no tool can open.

Check there is enough disk space. The file is roughly as big as the memory in use. An 8 GB heap needs 8 GB free.

And the important case. If the server was stopped with the number 137, there is no snapshot and there never will be. Linux shut the program down instantly, so Java had no chance to write anything. Your only evidence is the memory graphs from before it died, which is why this kind of problem needs monitoring set up in advance.

How would you catch this before it crashes?

Four things, cheapest first.

Watch memory after cleanup, not raw memory. Raw heap usage is noisy, because it always looks nearly full just before a cleanup. The number that means something is how much is still in use after a full cleanup. If that climbs day after day, you have a leak. If it goes up and down around the same level, you are fine.

Watch how much time goes into cleanup. A healthy service spends well under 5 percent of its time on it. A leak pushes this up long before anything crashes, and it explains why things feel slow.

Compare two snapshots. Take one, wait a day of normal traffic, take another, and compare. If the same thing is holding more memory than yesterday, that is a leak with no argument.

Catch it in code review. Every cache needs a maximum size and an expiry time. Every queue needs a limit. Every ThreadLocal needs a matching cleanup. Those three checks catch most real leaks before they ship.

Does calling System.gc() help?

No, and being clear about why is a good sign in an interview.

First, it is only a suggestion. Java is allowed to ignore it completely, and sometimes does.

Second, and more importantly, it cannot possibly fix a leak. A leak means something is still pointing at the object. Cleanup only removes things nothing points at. You could run cleanup a thousand times and Java would look at that object every single time and correctly decide to keep it.

The one fair use is for measuring. You force a cleanup first so that what you measure afterwards is real data rather than rubbish waiting to be removed.

04 Reading the snapshot

  • Explain shallow size and retained size, with an example.
  • Why is the main view sorted by retained size instead of shallow size?
  • Name the four views in order and what each one tells you.
  • The file is 8 GB and the tool will not open it. What now?

The snapshot is a photo of every object in memory. Eclipse MAT is a free tool that opens it.

Your goal is never "which object is big". Your goal is what is holding it. Big objects are the symptom. Whatever is holding them is the bug.

Two sizes, and why they are different

These two get asked directly, and most people mix them up.

  • Shallow size is how big the object is by itself. Just its own fields.
  • Retained size is how much memory you would get back if you deleted it.

Click any object below to see both numbers.

The four views, in order

  1. Histogram. A list of every type, how many there are, and how much space they take. In our demo: byte arrays, about 1,850 of them, about 118 MB.
  2. Dominator Tree. Sorted by retained size, so it shows what is actually holding all that memory. This is the view you spend your time in. In our demo it points at the CACHE map, holding about 118 MB.
  3. Path to GC Roots. Right click the suspect and choose this, then pick the option that excludes weak and soft links. It shows the chain from a starting point down to the object. In our demo it lands on the static variable LeakDemo.CACHE.
  4. Leak Suspects. The tool's own automatic guess. A useful place to start, but do not trust it blindly.

"Retained size is the object and its fields." That is shallow size. Retained is about what dies with it.

"I look at the histogram and find the biggest type." The biggest type is nearly always byte arrays, character arrays or text. That tells you nothing. You need to know what is holding them.

Follow-up questions

Why sort by retained size instead of shallow size?

Because shallow size tells you nothing about impact. Deleting something only helps if the things it points at go away too.

Here is the clearest example. A map holding two gigabytes of orders has a shallow size of about 48 bytes. Sorted by shallow size, it does not appear anywhere near the top of the list. Sorted by retained size, it is the first row, and it is your bug.

The word "dominator" is just a precise way of saying: everything that reaches this object has to come through here first. If that is true, deleting it definitely frees everything below it. So the tree answers exactly the question you care about, which is "if I could remove one thing, how much would I actually get back".

That is also why shared objects behave the way they do in the diagram above. The Manager does not fully control Employee C, because there is a second way to reach C through the static list. So C's 120 bytes are not counted in the Manager's retained size.

Why exclude weak and soft links?

Because those kinds of links do not stop Java from cleaning something up, so a chain made of them is not a leak at all.

Java has four strengths of link. A normal link always keeps the object. A soft link is dropped when memory gets tight, which is exactly what you want for a cache. A weak link is dropped at the next cleanup no matter what. A phantom link never keeps anything at all.

So if the tool shows you a chain and every link in it is weak or soft, you have found something that will clean itself up. Chasing it wastes your afternoon. Excluding them leaves only the chains that genuinely pin things in memory.

Useful consequence: if excluding them makes the chain disappear completely, that object is not your leak. Go back to the tree and pick the next one down.

The file is 8 GB and the tool will not open it. What now?

Eclipse MAT is itself a Java program, so it needs enough memory to hold an index of your file. By default it ships with a small limit and simply gives up.

First, give the tool more memory. Edit its MemoryAnalyzer.ini file and raise -Xmx to comfortably more than the file size. For an 8 GB file, try 12 GB. This fixes it most of the time.

If your laptop cannot do that, process it on a bigger machine. MAT includes a script that builds the index and produces the reports without opening any windows. Run it on a server and copy the results back.

Better, make the file smaller. Taking the snapshot with the "live" option does a full cleanup first and only includes what is still being held, which on a busy server can shrink the file a lot.

And the option people forget. You do not always need the full file. This command prints the list of what is in memory instantly, with no file at all, and it is often enough to spot the runaway type:

jcmd <pid> GC.class_histogram
How do you tell a leak from a heap that is just too small?

Look at the shape over time, not at one moment. This is the real question behind the "ran fine for 30 days" scenario.

A heap that is too small fills up quickly and always under the same conditions, like a big overnight job or a traffic peak. After each cleanup, memory in use drops back to roughly the same level every time. It fails early and repeatably, usually within hours of the load going up.

A leak shows memory in use after cleanup creeping upwards day after day. Each cleanup gets back slightly less than the last. That baseline moving upwards is the signature, and no amount of tuning fixes it.

The test that settles it is comparing two snapshots taken 24 hours apart under normal traffic. If the same thing is holding much more memory in the second one while traffic stayed flat, it is a leak. If the top items are the same size in both, your heap is simply too small.

This matters in an interview because the fix is completely different. One is a setting. The other is code.

05 Nine leak types

  • List as many leak types as you can, with the fix for each.
  • Why does a ThreadLocal value stay alive long after the request ended?
  • What happens to a map entry if you change a field used by hashCode()?
  • Can Java leak memory at all, if it cleans up automatically?

Almost every real Java leak is one of nine shapes. Knowing the shapes lets you name the likely cause before you even open the snapshot, and that is what makes you sound experienced.

  1. A static cache with nothing ever removed. Static things live as long as the application, so everything inside stays too. Fix: a cache with a maximum size and an expiry time.
  2. Web sessions piling up. Sessions stay in memory for 30 minutes by default. Users close the browser without logging out, so under steady traffic they build up faster than they expire. Fix: shorter timeout, and never put big objects in a session.
  3. ThreadLocal never cleared on a reused thread. Explained below.
  4. Redeploying onto a running server. Each redeploy loads a fresh copy of every class. If anything from the old version is still being pointed at, the old copy cannot be thrown away. This shows up as a Metaspace error, not a heap error.
  5. A queue with no size limit. If work arrives faster than it is processed, the queue grows until memory runs out. It looks like it is coping. It is not. Fix: always set a size limit, and decide what happens when it is full.
  6. Listeners added but never removed. Whatever you registered with keeps pointing at your object long after you are done with it. Fix: remove them when you are finished.
  7. Changing a key after putting it in a map. Explained below.
  8. Files and connections never closed. Each one holds resources and usually a buffer. Fix: use try-with-resources every time.
  9. A cache keyed on something that is never the same twice. Caching by request id, session id or timestamp. It looks bounded. In practice the key never repeats, so you never get a hit and it only ever grows.

Number 3 in detail, the answer nobody gives

private static final ThreadLocal<UserContext> CONTEXT = new ThreadLocal<>();

public void handleRequest(Request req) {
    CONTEXT.set(new UserContext(req.getUser()));
    process();
    // nothing clears it. This is the bug.
}

You store a value. The request finishes. You assume the value is gone. It is not.

The thread went back into the pool. It did not stop. That thread will still be alive next week. Every thread carries its own little box of ThreadLocal values, and while the thread is alive, that box is alive, and so is whatever you put in it.

Now multiply by 200 threads in a web server pool, each holding a user object, which holds their orders, which hold more things again.

try {
    CONTEXT.set(new UserContext(req.getUser()));
    process();
} finally {
    CONTEXT.remove();     // this one line is the whole fix
}

Measured, not guessed. A test program with 200 threads, holding 1 MB each, lets every task finish, forces a full cleanup, then measures what is left. 403 MB is still held without the cleanup line. 3 MB with it. Same tasks, same threads, same work. One line in a finally block.

Number 7 in detail, the entry you cannot see

Map<Customer, Order> orders = new HashMap<>();
Customer c = new Customer("anupam@x.com");
orders.put(c, order);

c.setEmail("new@x.com");     // hashCode() uses the email, and it just changed

A map decides where to file an entry using the key's hashCode(). Here the entry was filed using the old email. Now lookups use the new email, so they look in the wrong place.

So orders.get(c) returns nothing, and orders.remove(c) does nothing. Your code can no longer see the entry, but the map is still holding it, so Java will never clean it up. You cannot find it and you cannot delete it. It is stuck there forever. Fix: never use a field in hashCode() that can change. Best of all, use keys that cannot change at all.

"Java cleans up automatically, so leaks are impossible." Java only removes things that nothing is pointing at. A leak is something you are still pointing at but no longer need.

"Call System.gc()." It is only a suggestion, and it cannot remove something you are still holding.

Follow-up questions

Which of these is hardest to spot?

Two stand out, for opposite reasons.

The redeploy one, because it does not appear where you are looking. Your heap graph stays flat and healthy while the class info area grows, and most dashboards do not show that area at all. It also only happens after several redeploys, so it never shows up in testing where the app starts once. You catch it by graphing that area and watching whether it steps up with every deployment.

The changed key one, because your own code cannot see the entry. You cannot write anything to count it, because looking it up and removing it both fail. The only way to see it is in a snapshot, where the map is far bigger than any code path can explain. The clue is a map whose size keeps growing while the number of real business objects does not.

The static cache and web session ones are easy by comparison. They sit right at the top of the tree.

How do you prevent these instead of fixing them?

Five rules that cover most of the nine, and all of them are cheap to check in review.

1. Every cache has a maximum size and an expiry time. No exceptions, and no hand built map caches. Use a proper cache library so the limit is visible in the code.

2. Every queue has a size limit, and a decision about what happens when it fills up. Wait, drop, or reject. A queue with no limit is just an outage you have not had yet.

3. Every ThreadLocal that is set is cleared in a finally block. This one is mechanical and easy to search for.

4. Every file and connection is opened with try-with-resources. Tools can check this automatically, so it never needs a human to remember.

5. Keys in maps and sets cannot change. Using simple value objects with final fields makes this the default rather than something to remember.

Then add the four graphs that catch whatever slips through: memory in use after cleanup, class info size, thread count, and time spent on cleanup.

Why does the ThreadLocal box not clean itself up?

It half tries, and the half that fails is the half that matters.

Inside that box, the labels are held weakly but the values are held normally. The idea was that once your ThreadLocal object is no longer used anywhere, its label disappears and the entry can be tidied away later.

The problem is how everyone actually writes them: private static final ThreadLocal. Static means it never goes away. So the label is always in use, the entry never looks unused, and the value sits there for the entire life of the thread.

So the automatic tidying protects against a situation that almost never happens in real code, and does nothing about the situation that happens every time. That is why calling remove() is not optional. It is the only thing that actually clears the value.

06 Answering it in the interview

  • Give the five steps of a production incident answer, in order.
  • Why is "what built up?" a better first question than "what broke?"
  • Which step do most people skip, and what does skipping it cost?
  • Give the full 90 second answer to the 30 day question, out loud.

You can know everything above and still lose the round by telling the story badly. This chapter is about structure.

The one idea that is the whole answer

"Your Spring Boot application ran perfectly for 30 days. Today it crashed with OutOfMemoryError. You did not change a single line of code. What happened?"

Most people start by asking "what broke?" Nothing broke. Today's code is the same as it was 30 days ago.

The right question is "what built up?"

That is the answer. Everything after it is just steps: take a snapshot, open it, find what is holding memory, find the static map that never removes anything. The interviewer is listening for whether you work it out or whether you are repeating a story you memorised.

The five steps

  1. How you found out. What alerted you, and how quickly. "A memory alert at 90 percent, and the restart woke the on call engineer."
  2. Get it running again. Raise the memory, restart, roll back. Say clearly that this buys time and fixes nothing. Skip this step and you sound like you have only read about it. Stop at this step and you sound junior.
  3. Work out the cause. The evidence trail. Take a server out of the pool, take a snapshot, open it, look at what is in memory, then at what is holding it, then at where the link starts.
  4. Fix it properly. Not "we gave it more memory". Something like "we replaced the static map with a proper cache with a maximum size and a 10 minute expiry".
  5. Make sure it cannot come back quietly. "We added a memory alert at 75 percent, and unlimited caches are now something we check in code review."

Why step 5 matters most. Almost everyone stops after step 4. Step 4 says: I solved a problem. Step 5 says: I made sure this kind of problem cannot happen again without us noticing. The second one sounds like ownership. The first sounds like firefighting.

What a good answer sounds like

"Nothing changed, so nothing broke. Something built up. I would start there.

First, get it running again. Raise the memory and restart so users are unblocked. That buys time, it does not fix anything.

Then work out the cause. We would already have the setting that writes a snapshot when memory runs out, so there should be a file. If not, I would take one, but from a server taken out of the pool first, because taking a snapshot freezes the whole application and the bigger the heap the longer that takes.

Then open it in MAT. See what is in memory, see what is holding it, then follow the chain back to find what is pointing at it.

In the case I have seen, it was two things. Web sessions that were never cleared, and a static map used as a cache that never removed anything.

The fix was a shorter session timeout and replacing that map with a proper cache with a size limit and an expiry. To stop it coming back, we added a memory alert at 75 percent so we would see it building up, and we started checking for unlimited caches in code review."

That is about ninety seconds. It has the reframe, getting the service back, the steps you took, a real cause, and how you stopped it recurring.

Going straight to the tool. Opening with "I would take a heap dump" skips the thinking, which is the part being tested.

Not mentioning getting the service back. Sounds like you have never been on call.

A vague cause. "There was a memory leak" is not a cause. Name the thing and what was holding it.

Stopping after the fix. Costs you the senior signal.

Follow-up questions

What if the snapshot shows nothing unusual?

Then believe the snapshot and change your theory. It is probably not a heap problem.

First check whether there was a Java error at all. If the server stopped with the number 137, Linux shut it down for total memory and Java never got to raise anything, so no snapshot would exist in the first place. That immediately points you outside the heap.

Then compare the heap size against the total memory the whole program is using. If the total is much bigger, the memory is in one of the other four places: thread stacks (count your threads), class info (does it grow with each deploy), direct memory, or a library written in C.

Also consider that it might not be memory at all. A service that looks frozen can be out of threads or out of database connections while memory stays perfectly flat. In that case you want a thread snapshot, not a memory snapshot.

How would you prove the fix actually worked?

Three pieces of evidence. Giving all three is what makes the answer sound confident rather than hopeful.

1. The shape of the memory graph changes. Memory in use after a full cleanup should now be flat across days instead of climbing. That is the specific number to quote. Raw memory usage is too noisy to prove anything.

2. Two snapshots, 24 hours apart. Take one after the fix goes out and another a day later under similar traffic, then compare how much the suspect is holding. If it is the same, the leak is closed.

3. Time. The original problem took 30 days to appear, so a green dashboard on day one proves very little. Say that out loud. It shows you understand your own failure. Keep the alert in place through at least one full cycle of however long it took the first time.

What if you cannot reproduce it in the test environment?

Expect not to. That is normal for this kind of bug, not a failure on your part. It needed 30 days of real traffic and real user behaviour to show up.

So stop trying to force a crash and compare production against itself over time instead. Two snapshots a day apart from the live system tell you more than any amount of fake load, because the growth itself is the evidence.

If you do want to reproduce it, squeeze the time rather than copying the traffic. Run the test environment with a deliberately tiny heap, so the same build up hits the ceiling in hours instead of weeks. Something that takes 30 days with a 4 GB heap can take under a day with a 256 MB one.

And say the honest thing, because interviewers respect it. Some problems are diagnosed in production, using snapshots and graphs, not in a test environment. Pretending otherwise is how people waste a week.

G Word list

Every term on this page that you might not already know, in one place.

heap
The area where all your objects live. Shared by the whole program. This is what -Xmx sets the size of.
stack
A small private workspace for one thread. Holds the chain of method calls it is currently inside, and any plain numbers declared in them.
Metaspace
The area holding a description of your classes: their shape and their method code. Not your data. It replaced an older area called PermGen in Java 8.
garbage collection
Java automatically removing objects that nothing points at any more. Often shortened to GC.
heap dump
A photo of every object in memory at one moment, saved to a file so you can inspect it later.
thread dump
A photo of every thread and what each one is currently doing. Useful for freezes and slowness, not for memory.
Eclipse MAT
A free tool that opens a heap dump and shows you what is using memory and what is holding it.
shallow size
How big one object is on its own, counting only its own fields.
retained size
How much memory you would get back in total if you deleted that object.
GC roots
The fixed starting points Java traces from when deciding what to keep: static variables, running methods, and live threads.
exit code 137
The number left behind when Linux force stops a program for using too much memory. Java gets no warning, so there is no error message and no heap dump.
ThreadLocal
A way to give each thread its own private copy of a value. Safe on its own, but a common cause of leaks when threads are reused and the value is never cleared.
jcmd / jstack / jmap
Command line tools that ship with Java. jcmd is the modern all rounder, jstack takes thread dumps, jmap is the older heap dump tool.
pid
Process id. The number the operating system uses to identify your running program. You pass it to the tools above.
