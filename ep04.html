The collection questions, answered by looking inside

Everything on this page was produced by running code: reflecting into a real HashMap to watch it resize and change shape, timing lists against each other, and writing to a shared map from eight threads to see what actually breaks. The surprising results are the ones worth remembering.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 Inside a HashMap

  • What happens, step by step, when you call put?
  • What is the default capacity and load factor, and when does it resize?
  • What happens when two keys land in the same bucket?
  • When does a bucket become a tree? Both conditions.
  • Why is resizing expensive?

A HashMap is an array of buckets. Each bucket holds entries whose keys landed there. That is the whole idea, and everything else is detail about what happens when the array fills up or too many keys land in one place.

What put actually does

  1. Call hashCode() on the key.
  2. Mix that number a little, so that keys whose hash codes differ only in the high bits still land in different buckets.
  3. Turn it into an index into the array.
  4. If that bucket is empty, put the entry there.
  5. If it is not empty, walk what is already there. If a key equals() yours, replace its value. Otherwise add yours to the end.
  6. If the map is now too full, double the array and move everything.

Measured: when does it resize?

Adding entries one at a time to a real HashMap and reading its internal array after each one:

size   1 -> capacity became  16  (resizes when size passes 12)
size  13 -> capacity became  32  (resizes when size passes 24)
size  25 -> capacity became  64  (resizes when size passes 48)
size  49 -> capacity became 128  (resizes when size passes 96)
size  97 -> capacity became 256  (resizes when size passes 192)

So: capacity starts at 16, and doubles once size passes capacity times 0.75. That 0.75 is the load factor. Those are the two numbers the question is asking for.

Measured: do keys spread out evenly?

Not as evenly as people assume. A thousand keys in a real map:

1000 keys in a table of 2048 buckets
  buckets used   : 602
  buckets empty  : 1446
  longest chain  : 4 entries

Only 602 buckets held anything, and the busiest held 4 entries. That is normal. Hashing spreads keys out well enough, not perfectly, and a HashMap is designed to cope with some clustering rather than to prevent it.

Measured: when does a bucket become a tree?

This is the part almost everyone states incorrectly. The usual answer is "at 8 entries in a bucket". Here is what actually happens, using keys deliberately built so that every single one collides:

after  8 puts: table= 16  chain= 8  bucket type = Node
after  9 puts: table= 32  chain= 9  bucket type = Node      <-- resized instead
after 10 puts: table= 64  chain=10  bucket type = Node      <-- resized again
after 11 puts: table= 64  chain= 1  bucket type = TreeNode   <-- now it treeified

The chain reached ten entries and still had not become a tree. Instead the map resized, twice.

There are two conditions, not one. A bucket becomes a tree only when it holds at least 8 entries and the array is at least 64 long. Below 64, HashMap resizes instead, because with a small array the collisions are more likely caused by a cramped array than by genuinely bad keys, and doubling it is the cheaper fix.

Why turn a chain into a tree at all? A chain has to be walked one entry at a time, so a bucket with a thousand entries takes a thousand steps. A tree can be searched far more efficiently, so even a badly clustered bucket stays fast. It is a defence against bad hashing, not something you should ever be relying on.

"A bucket becomes a tree at 8 entries." Only if the array is also at least 64 long. Otherwise the map resizes instead, which the measurement above shows happening twice while the chain sat at 9 and 10 entries.

"HashMap is O(1)." On average, yes. In the worst case, where every key collides, it used to become O(n). Since the tree change it is O(log n) in that worst case, which is the actual reason trees were added.

Follow-up questions

Why is resizing expensive?

Because it is not just allocating a bigger array. Every existing entry has to be looked at again and placed into the new array, since the bucket index depends on the array length, and the length just changed.

So a resize is proportional to how many entries you already have. Growing a map to a million entries means resizing repeatedly along the way, and each resize moves everything currently in there.

The practical consequence is worth stating: if you know roughly how many entries you will have, say so when you create the map. Passing an expected size lets it allocate a big enough array once instead of growing into it.

One catch worth knowing. The number you pass is the capacity, not the number of entries it can hold, so it still resizes once you pass capacity times 0.75. If you want room for 1000 entries without a resize, you need a capacity above 1333, not 1000.

Why does HashMap mix the hash code instead of using it directly?

Because of how the bucket index is worked out. The array length is always a power of two, which lets the map find the index with a fast bitwise operation instead of a division. That operation keeps only the lowest bits of the hash code.

So with an array of 16, only the bottom 4 bits matter. Any two keys whose hash codes differ only in higher bits would land in the same bucket, even though their hash codes are completely different numbers.

That is not hypothetical. Plenty of real hashCode implementations produce values that vary mostly in the upper bits, for example anything derived from a memory address or a large identifier.

So before using the hash code, HashMap folds the high bits down into the low ones. It is one cheap operation that mixes the whole value into the part that actually gets used, and it turns a class of pathological cases back into ordinary ones.

Why is the capacity always a power of two?

For speed, and it explains the previous answer.

To turn a hash code into a bucket index you need a number in range. The obvious way is a remainder operation, which is relatively slow. When the length is a power of two, you can get the same result with a single bitwise operation that simply keeps the lowest bits, which is far faster and happens on every single get and put.

It also makes resizing cheaper. When the array doubles, an entry either stays at its current index or moves to that index plus the old length. Nothing else is possible. That means the map can split each bucket into two without recomputing anything from scratch.

The cost is the one from the previous answer: keeping only the lowest bits throws away the high bits entirely, which is why the hash has to be mixed first. The two design decisions exist together.

02 equals and hashCode

  • What is the contract between equals and hashCode?
  • What breaks if you override equals but not hashCode?
  • What happens if you change a key after putting it in a map?
  • Why must map keys be immutable?

Everything in the previous chapter depends on two methods being consistent with each other. The rules are short.

1. If two objects are equal, they must have the same hash code.
2. If two objects have the same hash code, they do not have to be equal.
3. The hash code must not change while the object is in a map.

Rule 1 is the one people break by overriding equals and forgetting hashCode. Two objects you consider equal then get different hash codes, so they land in different buckets, so the map never even compares them. You put something in and cannot find it again.

Rule 3 is the one people break without realising, and it is worth seeing rather than being told.

Measured: changing a key after putting it in

A Customer whose hashCode() is based on its email. Put it in a map, then change the email:

before changing the email:
  get(c)      = order-1
  size        = 1

after changing the email:
  get(c)      = null        <-- gone
  containsKey = false
  remove(c)   = null        <-- cannot delete it either
  size        = 1           <-- still there, taking memory
  iterating   = Customer(new@x.com) -> order-1   <-- visible, but unreachable

Read those five lines carefully, because together they describe something genuinely nasty.

  • You cannot find it. get returns nothing.
  • You cannot delete it. remove does nothing.
  • It still counts. The size is 1.
  • It is still there. Walking the map shows it.

The entry was filed under the old hash. Lookups now compute the new hash and search a different bucket. The map is still holding the entry, so it is never cleaned up, and your code has no way to reach it. That is a permanent leak, and it is the leak archetype from Episode 1 that nobody can find by searching.

The same thing happens with a Set. Adding an object and then changing it means the set no longer contains the very object you put in:

contains(the very same object) = false
size                           = 1

The fix

Use keys that cannot change. In modern Java a record is the easiest way, because its fields are final and it generates a correct equals and hashCode for you.

record CustomerId(String email) { }     // cannot be changed after creation

If you must use a mutable class as a key, base its identity on something that genuinely never changes, such as a database id assigned at creation, and never on a field a setter can touch.

"I only need equals, hashCode is optional." Only if the object never goes into a HashMap or HashSet, and you cannot guarantee that about a class other people will use. Override both or neither.

"Returning a constant from hashCode is valid." It is technically legal, because equal objects do get the same hash code. It is also catastrophic: every key lands in one bucket, so the map degrades into a single long chain. That is exactly the setup used to force the tree behaviour in the previous chapter.

Follow-up questions

What exactly breaks if you override equals but not hashCode?

Anything hash based stops working, while everything else looks fine, which is what makes it hard to spot.

Without overriding hashCode, you inherit the default, which is derived from the object's identity rather than its contents. So two objects your equals considers equal get two unrelated hash codes.

The map computes a bucket from the hash code. Two equal objects land in different buckets. The map never compares them because it only compares within a bucket. So you put an entry in with one object and look it up with an equal one, and it is not found.

The reason this survives testing is that plain comparisons still work perfectly. a.equals(b) is true, list.contains(a) is true, because a list compares every element directly. Only hash based structures break, and only when the lookup object is a different instance from the one that was stored.

Also worth naming: HashSet is backed by a HashMap, so it has exactly the same problem, and so does using your object as a key anywhere in a cache.

Can two different objects have the same hash code on purpose?

Yes, and it is unavoidable rather than a flaw.

A hash code is a 32 bit number, so there are about four billion possible values. There are infinitely many possible strings. So different objects sharing a hash code is guaranteed by counting alone, no matter how good the hashing is.

That is exactly why the map does not trust the hash code by itself. It uses the hash code to pick a bucket, and then within that bucket it compares keys with equals to find the right one. The hash code narrows the search, equals decides the answer.

This is also why rule 2 exists: equal hash codes do not imply equal objects. Only the other direction is required.

The practical consequence for writing a hashCode: you are not trying to guarantee uniqueness, which is impossible. You are trying to spread values out so that unrelated keys rarely land together. Include the fields that actually distinguish your objects, and leave out ones that are usually the same for everything.

03 ConcurrentHashMap

  • What actually goes wrong if several threads write to a plain HashMap?
  • How did ConcurrentHashMap work in Java 7, and what changed in Java 8?
  • Why does it not allow null keys or values?
  • Why is it faster than wrapping a HashMap in a lock?

Everyone can say a HashMap is not thread safe. The interesting question is what that actually means, and the answer is worse than most people expect.

Measured: eight threads writing to one map

Eight threads, twenty thousand distinct keys each. No key is written twice, so a correct map ends with exactly 160,000 entries. Run five times:

HashMap (no protection)
  attempt 1: DID NOT FINISH - threads still spinning after 10s
  attempt 2: 105,688 entries  LOST 54,312
  attempt 3: DID NOT FINISH - threads still spinning after 10s
  attempt 4: 160,000 entries  correct
  attempt 5: 151,665 entries  LOST 8,335

Three different outcomes from the same code. It lost a third of the data once, hung completely twice, and worked perfectly once.

Attempt 4 is the most dangerous line in that output. It was correct. That is why this bug reaches production: it passes review, it passes tests, it works on your machine, and then it loses data or hangs under real load. A bug that always failed would have been caught.

The hang is worth understanding. Two threads resizing the map at the same time can leave the internal structure pointing at itself in a loop. A later lookup then walks that loop forever, at full processor speed, and never returns. That is a thread stuck in RUNNABLE burning a whole core, which is exactly the shape of the problem from Episode 2.

The same test with the safe options

Collections.synchronizedMap
  attempt 1 to 5: 160,000 entries  correct   (52, 77, 14, 15, 38 ms)

ConcurrentHashMap
  attempt 1 to 5: 160,000 entries  correct   (117, 25, 31, 22, 12 ms)

Both are correct every time. On this small test their speeds overlap, and that is worth being honest about rather than claiming a dramatic win: the difference between them shows up under sustained contention with many readers, not in a short burst.

How it works, then and now

This comes up as a direct question, so know both.

Java 7: segments. The map was divided into a fixed number of independent sections, each with its own lock. Two threads writing to different sections did not block each other. The limit was the number of sections, so with 16 of them only 16 threads could ever write at once, no matter how big the map was.

Java 8 onwards: per bucket. The segments are gone. Instead, adding to an empty bucket uses a single hardware level operation that either succeeds or fails without any lock at all. If the bucket already has entries, only that one bucket is locked while the entry is added.

The improvement is that the amount of possible parallel work now grows with the map. A bigger map has more buckets, so more threads can write at once, rather than being capped at a fixed number of sections.

Reads take no lock at all, in both versions.

"HashMap is not thread safe, so you might see stale data." Far too gentle. You can lose tens of thousands of entries, or hang the program with a thread spinning at full speed forever.

"ConcurrentHashMap locks the map on write." It locks one bucket, and only when that bucket is already occupied. Adding to an empty bucket takes no lock at all.

Follow-up questions

Why does ConcurrentHashMap not allow null keys or values?

Because with several threads, a null result would be genuinely ambiguous, and there would be no safe way to resolve it.

With a plain HashMap, get returning null could mean the key is absent, or the key is present with a null value stored against it. You resolve that by calling containsKey.

In a concurrent map that check does not help. Between your get returning null and your containsKey running, another thread may have added or removed that key. So the answer you get back describes a moment that has already passed, and there is no way to ask both questions as one atomic step.

Rather than provide a method whose result cannot be trusted, the designers removed the ambiguity: null is not allowed, so null always means absent.

Worth adding, because it demonstrates you understand rather than memorised: this is the difference between a design flaw and a deliberate trade. Allowing null would not have been unsafe, it would have been unanswerable, and an API that cannot answer its own question is worse than one that forbids the input.

What does "weakly consistent" mean for its iteration?

It means walking the map never throws, but it also does not promise you a single frozen moment in time.

A plain HashMap gives you the opposite deal. Change it while walking and it throws immediately, so you know your walk was invalid rather than getting quietly wrong results.

ConcurrentHashMap cannot do that, because in a concurrent map other threads changing things is normal rather than a bug. So its iteration is defined loosely on purpose: you will see every entry that was present for the whole walk, you will never see the same entry twice, and you may see entries added during the walk, or miss ones removed during it.

What it guarantees firmly is that it never throws and never shows you corrupted data.

The practical consequence: size() on a concurrent map is an estimate that may be stale the instant it returns. If you need a count you can act on, either you do not really need it to be exact, or a concurrent map is the wrong structure for that part of the problem.

Why is it faster than wrapping a HashMap in a lock?

Because of how much gets blocked, and it matters most for reads.

Wrapping a HashMap means every operation takes the same single lock. Two threads reading different keys still queue behind each other, even though neither is changing anything. With many readers, that one lock becomes the bottleneck and adding processors does not help.

ConcurrentHashMap takes no lock at all for reads. Any number of threads can read at the same time, including while another thread is writing somewhere else. Writes lock only the single bucket involved, so two threads writing different keys usually do not interact.

The honest caveat, visible in the measurement above: on a short burst of pure writes the two came out similar, because the wrapped version's lock was held very briefly each time and there was little real contention. The gap opens up as you add readers and sustain the load.

So the accurate answer is not "it is faster", it is "it scales, whereas a single lock does not". Under one thread they are much the same; the difference is what happens when you add the eighth.

The trap in synchronizedMap. Each individual call is safe. A sequence of calls is not. Checking whether a key is absent and then adding it is two operations, and another thread can act in between, so you can still lose an update. ConcurrentHashMap gives you single operations that do both at once, which is the real reason to prefer it.

"Hashtable and ConcurrentHashMap are both thread safe, so they are equivalent." Hashtable locks the entire map on every single call including reads. ConcurrentHashMap locks nothing for reads and one bucket for writes. Under load that is the difference between scaling and not.

"synchronizedMap makes my code thread safe." It makes each call safe. Your read then write sequence is still a race, and so is iterating over it, which needs you to hold the lock manually for the whole walk.

Follow-up questions

Why is Hashtable obsolete rather than just old?

Because everything it offers is now done better by something else, and it carries costs nothing else does.

It locks the whole map on every operation, including reads, so it cannot scale with more threads. ConcurrentHashMap does the same job without that limitation.

It also predates the collections framework, so it fits awkwardly with everything else. Its original interface used different method names, and it exposes an older style of iteration alongside the modern one.

The reason to still know it is that interviewers use it to check whether you understand why one design is better, rather than just which name is newer. The answer they want is the locking granularity: whole map versus one bucket, and reads locking versus reads not locking.

One historical note that lands well: Hashtable rejecting nulls was not a considered design decision the way it was for ConcurrentHashMap. It simply predates the discussion. The two make the same choice for completely different reasons.

Is there any case where you would still choose synchronizedMap?

A few narrow ones, and being able to name them shows you are thinking rather than reciting "always use ConcurrentHashMap".

You need null keys or values. ConcurrentHashMap forbids both. If you are wrapping an existing structure that legitimately stores nulls, changing that may be a bigger job than accepting the wrapper.

You need to wrap something that is not a HashMap. The wrapper works on any Map, including a LinkedHashMap that maintains order or a TreeMap that keeps keys sorted. There is no concurrent equivalent of a LinkedHashMap.

You need a genuinely consistent view across several operations. Because there is one lock, you can hold it yourself and do a multi step sequence knowing nothing else can interleave. With a concurrent map that guarantee does not exist, by design.

Contention is genuinely low. A map touched rarely by a couple of threads gains nothing measurable from the more sophisticated option, and the wrapper is one line.

Outside those, ConcurrentHashMap is the default and the burden of proof is on choosing something else.

05 Changing a collection while walking it

  • What is fail-fast, and what is fail-safe?
  • How does an ArrayList detect that it changed?
  • Is fail-fast guaranteed?
  • What is the correct way to remove items while walking?

Change a collection while you are in the middle of walking it and one of two things happens, depending on the collection.

  • Fail-fast collections notice and throw ConcurrentModificationException straight away. ArrayList, HashMap, HashSet.
  • Fail-safe collections carry on without complaining. CopyOnWriteArrayList, ConcurrentHashMap.

How the detection works

Every fail-fast collection keeps a counter of how many times its structure has changed. When you start walking it, the iterator records the current value. Before each step it checks the counter still matches. If something added or removed an element behind its back, the numbers differ and it throws.

Note that the name is misleading. It has nothing specifically to do with threads. The most common way to trigger it is a single thread modifying a list inside its own loop.

Measured, including the case that surprises people

ArrayList, remove 'b' of 5 : ConcurrentModificationException   <-- as expected
ArrayList, remove 'b' of 3 : no exception, but only saw [a, b]   <-- silently skipped 'c'

The same operation, on the same type of list, with a different number of elements. The first throws. The second does not, and quietly gives you the wrong answer instead.

Why the second one does not throw. Removing the second to last element leaves the list one shorter, and the iterator's position now equals the new size. So it concludes it has finished, stops, and never runs the check that would have thrown. You get no error and a walk that silently skipped the last element.

This is why the detection is documented as best effort: fail-fast is a debugging aid, not a guarantee. Never write code that relies on getting the exception.

The two correct ways to remove while walking

// 1. use the iterator's own remove
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) it.remove();
}

// 2. or say what you mean, in one call
list.removeIf(s -> s.equals("b"));

The iterator's own remove works because it updates the counter it is checking against, so the two stay in step. removeIf is usually clearer and is the better choice when the condition is simple.

What the fail-safe collections did instead

CopyOnWriteArrayList : no exception, walked [a, b, c], list is now [a, c]
ConcurrentHashMap    : no exception, saw 3 keys, map is now {}

The list walked a snapshot taken when iteration began, so it saw all three original elements even though one was removed during the walk. The map walked live data and let the removals happen as it went.

Both are correct behaviour for their design, and neither gives you the frozen consistent view a plain ArrayList would have given you if nothing had changed.

"ConcurrentModificationException means two threads touched it." Usually it is one thread modifying a collection inside its own loop over that collection.

"If there is no exception, my loop was fine." The measurement above shows a loop that threw nothing and silently skipped an element.

Follow-up questions

What does CopyOnWriteArrayList actually copy, and when?

It copies the entire underlying array on every single modification. Add one element to a list of ten thousand and it allocates a fresh array of ten thousand and one, copies everything across, and swaps it in.

That sounds obviously wasteful, and for most uses it is. What it buys is that readers never need a lock and never see a half changed list, because the array they are walking is never modified. It is replaced, and their walk continues over the old one.

That is also why its iteration cannot throw and why its remove during iteration does nothing to what you are walking: you are holding a snapshot that is now out of date, by design.

So it fits one specific shape: read very often, write very rarely. The classic example is a list of registered listeners, set up at startup and then read on every event. If writes are anything but rare, the copying will dominate and you want a different structure.

How do you safely walk a map that other threads are changing?

Depends which map, and the answer differs sharply.

With ConcurrentHashMap, just walk it. Its iteration is built for this and will not throw. Accept that what you see reflects a period of time rather than one instant: entries added during the walk may or may not appear.

With a wrapped synchronized map, you must hold the lock yourself for the entire walk. The wrapper makes each individual call safe but does nothing for iteration, so without holding it you will get an exception. That means blocking every other thread for as long as your walk takes, which is often unacceptable.

With a plain HashMap shared between threads, there is no safe answer. Fix the sharing rather than the iteration.

The pattern worth mentioning if you need a genuinely consistent snapshot: copy first, then walk the copy. Take the lock briefly to make the copy, release it, and iterate at your leisure. You get a consistent view and hold the lock for the shortest possible time.

06 ArrayList versus LinkedList

  • How is each one laid out in memory?
  • Which is better for inserting, and why is the usual answer wrong?
  • When would you genuinely choose LinkedList?
  • What is CopyOnWriteArrayList for?

The textbook answer is that ArrayList is better for reading and LinkedList is better for inserting. The second half of that is mostly wrong, and it is easy to show.

How they are laid out

ArrayList is one array. The elements sit next to each other in memory. Getting element 5000 is arithmetic: jump straight there. Inserting in the middle means shifting everything after it along by one.

LinkedList is a chain of separate objects, each holding a value and pointers to its neighbours. They can be anywhere in memory. Getting element 5000 means starting at one end and following 5000 pointers. Inserting means changing two pointers, once you are already there.

That last clause is where the textbook answer falls apart.

Measured

100,000 elements, 20,000 operations, best of seven rounds after warmup:

OperationArrayListLinkedListVerdict
get by random index91 us628,300 usArrayList 6852x faster
add at the end193 us70 usLinkedList 3x faster
add at the front143,017 us76 usLinkedList 1877x faster
insert in the middle71,721 us1,404,909 usArrayList 20x faster
walk the whole list68 us349 usArrayList 5x faster
remove while iterating164,400 us404 usLinkedList 406x faster

Look at rows three and four together, because they look contradictory and are not.

LinkedList is 1877 times faster at inserting at the front, and 20 times slower at inserting in the middle. The insert itself is cheap either way. The difference is entirely the cost of getting to the position. The front is free. The middle means following 50,000 pointers, every single time.

So the correct version of the textbook claim is: LinkedList is faster at inserting only when you already have the position. That means at the ends, or when you are holding an iterator that is already there. That is exactly why row six is so lopsided, since removing through an iterator needs no searching at all.

The other quiet result is row five. Walking the whole list is 5 times faster on ArrayList even though both are simply visiting every element in order. Its elements sit together in memory, so the processor fetches them in efficient blocks. LinkedList elements are scattered, so each step is a jump to somewhere unrelated.

The honest practical conclusion

Use ArrayList by default. Reach for LinkedList only when you are genuinely working at the ends of the list, and at that point what you usually want is a Deque, which says what you mean and is normally implemented with an array anyway.

CopyOnWriteArrayList

The third option, for one specific situation: read constantly, write almost never. Every write copies the whole array, which is expensive, but reads take no lock at all and can happen while a write is in progress. Listener lists set up at startup and read on every event are the standard example.

"LinkedList is better for inserting and removing." Only at a position you already hold. Inserting in the middle measured 20 times slower, because it had to walk there first.

"LinkedList uses less memory because it grows exactly as needed." The opposite. Every element is a separate object holding two extra pointers, so it uses substantially more memory per element than an array, even accounting for the array's spare capacity.

Follow-up questions

Why is walking a LinkedList slower when both visit every element once?

Because of how memory is physically read, and this is a good answer because it goes past the counting of operations.

Memory is not fetched one value at a time. The processor pulls in a block of neighbouring bytes at once, on the assumption that if you wanted one you will probably want the ones next to it.

An ArrayList rewards that assumption exactly. Its elements sit next to each other, so fetching one brings several neighbours along for free, and the next few steps need no fetch at all.

A LinkedList defeats it. Each element is a separate object allocated at a different time, so they end up scattered. Every step is a jump to an unrelated place, and the block fetched around it is mostly useless.

So both do the same number of steps, and one does far more waiting. In the measurement that was a factor of five, and it is why the theoretical complexity of an operation is a starting point rather than an answer.

How does ArrayList grow, and what does that cost?

When the array is full, it allocates a larger one, copies everything across and continues. The new size is roughly one and a half times the old one, not double as people often assume.

Growing by a proportion rather than a fixed amount is what keeps adding at the end cheap on average. Each individual growth costs a full copy, but they happen exponentially less often as the list gets bigger, so the cost spread across all additions stays small.

The measurement shows this: adding at the end came out at 193 microseconds for 20,000 additions including the growth steps, against LinkedList's 70. Slower, but in the same range, and both are fast enough that it rarely decides anything.

The practical advice is the same as for maps: if you know roughly how big it will be, say so when you create it. That skips the growth steps entirely and, for a large list, also avoids briefly holding both the old and new arrays at once, which matters if the list is big enough to strain the heap.

Two different keys landing in the same bucket. Normal and expected, not an error.
treeify
Turning a long chain into a tree so it can be searched more efficiently. Needs at least 8 entries in the bucket and a capacity of at least 64.
resize
Doubling the array and placing every existing entry again, because the bucket index depends on the array length.
hash code
A number derived from an object's contents, used to choose a bucket. Equal objects must produce equal hash codes.
fail-fast
A collection that throws immediately if it changes while you are walking it. A debugging aid, and explicitly not guaranteed.
fail-safe
A collection that lets you carry on walking while it changes, without throwing. Usually because you are walking a snapshot or a structure built for it.
ConcurrentModificationException
The error thrown by a fail-fast collection. Despite the name, it is usually caused by one thread, not two.
weakly consistent
Iteration that never throws but does not promise a single frozen moment: you may or may not see changes made during the walk.
snapshot
A frozen copy taken at one moment. CopyOnWriteArrayList walks a snapshot, which is why changes during the walk do not affect it.
contention
Several threads wanting the same lock at the same time. The thing ConcurrentHashMap is designed to reduce.
Deque
A collection designed for adding and removing at both ends. Usually what people actually want when they reach for a LinkedList.
