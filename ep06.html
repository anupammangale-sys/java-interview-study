One million threads in 656 milliseconds

Virtual threads make blocking cheap again, which undoes most of the reason asynchronous code existed. Everything here was measured on Java 24, including one result that contradicts the advice almost every article still gives.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 Two kinds of thread

  • What is the difference between a platform thread and a virtual thread?
  • Why can you have a million of one and not the other?
  • What problem were virtual threads actually built to solve?
  • When do virtual threads give you nothing?

A platform thread is a thin wrapper around a thread belonging to the operating system. Creating one asks the operating system for a real thread, which comes with about a megabyte of memory reserved outside the heap, and the operating system decides when it runs.

A virtual thread is an ordinary Java object on the heap. Java schedules it itself, onto a small set of real threads. The operating system never knows it exists.

Measured: how many can exist

Threads that only wait, so this is the cost of existing rather than the cost of working. Each kind run in its own program.

Measured: the thing that actually matters

Counting threads is not the point. Here are ten thousand tasks, each waiting 100 ms for something slow, which is what a service calling other services does all day.

The third column is the arithmetic you can do in your head, and the measurement matches it almost exactly. With a fixed pool, wall time is tasks divided by threads, multiplied by how long each one waits. You are rationing threads.

Virtual threads remove the divisor. Ten thousand tasks each waiting 100 ms takes about 100 ms, because all ten thousand wait at the same time.

What they were built for

Nearly every backend service spends its time waiting: for a database, for another service, for a queue. The thread doing the waiting is not using the processor, it is just occupying a scarce and expensive resource.

The old answer was to stop blocking, and write callbacks or reactive pipelines instead. That works, and it makes the code much harder to read, debug and profile. Virtual threads take the other route: keep the simple blocking code, and make blocking cheap.

"Virtual threads make everything faster." They make waiting cheap. Work that keeps the processor busy gains nothing, because you still only have as many cores as you have. Measured here on a machine with 12 processors, processor bound work would land at the same total time either way.

"They are just a lighter thread pool." The point is not to pool them at all. You create one per task and let it end. Pooling virtual threads is a mistake, and the reason is in chapter six.

Follow-up questions

Why does creating platform threads get slower and slower?

Because each one is a request to the operating system, and the operating system is doing real work each time.

It has to reserve a stack, which is about a megabyte of address space per thread by default. It has to create its own bookkeeping structures. And every additional thread makes its scheduler's job harder, because there are more candidates to consider each time it decides what runs next.

The measurements show that curve clearly: 1,000 in 37 ms, 10,000 in 513 ms, 20,000 in 2,129 ms, 50,000 in 12,605 ms. Doubling from ten to twenty thousand cost four times as much, not twice.

The memory is the harder limit in production. Fifty thousand platform threads is roughly fifty gigabytes of reserved stack space, which is why a service creating threads per request falls over long before the processor is busy, and why it shows up as the container being killed rather than as a Java error.

A virtual thread has none of this. It starts as a small object on the heap with a stack that grows and shrinks as needed, so a million of them is a heap question, not an operating system question.

When do virtual threads give you nothing at all?

When your threads are busy rather than waiting. Being able to say this clearly is what separates understanding from enthusiasm.

Virtual threads work by unmounting from their carrier whenever they block, freeing it for someone else. A thread that never blocks never unmounts, so there is nothing to gain. Image processing, parsing large files, cryptography, heavy calculation: all of these keep the processor busy, and you can only ever run as many of those at once as you have cores.

In fact you can do slightly worse, because you have added a scheduling layer for no benefit. For that kind of work a fixed pool sized to the core count remains exactly right.

The other case is work that is already fast. If a task takes a microsecond, thread creation cost was never your problem, and a pool was fine.

The honest summary: virtual threads are for code that waits on other systems. That happens to be most backend code, which is why they matter, but it is a specific claim rather than a general one.

02 Mounting and unmounting

  • What is a carrier thread?
  • What happens when a virtual thread blocks?
  • Where does its stack go while it is not running?
  • How many carriers are there by default?

A virtual thread does not run by itself. To execute, it has to be mounted onto a real platform thread, called a carrier. There is a small pool of carriers, by default one per processor.

The interesting part is what happens when the virtual thread blocks. Instead of the carrier sitting there waiting, Java unmounts the virtual thread: it copies its stack onto the heap, frees the carrier for somebody else, and remembers where to resume. When the thing it was waiting for arrives, it is mounted again, possibly onto a completely different carrier.

This is the entire trick. A blocked platform thread holds a real operating system thread hostage. A blocked virtual thread holds nothing except some heap memory. That is why ten thousand of them can wait at the same time on a machine with twelve processors.

Where the stack lives

A platform thread's stack is a fixed block of memory reserved by the operating system, whether it is used or not. That is where the megabyte goes.

A virtual thread's stack lives on the heap and is only as big as it currently needs. While the thread is running it is copied onto the carrier's real stack; when it unmounts, the used part is copied back to the heap. That copying is not free, but it is far cheaper than reserving a megabyte per thread, and it is why a virtual thread's cost is proportional to how deep its call stack actually is.

How many carriers

By default, one per processor. On the machine these measurements came from that is twelve. You can change it, but the number is deliberately small: carriers are meant to be always busy, never waiting, so having many more than you have processors would defeat the purpose.

# only if you have measured a reason to
-Djdk.virtualThreadScheduler.parallelism=16
-Djdk.virtualThreadScheduler.maxPoolSize=256

"A virtual thread runs on its own thread." It borrows a carrier while it is running and gives it back the moment it waits. It may run on a different carrier each time.

"Unmounting is free." The stack has to be copied both ways. It is cheap next to reserving a megabyte, but a virtual thread with a very deep call stack that blocks constantly will pay for it.

Follow-up questions

Which operations actually cause an unmount?

The ones Java rewrote to know about virtual threads. That covers almost everything you would normally block on:

  • Thread.sleep
  • Reading and writing sockets, which means almost all network calls, including database drivers and HTTP clients that use standard Java networking
  • Waiting on locks, queues, latches and futures from the concurrency library
  • Waiting on an object monitor

The important consequence is that you do not write anything special. Ordinary blocking code unmounts automatically. That is the whole design goal: existing code, existing libraries, no rewrite.

What does not unmount is anything that blocks below Java, in code written in C. The virtual thread's stack is interleaved with native frames that Java cannot move to the heap, so it has to stay put and the carrier stays with it.

Ordinary file input and output is worth a specific mention, because it is the common surprise: on most platforms file operations are not truly non blocking underneath, so Java runs them on a separate pool rather than unmounting. It works correctly and does not pin, but it does not get the full benefit either.

Should you ever change the number of carriers?

Rarely, and only with a measurement in hand, because the default is deliberately equal to your processor count for a good reason.

Carriers are meant to be doing actual work at all times. Waiting is supposed to happen by unmounting, not by a carrier sitting idle. If that holds, having more carriers than processors just adds switching overhead without letting more work happen.

The case where raising it genuinely helps is when something in your stack still holds a carrier while blocking, which is chapter three. If profiling shows carriers stuck rather than working, more carriers is a way to buy time while you fix the real cause.

Worth knowing that two settings exist and they are different. Parallelism is the target number of carriers running at once. Maximum pool size is the ceiling the scheduler may temporarily grow to when it detects carriers are stuck, which is a safety valve rather than something you tune.

The better answer in an interview is to say you would find out why carriers are not free, rather than adding more of them.

03 Pinning, and what changed in Java 24

  • What is pinning and why does it matter?
  • Did blocking inside synchronized pin the carrier?
  • What changed in Java 24?
  • What still pins?

Pinning is when a virtual thread blocks but cannot unmount, so it keeps its carrier. The carrier does no work and cannot be given to anybody else. Enough pinned threads and you are back to a small fixed pool, having paid for virtual threads and got nothing.

The advice almost every article still gives

For years the rule has been: blocking inside a synchronized block pins the carrier, so replace synchronized with ReentrantLock before adopting virtual threads. That advice was correct for Java 21, 22 and 23.

Measured on Java 24

Two thousand virtual threads, each locking its own object so there is no contention at all, then sleeping 200 ms. The only thing that could serialise them is pinning. The machine has 12 carriers.

if pinning happens, expect roughly 33,200 ms
if it does not, expect roughly 200 ms

blocking inside                       wall time
--------------------------------------------------
synchronized (own monitor)               236 ms
ReentrantLock (own lock)                 212 ms

They are the same, and both are near the theoretical floor. If synchronized still pinned, the first row would have been about 33 seconds. Java 24 removed that behaviour, so a virtual thread blocking inside synchronized now unmounts like anything else.

So the most repeated piece of virtual threads advice is out of date on Java 24, and correct on Java 21 to 23. Know both, and know which version you are on. Saying that in an interview is a much stronger answer than either rule alone.

What still pins

The remaining case is code that blocks below Java, in native code written in C. The virtual thread's stack is then mixed with frames that Java cannot copy to the heap, so it cannot be moved and the carrier stays with it.

In practice that means some older database drivers and libraries with native components. The way to find out is to measure rather than guess: Java can record an event whenever a virtual thread is pinned, and looking for those events tells you whether your dependencies have the problem.

"You must replace all synchronized with ReentrantLock." True on Java 21 to 23. Measured false on Java 24. Doing it anyway is a large change to working code for no gain.

"Pinning means deadlock." It means lost throughput. The work still completes, just with far less parallelism than you were expecting, which makes it a performance mystery rather than an obvious failure.

Follow-up questions

How would you detect pinning in a running service?

Java records an event every time a virtual thread is pinned for a meaningful length of time, and that event is the direct evidence. Start a recording, run your load, and look for those events. Each one tells you where it happened, so you get the exact code path rather than a suspicion.

The symptom that sends you looking is distinctive. Throughput is far lower than the arithmetic says it should be, the processor is not busy, and adding more virtual threads changes nothing. That last part is the giveaway: with virtual threads working properly, more concurrent waiting work should cost almost nothing.

A thread dump helps too. On a service using virtual threads properly, the carrier threads should be doing work or idle. Carriers sitting inside application code that is waiting for something is the picture of pinning.

Practical caveat worth adding: before hunting pinning, check the simpler explanation. A connection pool with twenty connections limits you to twenty concurrent database calls no matter how many virtual threads you have. That is not pinning, it is chapter six.

If synchronized no longer pins, is there any reason left to prefer ReentrantLock?

Yes, but the reasons are the same ones that always applied, and none of them are about virtual threads any more.

ReentrantLock can be taken with a timeout, so a thread can give up rather than wait forever. That turns a potential deadlock into a failed request you can retry, which is genuinely valuable in a service.

It can be taken in a way that allows the waiting thread to be interrupted, so work can be cancelled.

It can be made fair, so the longest waiting thread goes next rather than whoever happens to win the race.

And it can be acquired in one method and released in another, which synchronized cannot do, because its scope is a block.

Against all that, synchronized releases automatically when the block exits, including on an exception, which removes the most common bug with locks. So the honest answer is that the choice went back to being the ordinary one it was before virtual threads existed: use synchronized unless you need one of those four things.

04 Which model, and why

  • Compare virtual threads, CompletableFuture and reactive.
  • What do virtual threads give you that the other two do not?
  • When is reactive still the right answer?

All three exist to solve the same problem: how do you handle many things at once without one real thread per thing. They differ in what they cost you to read and debug.

Which model are you asking about?

Model

Pick one

Each one trades away something different. The question is which cost you are willing to pay.

The same work, three ways

// blocking, on a virtual thread: reads top to bottom
var user = userService.find(id);
var orders = orderService.forUser(user);
return render(user, orders);

// CompletableFuture: the same logic, turned inside out
return supplyAsync(() -> userService.find(id), pool)
    .thenCompose(user -> supplyAsync(() -> orderService.forUser(user), pool)
        .thenApply(orders -> render(user, orders)));

The first version can be stepped through in a debugger, and a stack trace from inside it shows the whole path that led there. The second version cannot, and does not: a failure inside the second call gives you a stack trace full of framework machinery rather than your own call chain.

That readability is the actual argument for virtual threads. The performance argument matters, but the cost of asynchronous code has always been paid in debugging.

The one line answer. "Virtual threads let you write blocking code that scales like asynchronous code. You keep ordinary control flow, real stack traces and working debuggers, and you give up the fine grained control over scheduling and backpressure that reactive gives you."

"Virtual threads replace reactive entirely." They replace the most common reason people reached for reactive, which was thread efficiency. They do not give you operators for streams of events, backpressure across a pipeline, or composition over time.

"You should rewrite your reactive code." Working code that is well understood is not a problem to be solved. This is a decision for new code, or for code you are already rewriting.

Follow-up questions

When is reactive still genuinely the right choice?

When you need the things it does that have nothing to do with thread efficiency.

Backpressure across a whole pipeline. If a fast producer feeds a slow consumer through several stages, reactive lets the slow end tell the fast end to slow down, all the way up. Virtual threads give you cheap blocking, which handles it at one hop but does not propagate a rate limit through a chain of stages.

Streams of events over time. Anything where the natural unit is a sequence that arrives gradually: server sent events, websockets, message streams. Operators for buffering, windowing, throttling and merging are real value that blocking code has no direct answer to.

Composition over time. Combining several sources with rules like "take the first to answer, but retry this one twice, and time the whole thing out" is genuinely nicer as operators than as hand written code.

The clean way to say it: reactive is a programming model for streams that happened to also solve thread efficiency. Virtual threads solve the thread efficiency part far more simply. If you were using reactive only for that, you no longer need it. If you were using it for the stream operators, you still do.

05 Structured concurrency

  • What problem does structured concurrency solve?
  • What happens when one subtask fails?
  • Why is it better than submitting to an executor?

Virtual threads make it cheap to start work. Structured concurrency is about not losing track of it.

The problem: you start three calls in parallel and wait for all three. One fails. What happens to the other two? With an executor, nothing. They carry on, using resources, producing results nobody will read, and possibly failing later in a log nobody connects to the original request.

The idea

Work started inside a block must finish inside that block. If one part fails, the rest are cancelled automatically. You cannot accidentally leave something running, because the block will not exit until everything it started has finished or been cancelled.

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user = scope.fork(() -> loadUser(id));      // each on its own virtual thread
    var cart = scope.fork(() -> loadCart(id));

    scope.join();                                  // wait for both
    scope.throwIfFailed();                         // rethrow the first failure

    return new Order(user.get(), cart.get());
}

Measured

Running the above with one subtask taking 100 ms, the other 300 ms:

1. both succeed:
   Order[user=user-42, cart=cart-7]

2. one fails, so the other is cancelled:
   whole scope failed: cart service is down

Both calls run at the same time, so the whole thing takes as long as the slower one rather than the sum. When one fails, the other is cancelled rather than left running.

Still a preview feature. On Java 24 this needs --enable-preview, and the API has been changing between releases. Worth knowing about and worth saying you know it is not final. Do not put it in production code yet.

"It is just a nicer executor." The difference is the guarantee. An executor lets work outlive the code that started it. A scope cannot exit while anything it started is still running.

Follow-up questions

What does it actually fix that an executor does not?

Three things, and the third is the one people feel most often.

Leaked work. With an executor, submitting three tasks and returning early after one fails leaves the other two running. They consume connections and processor time producing a result nobody wants, and if they fail they do so in a log with no obvious link to the request that caused them. A scope cancels them.

Cancellation that actually propagates. If the caller gives up, everything below should stop. With executors that has to be plumbed by hand through every layer, and usually is not. With scopes it is the default.

Stack traces that make sense. A failure in a subtask carries the relationship back to the code that started it, so the trace shows where the work came from. Failures inside pooled tasks show the pool's thread and nothing about the request.

The framing that lands well: it does for concurrency what structured programming did for control flow. Submitting to an executor is the concurrency version of a jump: work goes somewhere and the relationship is gone. A scope keeps the shape of the code and the shape of the work the same.

06 What breaks when you migrate

  • Why should you not pool virtual threads?
  • What happens to ThreadLocal with millions of threads?
  • What becomes the new bottleneck?
  • What do you actually change to adopt them?

Adopting virtual threads is mostly a one line change. The problems come from things built on the old assumption that threads are scarce.

Do not pool them

// wrong: a pool exists to ration something expensive
Executors.newFixedThreadPool(200, Thread.ofVirtual().factory());

// right: one per task, created and discarded freely
Executors.newVirtualThreadPerTaskExecutor();

Pooling virtual threads reintroduces exactly the limit you were removing. The first line caps you at 200 concurrent tasks again, having gained nothing.

The bottleneck moves

This is the most useful thing in the chapter. Your thread pool was quietly limiting how much load you sent downstream. Remove it and ten thousand requests hit the database at once. The connection pool becomes the new limit, or the database falls over.

So a virtual threads migration is really a conversation about where the limit should live. It has to live somewhere. Previously it was an accident of pool size; now you choose it deliberately, with a connection pool size, a semaphore, or a rate limiter.

ThreadLocal

With two hundred pooled threads, a ThreadLocal holds two hundred values. With a virtual thread per request and ten thousand concurrent requests, it holds ten thousand.

The good news is that virtual threads are short lived, so a value dies with its thread rather than living forever on a pooled thread. That removes the leak from Episode 1. The bad news is the sheer count: anything expensive per thread, a buffer or a parser, is now allocated per request.

The replacement is a scoped value: set once for a block of work, visible to everything inside it including subtasks, and immutable. Still preview, like structured concurrency.

What you actually change

  1. Swap the executor. One line, and often that is genuinely all.
  2. Put a real limit on shared resources. Size the connection pool deliberately, and use a semaphore around anything a downstream service cannot take at full speed.
  3. Check timeouts exist. Blocking is cheap now, so a call with no timeout can accumulate an enormous number of waiting threads instead of being capped by pool size.
  4. Look for per thread caching. Anything held in a ThreadLocal for reuse is now per request.
  5. Measure before deciding anything else. On Java 24 you do not need the synchronized rewrite that older guides insist on.

"We switched to virtual threads and it got slower." Usually the limit moved somewhere worse. The old pool was protecting the database, and removing it sent everything downstream at once.

"Virtual threads mean we do not need timeouts." The opposite. Cheap blocking means far more things can be waiting at the same time, so a missing timeout accumulates much faster.

Follow-up questions

Walk me through adopting them in an existing Spring service.

The change itself is small, and saying that plainly is correct rather than glib.

Turn it on. Modern Spring Boot has a single property that makes the web server handle each request on a virtual thread. That covers the main case, because most of a service's threads are request handling threads.

Then look at what you have removed the limit from. The request thread pool was capping concurrent database work. Now it is not, so the connection pool size becomes the real limit and needs choosing deliberately rather than inheriting a default.

Check every outbound call has a timeout. Connect and read timeouts on HTTP clients, query timeouts on the database. Under the old pool a missing timeout was capped by the pool size; now it is not capped by anything.

Add a limit where a downstream service is fragile. A semaphore around calls to a service that cannot take a thousand at once is the honest way to express what the thread pool was doing accidentally.

Then measure. Compare latency at high percentiles and throughput under real load. The expected result is that throughput stops being capped by thread count, and the slowest requests improve because they are no longer queueing for a thread.

Do virtual threads change how you debug a stuck service?

Yes, and it is worth knowing before you need it at three in the morning.

An ordinary thread dump shows platform threads. With virtual threads, the interesting ones may not appear, because there can be a million of them and they are not operating system threads. What you see is a small number of carriers, which tells you very little.

The replacement is a thread dump in a structured format that includes virtual threads, which Java can produce on demand. Because it may contain enormous numbers of entries, you read it by grouping and counting rather than scrolling: how many are waiting on the same call is the question, exactly as in Episode 2, but at a scale where you must aggregate rather than eyeball.

The good news is that the diagnosis itself gets easier. Blocking code produces real stack traces showing the whole path, so a stuck virtual thread tells you what it is waiting for and how it got there. That is a genuine improvement over debugging a stuck reactive pipeline, where the stack is mostly framework.

One habit worth keeping: name them. A virtual thread with a meaningful name is as much easier to read in a dump as a well named pool was.

G Word list

Every term on this page that you might not already know.

platform thread
An ordinary Java thread, backed by a real operating system thread. Costs about a megabyte of memory outside the heap.
virtual thread
A thread managed by Java itself, living on the heap. Cheap enough to have a million of them.

The real platform thread a virtual thread borrows while it is actually running. One per processor by default.

Attaching a virtual thread to a carrier so it can run.

Detaching it when it blocks, copying its stack to the heap and freeing the carrier for someone else. This is the whole trick.
