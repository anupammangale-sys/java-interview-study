Your Singleton is not one, and here is the proof

Reflection, serialization and cloning each produced a second instance of a textbook Singleton. Thirty two threads calling an unsynchronised lazy getInstance created thirty one objects. Everything on this page was run, so the broken results are real rather than claimed.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 Writing a Singleton

  • Write an eager and a lazy Singleton.
  • What goes wrong with lazy initialisation and threads?
  • Why does double checked locking need volatile?
  • What is the holder idiom and why is it the neat answer?

Four ways to write it. Only the first one is unconditionally safe without thinking.

// 1. eager: built when the class loads
private static final Heavy INSTANCE = new Heavy();

// 2. lazy, unprotected: broken with threads
if (instance == null) instance = new Heavy();

// 3. synchronized method: correct, and every call pays for the lock
static synchronized Heavy get() { ... }

// 4. double checked locking, which needs volatile to be correct
static volatile Heavy dcl;

Measured: what unprotected lazy initialisation actually does

Thirty two threads calling getInstance() at the same moment, five attempts. A correct Singleton gives exactly one object every time.

How it is writtenDistinct instances createdCorrect
no protection29, 30, 29, 29, 31no
synchronized method1, 1, 1, 1, 1yes
double checked with volatile1, 1, 1, 1, 1yes
holder idiom1, 1, 1, 1, 1yes

Twenty nine "singletons". Almost every thread passed the null check before any of them finished building, so almost every thread built its own. This is not a rare interleaving, it is what happens whenever construction takes any time at all.

The holder idiom, which is the answer worth giving

static class Holder {
    static final Heavy INSTANCE = new Heavy();
}
static Heavy getInstance() { return Holder.INSTANCE; }

It is lazy, because the inner class is not loaded until Holder.INSTANCE is first mentioned. It is thread safe, because the language already guarantees that class initialisation happens once even with many threads. And it costs nothing per call, because there is no lock to take.

You get everything double checked locking gives you, without writing the tricky part.

Why double checked locking needs volatile

new Heavy() is not one step. Memory is allocated, the constructor runs, and the reference is assigned. Without volatile, the compiler or processor is allowed to reorder the last two, so another thread can see a non null reference pointing at an object whose fields have not been written yet.

An honest caveat. That reordering was not demonstrated here, and the demo says so. It needs a processor with weaker memory ordering than an ordinary desktop, so on this machine the version without volatile would appear to work. Saying "I know why it is required and I know I cannot easily reproduce it" is a stronger answer than pretending to have seen it.

"Lazy is better because it saves memory." For most singletons the object is small and will be needed anyway. Eager, or the holder idiom, avoids the entire problem. Lazy is worth it when construction is genuinely expensive and often skipped.

"Double checked locking is the right answer." It is a correct answer that is easy to write wrongly. The holder idiom gets the same result with nothing to get wrong.

Follow-up questions

Why is the holder idiom thread safe without any locking of your own?

Because the language already promises that a class is initialised exactly once, and it makes other threads wait while that happens.

When the first thread touches Holder.INSTANCE, the runtime begins initialising Holder. Any other thread arriving during that window blocks until initialisation finishes, then sees the completed result. That is a guarantee of class initialisation itself, not something you arrange.

So you get the locking behaviour without writing a lock, and once the class is initialised there is no further cost at all: later calls are just a field read with no synchronisation on the path.

The laziness comes free from the same mechanism. A nested class is not initialised when the outer class is, only when something first refers to it. So Holder stays untouched until the first getInstance().

The one thing worth knowing: if the constructor throws, the class fails to initialise and every later access throws NoClassDefFoundError rather than retrying. That is true of eager initialisation too, and it is the argument for lazy initialisation you can retry when construction can genuinely fail.

Is a Singleton a good idea at all?

Worth having an opinion on, because the pattern is often asked about precisely so you will say something thoughtful.

The honest criticisms are real. A Singleton is global state, so anything using it has a dependency that does not appear in its constructor and is invisible to a reader. It makes testing awkward, because you cannot easily give a test a different one. And it tends to accumulate responsibilities, because it is convenient to reach for.

What people actually want is usually "one instance shared by the application", which is not the same as "a class that enforces its own uniqueness". In a Spring application you get the first without the second: the framework creates one and injects it, so the dependency is visible in the constructor and a test can pass in a different one.

So a defensible answer: I would use the framework's scope rather than the pattern in application code. I would use the pattern for something genuinely global with no dependencies, such as a stateless utility or a registry, and I would write it as an enum.

That answers the question and shows you know what the pattern costs, which is what the question is really for.

02 Breaking it

  • How does reflection break a Singleton, and how do you stop it?
  • How does serialization break it, and how do you stop it?
  • Why is an enum the safest Singleton?
  • What does an enum Singleton give up?

A private constructor stops ordinary code. It does not stop reflection, serialization or cloning, and each of those was used below to produce a second instance of a textbook Singleton.

The attack matrix, all measured

Click any cell to see what actually happened and the code that caused it.

What each attack looks like

// reflection: private stops the compiler, not the runtime
Constructor<Classic> c = Classic.class.getDeclaredConstructor();
c.setAccessible(true);
Classic second = c.newInstance();      // a whole new object

// serialization: reading always builds a new object
Classic third = roundTrip(Classic.getInstance());

// cloning: only if the class implements Cloneable
Classic fourth = (Classic) Classic.getInstance().clone();

Defending the ordinary class

private Defended() {
    if (INSTANCE != null) {                      // stops reflection
        throw new IllegalStateException("already created");
    }
}
private Object readResolve() {                  // stops serialization
    return INSTANCE;
}

The constructor guard works because the static field is already set by the time anyone can call the constructor again. readResolve works because deserialization calls it and uses whatever it returns instead of the object just built.

For cloning, either do not implement Cloneable, or override clone() to return the instance or throw.

Why the enum wins

enum Config {
    INSTANCE;
    int value = 42;
}

Both attacks are blocked by the language, not by your code. Reflection fails with IllegalArgumentException: Cannot reflectively create enum objects, which is the runtime refusing rather than a guard you remembered to write. Serialization is guaranteed to give back the same constant. Cloning is not possible at all.

That is why an enum is the recommended Singleton: you cannot forget the defences, because they are not yours.

What the enum gives up

  • It cannot extend a class, because it already extends Enum. It can implement interfaces.
  • It is created when the enum class loads, so it is not lazy in the holder idiom sense.
  • Some people find Config.INSTANCE.doThing() reads oddly for something that is not a set of constants.

"A private constructor makes it a Singleton." Measured false three times over. It stops normal code and nothing else.

"Serialization is fine because it is the same class." Deserialization builds a new object every time. Without readResolve you get a second instance, measured.

Follow-up questions

How exactly does readResolve work?

It is a hook the deserialization machinery looks for by name. If your class declares a method called readResolve, it is called after the object has been rebuilt, and whatever it returns is handed to the caller instead.

private Object readResolve() {
    return INSTANCE;
}

So the new object is still built, it is just thrown away immediately and replaced with the real instance. That is why the measured result was same instance? true.

Two details that make this a good answer. It is found by name through reflection, not by implementing an interface, so a typo silently disables it with no compiler error. And it can be private, which is the usual choice, because the runtime finds it anyway.

The gap worth mentioning: readResolve fixes the instance but any non transient field was still read from the stream before it was discarded, so it does not protect against a maliciously crafted stream. If that matters, the enum is the better answer because there is nothing to craft.

If reflection can break anything, is the constructor guard worth writing?

Yes, and being precise about what it does and does not buy you is the better answer.

What it stops is real: the measured attack failed with IllegalStateException: already created. Anyone calling the constructor reflectively after the instance exists gets an exception rather than a second object.

What it does not stop is a determined attacker. If they can reach the constructor at all, they can usually also set the static field back to null reflectively first, and then the guard passes. Reflection can reach private state as easily as private methods.

So the honest framing: the guard protects against accident, not against malice. Accident is the realistic threat in most codebases, usually a framework or a serialization library instantiating things generically, and the guard turns that into a loud failure instead of a silent duplicate.

If you genuinely need to resist deliberate attack, the enum is the answer, because the refusal comes from the runtime rather than from code that can be worked around.

03 Java Singleton against Spring singleton

  • What does "singleton" mean in Spring?
  • How many instances exist if you have two application contexts?
  • What is the danger of state in a Spring singleton?
  • What happens when a singleton bean needs a prototype bean?

They share a word and mean different things, which is exactly why the comparison gets asked.

Java Singleton patternSpring singleton scope
One per whatper class loaderper application context
Enforced bythe class itselfthe container
Two contexts meansstill onetwo instances
Constructorprivatepublic, the container calls it
How you get itgetInstance()injected

The line that answers the question. "A Java Singleton is a class that refuses to be instantiated twice. A Spring singleton is an ordinary class that the container happens to create once per context. Two contexts give you two instances, so it is a scope, not a guarantee about the class."

Why the difference matters in practice

Because a Spring singleton is an ordinary object, it is shared by every thread handling every request. That makes mutable fields on a bean a concurrency bug, and it is one of the most common real ones.

@Service
class OrderService {
    private String currentUser;      // shared by every request at once

    void handle(Order o) {
        currentUser = o.user();       // another request overwrites this
        ...
    }
}

Every field on a singleton bean should be final and set in the constructor. Anything that varies per request belongs in a method parameter or a local variable.

When a singleton needs a prototype

A singleton bean is created once, so its dependencies are injected once. If it depends on a prototype bean, it gets one prototype instance and keeps it forever, which is almost never what was wanted.

The fix is to ask for a new one each time rather than holding a reference: inject a provider and call it per use, or use method injection. The important half of the answer is recognising the problem, because it fails silently.

"Spring singleton means only one instance in the JVM." One per application context. Tests routinely create several, and so do some applications.

"Beans are thread safe because Spring manages them." Spring manages the lifecycle, not the concurrency. A shared bean with mutable state is a race.

Follow-up questions

Where do the other Spring scopes fit?

Singleton and prototype are the two that exist everywhere. The rest only exist in a web application.

Singleton is the default: one per context, created eagerly at startup unless marked lazy. Almost everything should be this.

Prototype is a new instance every time it is asked for. The detail people miss is that the container does not manage its full lifecycle afterwards: destruction callbacks are not called, so anything holding a resource has to be closed by whoever asked for it.

Request and session are web only, giving one per HTTP request or per user session.

The interesting practical point is that scopes only work when the container is doing the wiring. If a singleton holds a direct reference to a request scoped bean, the reference would outlive the request, so Spring injects a proxy that looks up the right instance per call. That is why the injected type sometimes needs an interface, and why the stack trace shows a generated class rather than yours.

The one line summary worth giving: prefer singleton with no state, and treat any other scope as a signal that state is being carried where it probably should not be.

04 Strategy

  • Refactor a long if-else chain on a type code.
  • What does that buy you, concretely?
  • When is the if-else actually fine?

This is the most commonly asked refactor in the whole round, usually phrased as "clean this up".

// the version that grows a branch every time the business changes
if (method.equals("card"))        return amount * 0.029 + 0.30;
else if (method.equals("bank"))   return 0.25;
else if (method.equals("wallet")) return amount * 0.015;
else if (method.equals("crypto")) return amount * 0.01;
else throw new IllegalArgumentException("unknown method");
// the same rules as a lookup
static final Map<String, Function<Double, Double>> FEES = Map.of(
    "card",   a -> a * 0.029 + 0.30,
    "bank",   a -> 0.25,
    "wallet", a -> a * 0.015,
    "crypto", a -> a * 0.01);

Both were run against the same inputs and agree exactly:

card    if-else 3.20   map 3.20   enum 3.20
bank    if-else 0.25   map 0.25   enum 0.25
wallet  if-else 1.50   map 1.50   enum 1.50
crypto  if-else 1.00   map 1.00   enum 1.00

What it actually buys you

Not speed. The gain is what happens when a fifth payment method arrives: the chain has to be edited, the map has an entry added. That is the open closed principle in one concrete sentence, and it is the answer the question is fishing for.

It also means each rule can be tested on its own, and the rules can come from configuration rather than being compiled in.

The enum version, when the set is fixed

enum Fee {
    CARD   { double of(double a) { return a * 0.029 + 0.30; } },
    BANK   { double of(double a) { return 0.25; } },
    WALLET { double of(double a) { return a * 0.015; } };
    abstract double of(double amount);
}

The behaviour lives on the constant. You cannot add a case and forget to implement it, because the compiler will not let you. Use this when the set is genuinely fixed and known at compile time; use the map when strategies are registered or configured.

When the if-else is fine, and saying so is a good sign. Three branches that will never change, in one place, is clearer as an if-else than as a map. The pattern earns its place when the list grows, when the branches are long, or when the same switch appears in more than one place. That third one is the strongest signal.

"Strategy is faster than if-else." It is not, and that is not the point. A map lookup against a few string comparisons is noise.

Replacing every conditional with a pattern. Two branches wrapped in three interfaces is worse code, and interviewers notice that too.

Follow-up questions

How would you make the strategies pluggable at runtime?

Register them rather than declaring them, which is what a framework does for you.

interface FeeRule {
    String method();
    double feeOn(double amount);
}

// Spring injects every implementation it can find
FeeService(List<FeeRule> rules) {
    this.byMethod = rules.stream()
        .collect(toMap(FeeRule::method, r -> r));
}

Adding a payment method now means adding one class. No existing file changes, which is the whole promise of the refactor made literal.

Two things worth raising unprompted, because they are what goes wrong. First, toMap throws on a duplicate key, so two rules claiming the same method fail loudly at startup rather than silently picking one, which is what you want. Second, you need to decide what an unknown method does: throwing is usually right, and a silent default is how a pricing bug ships.

The same shape without Spring is a registry the implementations add themselves to, or a service loader. The idea is identical: the list of strategies is data, not code.

05 Factory

  • What problem does a factory solve?
  • Difference between a factory method and an abstract factory?
  • How is this different from Strategy?

A factory means the caller says what it wants and never names the class that provides it.

static Report reportFor(String format, List<String> rows) {
    return switch (format) {
        case "csv"  -> new CsvReport(rows);
        case "json" -> new JsonReport(rows);
        default -> throw new IllegalArgumentException("no such format");
    };
}
csv  -> ann,bob
json -> ["ann","bob"]

The calling code holds a Report and never mentions CsvReport. Adding a format changes one method, and nothing that calls it.

Factory method against abstract factory

  • A factory method makes one kind of thing. reportFor above.
  • An abstract factory makes a family of related things that must match each other. A UiFactory that produces a button, a checkbox and a scrollbar, where you must not mix one theme's button with another theme's scrollbar.

The honest note: abstract factory is asked about far more often than it is used. If your answer is "one method returning one interface" you have described what people actually build, and saying that the family version exists for keeping a set consistent is enough.

How it differs from Strategy

The code can look identical, and the difference is what varies. A factory decides which object to create. A strategy decides which behaviour to run, usually with the object already in hand.

A useful test: if the returned thing is used once and thrown away, it is probably a strategy. If it is a real object that lives on and holds state, it is probably a factory.

Calling every static creation method a factory pattern. A static method returning a concrete type you also name is just a helper. The pattern is about the caller not knowing the type.

Building a factory when a constructor would do. If there is only ever one implementation, you have added indirection and nothing else.

Follow-up questions

Why use a static factory method instead of a constructor?

Four reasons, and they are worth knowing separately from the pattern.

It has a name. Duration.ofSeconds(30) and Duration.ofMinutes(30) cannot both be constructors, because they take the same type. A name also makes the call readable at the call site.

It does not have to create anything. It can return a cached instance, which is how Integer.valueOf and Boolean.valueOf work. A constructor is obliged to make a new object every time.

It can return a subtype. List.of() returns different implementations depending on the number of arguments, and callers neither know nor care.

It can fail differently. Returning an Optional or a result object is possible; a constructor can only throw.

The trade off worth mentioning: a class with only private constructors cannot be subclassed, which is often deliberate but occasionally a problem. And factory methods are less discoverable than constructors, which is why the naming conventions matter: of, from, valueOf, getInstance.

06 The quick round

  • Builder: when and why?
  • Observer: what is the leak everybody creates?
  • Decorator against inheritance.
  • Adapter: what problem is it solving?

Four patterns that come up as quick questions. Click one for what it is for, what it looks like, and what actually goes wrong with it.

Which one?

Pattern

Pick one

Each was written and run. The output shown is what it printed.

The connection worth making out loud. Observer is where the listener leak from Episode 1 comes from. Subscribing without ever unsubscribing means the publisher holds a reference to your object forever, so it can never be cleaned up. In the measured demo, unsubscribing the email service stopped it receiving the second event; forgetting that call is the leak.

Builder for a class with two fields. A constructor is clearer. Builders earn their place at four or more, especially when several are optional or the same type.

Decorator confused with inheritance. Inheritance fixes the behaviour at compile time and multiplies classes for each combination. Decorators compose at runtime, so three layers give you every combination with three classes.

Follow-up questions

Which of these does the standard library use, and where?

Naming real examples is the strongest way to show these are not just diagram patterns.

Decorator is the input and output streams. new BufferedReader(new InputStreamReader(in)) is two decorators wrapping a source, each adding one behaviour. That is also the clearest argument against inheritance: buffering, character decoding and line reading combine freely instead of needing a class per combination.

Builder is StringBuilder, and more precisely HttpRequest.newBuilder() in the HTTP client, which is the modern shape with a validating build().

Observer is every listener API, and in the concurrency library CompletableFuture.thenAccept is the same idea with a nicer name.

Adapter is Arrays.asList, which makes an array look like a List without copying it. Its famous surprise, that add throws while set works, is exactly because it is an adapter over a fixed size thing rather than a real list.

Factory is List.of, Optional.of and Integer.valueOf, the last of which caches small values rather than creating one.

What is the difference between Decorator and Proxy?

They have nearly identical structure and different intent, which is why the question is asked.

Both wrap an object and implement the same interface, so a diagram of the two looks the same. The difference is what the wrapper is for.

A decorator adds behaviour to something you already have, and you usually stack several deliberately. You choose the layers and the order at the point of construction.

A proxy controls access to something, and often you do not know it is there. It might create the real object lazily, check permissions, cache results, or send the call over a network. There is typically one, and it is invisible.

The clearest example is the one you meet daily: Spring wraps a bean in a proxy to make @Transactional work. You did not ask for it and you cannot see it, which is exactly why calling an annotated method from inside the same class skips the transaction. The call never leaves the object, so it never passes through the proxy.

Saying that last part is worth a lot, because it turns a pattern question into a real Spring behaviour you can explain.
