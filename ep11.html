Study material

Forty five minutes

You get a vague sentence, a blank screen and about an hour. "Design a notification service." This episode builds one, in plain Java with no framework, and then measures the two things the follow-up questions are really about: what a rate limiter lets through, and what happens when everybody retries at once. One of those measurements came out the opposite of what the textbook version says.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 How the round actually runs

  • You get "design a notification service" and 45 minutes. What are the first five minutes for?
  • What is the interviewer actually scoring?
  • How much of the hour should be spent writing code?
  • What do you do when you are running out of time?

What the round is. Between 45 and 60 minutes. One vague sentence as the brief. You are expected to end up with running or nearly running code, usually in a shared editor with no compiler and no internet.

What it is not. It is not the system design round. Nobody wants a diagram with Kafka and three regions. The scope is one service, in one process, with real classes and real method signatures. If you find yourself drawing boxes, you are in the wrong round.

What is actually being scored. Interviewers are not counting features. They are watching for four things, and the last one is where most people lose:

  • Do you ask before you build? The brief is deliberately thin. Someone who starts typing immediately is telling you what they do at work.
  • Do your names mean anything? Channel, send, worthRetrying. Not Manager, process, flag.
  • Can it grow? The follow-up is always "now add WhatsApp" or "now add a rate limit". If that means editing three existing methods, the design has already answered.
  • Do you know what you did not do? Saying "this queue is in memory, so a restart loses everything, and here is what I would change" scores higher than a design that quietly has the same hole.

How to spend the time. This split is worth rehearsing until it is automatic, because the failure mode is spending 30 minutes on classes and never reaching the part they wanted to talk about.

Where the hour goesclick a phase

Pick a phase.

The questions to ask in the first five minutes. Ask three or four of these, not all of them. The point is to show you know the answer changes the design:

QuestionWhy it changes the design
Which channels? Email, SMS, push, more later? Decides whether channels are an interface or just a few methods
Roughly how many per second? Ten per second and ten thousand per second are different programs
If a message is lost, does anyone care? An OTP is not a marketing email. This decides whether an in memory queue is acceptable at all
Is sending the same thing twice a problem? Decides whether you need idempotency keys, which is a whole feature
Do we own the sending, or call a provider? Decides whether failures are yours to fix or someone else's to wait for

What to say when time runs out. Do not go quiet and keep typing. Say what you would do next and why, out loud. "I have not handled the case where the process restarts with jobs still in the queue. In production that queue would be Redis or a database table so the work survives, and the code would not change much because the interface stays the same." That sentence takes fifteen seconds and it is often worth more than the code.

Common wrong answers

Starting to code immediately. The brief is thin on purpose. Building the wrong thing quickly is the most common way to fail this round.

Drawing a distributed system. Queues between services, three regions, a message broker. That is the other round. Here it reads as avoiding the code.

Designing for a million a second when nobody asked. If you did not ask about scale, you cannot claim to be designing for it. Ask, then build for the answer.

Follow-up questions

How is this different from the system design round?

Different altitude, different artefact, different scoring, and mixing them up is a visible mistake.

System design is about how several services survive together. Boxes and arrows, which database, how many copies of things, what happens when a whole region goes away. The output is a diagram plus reasoning about trade-offs. Nobody writes a method signature.

Low level design is about how one service is put together inside one process. Classes, interfaces, method signatures, exception types, thread safety. The output is code that could compile. Nobody draws a region.

The clue is in the brief. "Design a notification service" with a shared editor open is the low level round. "Design a notification system for fifty million users" on a whiteboard is the other one. If you genuinely cannot tell, ask: "Would you like me to focus on the classes and interfaces, or on how the services fit together?" That question never loses points.

One overlap worth knowing: rate limiting and retries come up in both. In system design you say "we rate limit per client". Here you have to write the limiter and defend which algorithm you picked.

They said "no framework". Why does that matter?

Because a framework hides exactly the decisions being tested, and the interviewer knows it.

Say Spring is allowed. Retries become @Retryable. The queue becomes a message listener. Injection becomes an annotation. Every one of those is a decision somebody made, and reaching for the annotation means you never have to show that you understand it. The round exists to find out whether you do.

There is also a practical reason. In a shared editor with no compiler and no internet, anything you cannot write from memory is a risk. Plain Java is the only thing everyone in the room can read without asking which version of what is on the classpath.

The right way to handle it is to write the plain version and name the framework equivalent as you go. "This constructor is doing what Spring would do with an annotation." "This retry loop is what @Retryable generates." That shows you know both, and that you know which one is the actual mechanism. Reaching straight for the annotation only shows you know one.

How much code is enough? I never finish.

Almost nobody finishes, and finishing is not the bar. The bar is that the shape is clear and the important parts are real.

Write in this order. First, the interfaces and the record types, fully. These are small and they carry the whole design, so an interviewer can see your thinking from them alone. Second, the one class that ties it together, fully, because that is where the real decisions live. Third, one complete implementation of your main interface, so there is proof you can actually write a method.

Then stop writing implementations. The second and third channel can be a single line each: // SmsChannel and PushChannel look the same, different provider call. Nobody wants to watch you type the same class three times, and the minutes are worth more spent on the follow-ups.

The thing to protect is the part they will ask about. If you have twenty minutes of code and no rate limiter, and the follow-up is about rate limiting, you are answering in the air. Better to have a slightly thinner service and a real limiter.

What if I get stuck and go blank?

Say what you are stuck on. Silence is the only response that costs you marks, because from outside it is indistinguishable from not knowing.

"I am trying to decide whether the retry delay should block this worker or go back on the queue with a timestamp. Blocking is three lines and wastes a thread. Re-queueing needs a scheduler but keeps the workers free. I will re-queue, because at any real volume the threads matter more than the extra class." That is not being stuck, that is thinking out loud, and it is most of what the round is measuring.

If you are properly blank, go back to the data. Write the record for the thing being passed around, in our case Notification, with its fields. Fields are easier to reason about than behaviour, and once the data is on the screen the methods usually suggest themselves.

And take the hint when it comes. An interviewer who says "what happens if the provider is down?" is not curious, they are steering you towards the thing they want to score. Follow it immediately.

02 Three channels, one interface

  • Write the interface every notification channel implements.
  • Where do Strategy, Factory and Observer show up in this design?
  • How do you add a fourth channel without editing anything?
  • Why is Notification a record and not a class with setters?

Start with the data. One immutable thing gets passed between threads, so it is a record. Nothing can change it halfway through a retry:

service/Notification.javathe thing being sent
public record Notification(String id, String recipient, String channel,
                           String body, String idempotencyKey) {

    public Notification {
        if (recipient == null || recipient.isBlank()) {
            throw new IllegalArgumentException("recipient is required");
        }
    }
}

Then the one interface everything hangs off. Three methods would be too many. Two is right: what it is called, and how to send:

service/Channel.javathe strategy
public interface Channel {
    String name();
    void send(Notification n) throws NotificationException;
}

Three patterns are in this design and it is worth naming them out loud as you write, because interviewers are listening for whether you know what you are doing or stumbled into it.

PatternWhere it isWhat it buys here
StrategyChannel with email, SMS and push implementations A fourth channel is a new file. Nothing that already works gets edited.
FactoryChannels, which hands back a channel by name The service never writes new EmailChannel(), so it does not know which channels exist or how they are built.
ObserverNotificationListener, with metrics and audit implementations The service announces what happened and does not know who is listening. Adding metrics did not touch it.

The observer is the one people forget, and it is the one that keeps the service small. Without it, NotificationService would be counting metrics and printing audit lines itself, which is two more reasons for it to change. With it, the service says listeners.forEach(l -> l.sent(n, attempt)) and stops caring.

The listener interface uses default methods on purpose:

service/NotificationListener.javathe observer
public interface NotificationListener {
    default void sent(Notification n, int attempts) {}
    default void retrying(Notification n, int attempt, long delayMs) {}
    default void deadLettered(Notification n, String reason) {}
}

Empty bodies, not bodies that throw. A listener that only cares about failures implements one method and inherits three do-nothings, which is correct: doing nothing on an event you do not care about is a real, sensible behaviour. This is the one honest use of a default method, and it is worth saying why if you use it.

The whole thing runs. Three channels, one interface, two listeners nobody had to tell the service about:

service/Main.javareal output
=== 1. three channels, one interface ===
      [email] delivered to asha@example.com
      [push] delivered to device device-77
      [audit] N-3 sent after 1 attempt(s)
      [audit] N-1 sent after 1 attempt(s)
      retry N-2 in 50 ms, attempt 1 failed: sms provider busy
      retry N-2 in 100 ms, attempt 2 failed: sms provider busy
      [sms] delivered to +919876543210 on attempt 3
      [audit] N-2 sent after 3 attempt(s)

The lines are interleaved because three worker threads are running. That is worth pointing at rather than hiding: it is proof the queue and the workers are real.

Common wrong answers

An enum of channel types with a switch on it. It works, and it means every new channel edits the switch, and usually three switches in three places. That is the exact thing the follow-up question is designed to expose.

A base class AbstractChannel with the subclasses extending it. You do not need it yet. Reach for an interface first and add a shared base class only when there is real shared code, otherwise you have committed the design to inheritance for nothing.

Putting send on the notification itself. notification.send() reads nicely and means the data object now knows about providers, network calls and failure handling. Keep the thing and the doing separate.

Follow-up questions

Now add WhatsApp. What changes?

One new file, and one line where the channels are listed.

WhatsAppChannel implements Channel, with name() returning "whatsapp" and send() calling the provider. Then add new WhatsAppChannel() to the list handed to Channels at start up. Nothing else: not the service, not the queue, not the retry logic, not the other channels.

Say the wiring line out loud rather than pretending it does not exist. "Something has to learn the channel exists. I have put that in one place that holds wiring and no logic, so getting it wrong stops the application starting rather than breaking sending." That is a better answer than claiming zero changes, because the interviewer can see the line.

If they push further, the honest next step is that the list could be built by scanning for implementations rather than typed by hand. Java's ServiceLoader does this, and so does Spring when you ask for a List<Channel>. Worth naming, not worth writing in the round.

Why is Notification a record rather than a class with setters?

Three reasons, and the third is the one that matters here.

It cannot be half built. A record has one constructor that takes everything, so there is no window where the recipient is set and the body is not. With setters, any method receiving the object has to wonder which fields are filled in yet.

Validation happens once, in the compact constructor. The blank recipient check runs on creation and can never be bypassed afterwards, because there is no later.

It is safe to hand to several threads. This is the real reason in this design. The same Notification sits on a queue, gets picked up by a worker, fails, is scheduled for retry, and is picked up by a different worker. If any of those could change it, you would need locking, and you would get it wrong under time pressure. Because the fields are final, none of that applies and you can say so in one sentence.

The trade to admit: if a notification legitimately needs to change as it moves, a record forces you to create a new one each time. In this design nothing needs to, which is why it is the right choice here rather than always.

Why does the channel name live on the channel rather than in a map somewhere?

Because it keeps the two things that must agree in the same file.

With name() on the interface, EmailChannel owns both the string "email" and the behaviour behind it. To add a channel you write one file and everything about it is in that file. The factory just asks each channel what it is called and builds the map itself:

for (Channel c : channels) byName.put(c.name(), c);

The alternative is a map written out by hand somewhere else, pairing "email" with new EmailChannel(). Now the name and the class are in different files, and the failure mode is a typo that compiles perfectly and fails at run time with "no such channel". That is a genuinely nasty bug for something so small.

If an interviewer pushes on it, the honest limit is that a channel can now lie about its own name, and two channels could claim the same one. That is worth one line of defence in the factory: throw if a name is registered twice, because a silent overwrite would be much worse than a loud failure at start up.

Should the channel be told to send, or should it decide?

Told. And this is worth being able to argue, because it is the kind of thing an interviewer probes to see whether you have thought about where decisions live.

In this design, NotificationService reads notification.channel(), asks the factory for that channel, and calls send. The channel does one thing: it sends. It does not decide whether it should, does not know about retries, does not know a queue exists.

The alternative is to hand every channel every notification and let each decide whether it applies. That sounds flexible and it is worse: now the routing rule is spread across every channel, two channels can both claim the same notification, and none can claim it and it vanishes silently. To answer "why did this not get sent?" you have to read every implementation.

Where the alternative is right is when you genuinely want more than one to fire, for example send by push and also by email. That is a different requirement, and the clean answer is not to let channels decide, it is to let the notification carry a list of channels and have the service loop. The decision still lives in one place.

03 When it fails, and when the queue is full

  • Design the exception hierarchy. What is the one method that matters?
  • Checked or unchecked? Defend the choice.
  • The queue is full. What does submit do?
  • Why does the retry not just sleep on the worker thread?

The exception hierarchy is the highest scoring five lines in the round, because most candidates write one exception class and a comment. The useful idea is that the exception should carry the answer to the only question the caller has: is trying again ever going to work?

service/NotificationException.javathe base
public abstract class NotificationException extends Exception {
    protected NotificationException(String message) { super(message); }
    public abstract boolean worthRetrying();
}

// permanent: the address is wrong and will still be wrong in ten minutes
InvalidRecipientException      worthRetrying() -> false

// temporary: the provider is busy, later is genuinely worth a try
ChannelUnavailableException    worthRetrying() -> true

Now the entire retry decision in the service is one line:

if (!e.worthRetrying()) { giveUp(n, "permanent: " + e.getMessage(), attempt); }

No switch on exception type, no list of which classes are retryable kept somewhere else and slowly going stale. A new exception type answers the question itself, and the service never changes.

What that is worth, measured. 200 notifications, 60 of them permanently broken, up to 4 attempts each:

Attempts usedTime spent waiting
retry everything the same way52056,000 ms
ask the exception first34014,000 ms

180 wasted attempts and 42 seconds of waiting, removed by one abstract method. And the waiting is the worse half, because a notification stuck in a backoff loop is holding a slot that real work needs.

Checked or unchecked. This one gets argued about, so have a position. NotificationException is checked here, deliberately. Sending over a network fails routinely, that is not exceptional, and every caller genuinely has to decide what to do about it. Making it checked means the compiler will not let anyone forget.

The counter-argument is real and worth naming: checked exceptions spread through signatures and people wrap them in RuntimeException to make the compiler stop complaining, which is worse than not checking at all. The line to use is: checked when the caller can reasonably do something about it, unchecked when it means the program is broken. A provider being busy is the first. A null recipient is the second, which is why the record throws IllegalArgumentException and not a checked exception.

The queue is bounded, and that is a decision, not a detail.

service/NotificationService.javathe honest answer
public boolean submit(Notification n) {
    ...
    boolean accepted = queue.offer(new Job(n, 1));   // returns false when full
    if (!accepted) {
        rejected.incrementAndGet();
        System.out.println("    REJECTED " + n.id() + ", queue is full");
    }
    return accepted;
}

An unbounded queue does not remove the problem, it hides it until the process runs out of memory, and then everything is lost at once instead of the newest thing being refused. Returning false pushes the decision to the caller, who is the only one who knows whether this notification is an OTP worth waiting for or a marketing email worth dropping.

And the number is not stable, which is the point. Capacity 10, three workers, 40 submitted at once, four runs:

four runs of the same programreal output
run 1    accepted 31, rejected 9
run 2    accepted 27, rejected 13
run 3    accepted 29, rejected 11
run 4    accepted 26, rejected 14

stable across every run: 4 retries, 1 dead lettered

How many get rejected depends on how fast three workers drain the queue against how fast the caller fills it. You cannot reason your way to that number. Saying so in an interview is a strong answer: you measure it, then you choose the capacity from what you measured.

Common wrong answers

An unbounded queue. "It will never fill up" is a memory leak with a schedule. The failure moves from one rejected message to the whole process dying.

Blocking in submit until there is room. Tempting, and it turns a full queue into a stuck caller. Whatever thread called you is now waiting, and if that is a web request thread you have just spread the problem to the front door.

One exception class with a string message. Then the retry logic has to read the message text to decide what to do, which is exactly as fragile as it sounds.

Follow-up questions

Why does the retry not just sleep on the worker thread?

Because sleeping burns a worker for the whole delay, and the delay doubles each time.

With three workers and a backoff of 50, 100 and 200 milliseconds, three notifications failing at once would put every worker to sleep. Nothing else moves for the length of the longest delay, even though there might be a hundred perfectly healthy notifications waiting. At real backoffs, which are seconds, the whole service stops for one bad provider.

What this design does instead is put the job back on the queue later:

retryClock.schedule(() -> queue.offer(new Job(n, attempt + 1)), delay, MILLISECONDS);

One scheduler thread holds all the pending retries, and it is asleep almost all the time because it is only waiting on timers. The three workers go straight back to the queue and pick up the next thing. The cost is one extra class and one more thing to shut down, which is a good trade.

Say the simple version out loud first though. "The three line version sleeps on the worker. That works and it wastes a thread per retry, so I will re-queue with a delay instead." Showing you know the cheap option and rejected it on purpose is better than arriving at the good one with no explanation.

What happens to the queue when the process restarts?

Everything in it is lost. Say this before they ask, because it is the biggest hole in the design and an interviewer who finds it themselves scores it differently from one who hears you name it.

An ArrayBlockingQueue is memory in one process. A restart, a crash, or a deploy takes every queued and every scheduled retry with it. For a marketing email that is acceptable. For a one time password or a payment receipt it is not.

The fix is that the queue becomes something outside the process. A database table with rows in a "pending" state, or Redis, or a real message broker. Workers claim a row, mark it, and delete it when it is done. Anything left claimed but not finished after a timeout gets picked up again, which is how you survive a worker dying mid send.

The part worth saying next is why this design makes that change small. Nothing outside NotificationService knows a queue exists. Callers call submit, listeners hear about outcomes. Swapping the queue changes one class. That is the payoff for keeping the queue private, and it is worth pointing at.

And name the new problem it creates, because there always is one: once work survives restarts, the same notification can be delivered twice, once by the worker that died after sending and once by whoever picks the row back up. That is the idempotency problem, and it is why the key is on the record from the start.

How do you make this thread safe? Walk through what is shared.

Go through the shared state one item at a time. That is the answer they want, not the word "synchronized".

The notification itself is a record with final fields, so several threads can read it at once with nothing to protect. This is why the choice of a record earlier pays off here.

The queue is an ArrayBlockingQueue, which is built for exactly this: many producers, many consumers, all the locking inside. Writing your own with wait and notify in an interview is a way to introduce a bug in front of an audience.

The counters are AtomicInteger. A plain int++ is three operations, so two workers finishing at the same moment can lose a count. Atomics make the increment one indivisible step without any locking.

The idempotency map is a ConcurrentHashMap, and the important detail is putIfAbsent rather than a "check then put". Two threads can both find a key missing and both proceed; putIfAbsent makes the check and the write one step, so exactly one of them wins.

The listener list is copied once at construction with List.copyOf and never changed, so iterating it from several workers is safe with no locking at all. Immutability is doing the work again.

The running flag is volatile, so when shutdown sets it to false the worker threads actually see it rather than reading a stale cached copy forever.

Why three workers? How would you pick the number?

Three is a demo number and you should say so rather than defend it.

The real answer depends on what the work is doing. Sending a notification is almost all waiting on a network call, so the threads are idle most of the time. That means you want many more threads than processors, because they are not competing for the processor at all. A rough starting point for work that is mostly waiting is processors divided by one minus the fraction of time spent waiting, which for work that waits 90 percent of the time and 8 processors lands around 80 threads.

But the honest version is that you do not pick it from a formula, you pick a starting number, measure how long the queue is and how long notifications sit in it, and adjust. The formula tells you the order of magnitude, not the answer.

Two things constrain it from above regardless. The provider almost certainly rate limits you, so 500 threads will just produce 500 rejections faster. And every platform thread costs about a megabyte of stack, so a few thousand is a real memory decision.

If the interviewer wants to go further, the modern answer is that this is exactly the workload virtual threads exist for, since they are cheap and blocking on a network call does not tie up a platform thread. Naming that is a good place to end.

04 Rate limiting

  • Name three rate limiting algorithms and the flaw in the cheapest one.
  • A fixed window let 20 requests through when the limit was 10. How?
  • A token bucket also let 20 through. Why is that not the same problem?
  • How would you rate limit per client rather than globally?

The question. "The SMS provider charges per message and cuts us off above 10 a second. Add a rate limit." This is the most common follow-up in the round, and the interesting part is not writing one, it is knowing what each one lets through.

All three were given exactly the same requests, with a clock the test moves forward rather than the real one, so the results are about the algorithm and not about how the machine felt.

three limiters, limit 10 per secondclick any cell
steady 5/s
burst on a boundary
quiet then 30
worst ever
fixed window
sliding log
token bucket

Pick a cell above.

The result worth understanding. On the boundary test, the fixed window and the token bucket let through exactly the same 20 requests against a limit of 10. If you stopped there you would conclude they are equally bad. They are not, and the difference only shows up when you slide the same burst across every millisecond of the window:

the same burst, every possible offsetreal output
limiter                   best case     worst case
fixed window                     10             20   depends on timing
sliding window log               10             10   same every time
token bucket 20/10               20             20   same every time

The token bucket lets 20 through every single time, because 20 is the capacity somebody chose. The fixed window lets 20 through only when the traffic happens to land on a boundary. One is a dial you set. The other is luck.

That is the sentence to say in an interview, and it is much better than "fixed window is bad" because it is the actual difference. A limiter that is predictably generous is fine. A limiter whose behaviour depends on where the second happened to start is not, because you cannot test it and you cannot promise anything about it.

Why the fixed window does it. It counts inside blocks of time and throws the count away at every block boundary. Ten requests at 950 milliseconds fill block zero. At 1000 the count resets, so ten more go straight through. Twenty requests in 60 milliseconds, and every single one was allowed by a limiter set to 10 per second.

LimiterMemory per clientWorst caseWhen to pick it
fixed windowtwo numberstwice the limit, unpredictably When the limit is a rough guard and going over briefly costs nothing
sliding window logone timestamp per allowed request exactly the limit When the limit is a hard contract and you can afford the memory
token buckettwo numbersthe capacity, every time Almost always. Cheap, predictable, and the burst is a feature you control

Per client, not global. Every one of these keeps its state in a map keyed by client, which is why allow takes the client as an argument. A global limiter means one noisy customer starves everyone else. The thing to mention is that the map grows forever unless entries for clients who have gone quiet are removed, which is a real leak and an easy one to say out loud.

Common wrong answers

"Fixed window is fine, it is simpler." It is simpler, and it can let through twice the limit at a moment you do not control. Say the number.

"Token bucket never goes over the limit." It went over on two of the three tests here. It goes up to its capacity, on purpose. Claiming otherwise means you have not run one.

Sleeping the caller until it is allowed. That is not rate limiting, it is queueing with extra steps, and it turns a fast rejection into a stuck thread.

Follow-up questions

How do you make the rate limiter work across several machines?

The moment there are two instances, a limiter held in memory means each one allows the full limit, so the real limit is the number of machines times what you configured. Ten a second across four instances is forty a second at the provider.

The usual answer is to move the counter to something shared, normally Redis, because it is fast and its operations are atomic. A token bucket becomes a small script that reads the tokens and the last refill time, works out the new balance, and writes it back in one indivisible step. Doing that as separate read and write invites two machines to both see the same token.

Then name the costs, because this is where the good answers separate. Every request now makes a network call before doing any work, so the limiter is on the critical path. If Redis is slow, everything is slow. If Redis is down, you have to decide in advance whether to allow everything or block everything, and both choices are defensible for different products: allow for a marketing email, block for anything that costs money per send.

The cheap approximation worth mentioning is dividing the limit by the number of instances and keeping it in memory. It is wrong whenever traffic is uneven or an instance restarts, and it costs nothing, which is the right trade for a limit that is a guard rather than a contract.

What should happen to a notification that gets rate limited?

Not dropped, and not retried immediately. It should go back on the queue with a delay, and the delay should be how long until a token is available rather than a guess.

This is different from a failed send. A send that failed might never work, which is why the exception carries worthRetrying. A rate limited send is known to be fine and simply too early, so it deserves its own handling: no attempt counter increase, no progress towards the dead letter queue, just a wait.

That distinction is worth making out loud, because the sloppy version treats being rate limited as a failure, and then a busy hour quietly pushes perfectly good notifications into the dead letter queue after three attempts. That is a genuinely bad bug and it is entirely caused by putting two different things in the same box.

The token bucket makes the delay easy to compute, which is another point in its favour: you know the refill rate, so you know exactly how many milliseconds until the next token. A fixed window can only tell you when the block ends, which is why everything piles up at the boundary and causes the burst in the first place.

The sliding window log stores every timestamp. Is that a problem?

Yes, and it is the reason it is rarely the production answer despite being the only exact one.

The memory is one timestamp per allowed request per client, held for a full window. At 10 a second that is 10 longs per client, which is nothing. At 10,000 a second across 50,000 clients it is hundreds of millions of timestamps, and it is all live objects the garbage collector has to walk.

The middle option, and the one worth naming because it shows you know the space, is the sliding window counter. Keep only two numbers, the count in the current block and the count in the previous one, and estimate by weighting the previous block by how far into the current one you are. If you are 30 percent into this block, count 70 percent of the last one plus all of this one. Two numbers per client, and the boundary problem mostly disappears.

It is an approximation, and it can be slightly wrong when traffic is very uneven inside a block. In exchange it costs the same memory as the fixed window. That trade is why it is what a lot of real systems actually run.

Different clients need different limits. How does that fit?

The limit stops being a constant and becomes something looked up per client, which changes the interface slightly and the algorithm not at all.

In our code the limit is a field on the limiter. Make it a lookup instead: the limiter is given something that answers "what is the limit for this client", and it asks each time it creates state for a new one. A free account gets 10 a second, a paying one gets 1,000, and the algorithm is identical.

The token bucket handles this better than the others because it has two dials rather than one, and they can be set independently per tier. A free client might get capacity 10 and rate 10, so no bursting at all. A paying client might get capacity 200 and rate 100, so they can send a batch at the top of the hour and still be held to 100 a second on average. Expressing "you may burst this much and sustain that much" in two numbers is exactly what the algorithm is for.

The detail worth mentioning: when someone upgrades, their existing bucket has the old capacity. Either refresh the entry on a plan change or accept that the new limit applies from the next window, and saying which you chose is better than not noticing.

05 Retrying without making it worse

  • 500 clients all fail at the same moment. What does plain exponential backoff do?
  • What is jitter and what did it actually change?
  • When does something go to the dead letter queue?
  • What do you do with the dead letter queue afterwards?

Everyone knows to use exponential backoff. Wait 100 milliseconds, then 200, then 400. It stops one client hammering a provider that is already struggling.

It does nothing at all for the case that actually takes systems down. When a provider goes down, it does not fail for one client, it fails for all of them at the same moment. Doubling the wait moves the whole crowd together. Here is what that looks like with 500 clients, three retries each:

RetryAndDlq.javareal output
                              retries   10 ms slices      worst slice
no jitter, plain backoff         1500              3              500
with jitter                      1500             66              78

Without jitter, all 1,500 retries landed in three ten millisecond slices. The provider that just fell over gets hit by all 500 clients at once, recovers slightly, and is hit by all 500 again 200 milliseconds later. Backoff spread the retries out in time and did nothing to spread them across each other.

Jitter is one line. Instead of waiting exactly the backoff, wait a random amount up to it:

long wait = jitter ? (long) (rnd.nextDouble() * backoff) : backoff;

That took the worst slice from 500 down to 78, about 6.4 times lower, and spread the same 1,500 retries across 66 slices instead of 3. Same number of retries, same backoff, one multiplication.

What each part of the retry design buysmeasured

Pick a part of the design.

The dead letter queue is where you put what you have given up on. Two things land there, and keeping them apart matters:

  • Permanent failures, after one attempt. The address is malformed. Retrying is pure waste.
  • Temporary failures that ran out of attempts. The provider was down for the whole of the retry window. This one might well succeed if sent again in an hour.

The entry stores the reason and the attempt count, so the two are distinguishable later. In the real run the dead letter queue held one item: the malformed email address, after a single attempt, with the reason recorded.

A dead letter queue nobody reads is just a slower way of dropping things. Say what happens to it: someone gets alerted when it grows, the permanent ones become a report for whoever owns the bad data, and the temporary ones can be replayed once the provider is back. Replaying is only safe because every notification carries an idempotency key.

Common wrong answers

"Exponential backoff, done." Correct and incomplete. Without jitter it is synchronised backoff, and the measurement above shows what that means.

Retrying forever. Without a cap, one permanently broken notification retries until the process dies, and it holds a queue slot the whole time.

Retrying everything the same way. 520 attempts against 340 for the same work, and 56 seconds of waiting against 14.

Follow-up questions

How much jitter? Is random up to the backoff the right amount?

What the demo uses is called full jitter: wait a random amount anywhere between zero and the full backoff. It is the simplest and it spreads the load best, which is why it is the default worth knowing.

The objection people raise is that a random draw near zero means retrying almost immediately, which feels like it defeats the backoff. In practice it is fine, because only a small fraction of clients draw a small number and the point is the shape of the crowd, not any one client.

If that still bothers you, the variant is equal jitter: wait half the backoff plus a random amount up to the other half. Every client waits at least half, and the spread is half as wide. It trades some smoothing for a guaranteed minimum wait, and both are defensible. Amazon published measurements comparing these and full jitter came out best on total work done, which is a good thing to be able to attribute.

The version to avoid is adding a small fixed random amount, say the backoff plus up to 10 milliseconds. With 500 clients that spreads them over 10 milliseconds, which is still one crowd. The jitter has to be on the same scale as the backoff to do anything.

How many attempts, and how do you choose?

Work backwards from how long you are willing for the whole thing to take, because that is the number the business actually cares about.

With a base of 100 milliseconds and doubling, the waits are 100, 200, 400, 800. Four retries is 1.5 seconds of waiting. Ten retries is nearly two minutes, and the last few waits are longer than most people's patience. So the question "how many retries" is really "how long may this take", and three or four is common because the total stays in seconds.

Then let the type of notification decide. A one time password is worthless after 60 seconds, so a long retry chain is not just useless, it is harmful: it delivers something the user has already given up on. A payment receipt can retry for an hour because it is still useful late. That argues for the attempt cap being a property of the notification rather than one number for the whole service, which is a good thing to offer.

One more thing worth saying: attempts and total time are different limits and having both is reasonable. Stop after 4 attempts or 30 seconds, whichever comes first. The time limit is the one that protects you when someone sets a large base delay without thinking it through.

A worker dies halfway through sending. What happens?

In this design the notification is lost, and it is worth saying so plainly.

The job was taken off the queue by that worker. It is not on the queue any more and it was never written down anywhere else, so when the thread dies the job goes with it. Nothing retries it because nothing knows it existed.

The fix is that taking work off the queue and finishing it have to be separate steps. A worker claims the job, marks it as claimed with a timestamp and its own name, and only removes it once the send has succeeded. Anything still claimed after a timeout is assumed abandoned and becomes available again. This is what real queues do for you, and it is why "just use a real queue" is a reasonable answer once the requirement is that nothing may be lost.

Then name the problem that creates, because it is unavoidable and interviewers like to hear it: if the worker died after the provider accepted the message but before it could mark the job done, the replacement worker will send it again. You cannot design that window away, only make the duplicate harmless, which is what the idempotency key is for. This is the difference between at least once delivery, which you can have, and exactly once, which you cannot.

Should a failing provider be cut off entirely rather than retried?

Yes, once the failures stop being individual and start being everything, and the name for that is a circuit breaker. It is a natural thing to raise here and it scores well because it shows you are thinking about the provider and not only about your own code.

The idea: count recent failures for a provider. Above a threshold, stop calling it entirely for a cooling off period and fail immediately instead. After the period, let one request through as a test. If it works, resume. If it does not, wait again.

Two things this buys. The provider gets a real break instead of being poked by every retry, which is often what it needs to recover. And your own service stops spending workers and queue slots on calls that are all going to fail, so a healthy channel keeps moving while a sick one is parked.

The trade to admit is that a circuit breaker fails requests that might have worked, because it stops asking. And it needs tuning, since a threshold that is too low trips on normal noise and one that is too high never trips at all. In the round, describing it is the right level of detail. Writing one is usually a poor use of the remaining minutes unless they ask.

06 Idempotency and the last ten minutes

  • What is an idempotency key and what problem does it actually solve?
  • Why can you not have exactly once delivery?
  • What should you say in the last five minutes of the round?
  • Name three things wrong with this design.

Why duplicates happen at all. Not because anyone wrote a bug. A caller sends a request, the network drops the response, and the caller has no way to tell whether the notification was sent or not. So it sends again. That is the correct thing for the caller to do, and it means your service will receive the same request twice.

The fix is a key the caller supplies. Not one you generate, because a key you generate is different on the second request and defeats the whole idea:

service/NotificationService.javathe whole feature
String key = n.idempotencyKey();
if (key != null && alreadyHandled.putIfAbsent(key, n.id()) != null) {
    duplicatesIgnored.incrementAndGet();
    return true;                // already dealt with, and that is a success
}

Real output, the same payment notification submitted twice with the key pay-9912:

service/Main.javareal output
[email] delivered to ravi@example.com
ignored duplicate of N-7, key pay-9912

duplicates ignored: 1

Two details in that one line matter. It uses putIfAbsent rather than checking and then putting, because two threads can both find a key missing and both proceed; putIfAbsent makes the check and the write one indivisible step so exactly one wins. And it returns true, not an error. From the caller's point of view the notification has been dealt with, which is exactly what they wanted to know.

Where the key comes from. Something the caller already has that identifies the real world event: the order id, the payment id, the attempt id. "Order 9912 payment received" is one event no matter how many times the request arrives. A timestamp or a random value is not a key, it is a new event every time.

Exactly once delivery does not exist, and saying so is a strong answer. There is always a moment where the provider has accepted the message and your process has not yet recorded that fact. If it dies in that window, either you resend, which is a duplicate, or you do not, which is a loss. You cannot remove the window, only choose which side to fall on. The usual choice is deliver at least once and make duplicates harmless, which is exactly what the key is doing.

The last five minutes

Do not spend them typing. Spend them naming what is wrong with what you built, and be specific enough that it is clear you knew while you were writing it.

What to say about this design. Three real holes, each with the fix in one sentence:

What is wrongWhat it costsWhat you would do
The queue is in memory A restart loses everything queued and every pending retry Move it to a database table or a real queue. Only NotificationService changes, because nothing else knows a queue exists.
The idempotency map grows forever A memory leak with a slow fuse, and it does not survive a restart either Give keys an expiry, hours rather than days, and move the map to the same store as the queue.
Nothing reads the dead letter queue Failures are stored and never seen, which is a slower way of dropping them Alert on its size, report the permanent ones to whoever owns the bad data, replay the temporary ones once the provider is healthy.

The three sentences worth having ready. These cover most of what is left:

  • "Adding a channel is one new file and one line where channels are listed. Nothing that already works gets edited."
  • "The retry decision is one method on the exception, so a new failure type answers the question itself and the service never changes."
  • "This queue is in memory, so a restart loses it. For a marketing email that is fine. For a one time password it is not, and the fix is a real queue."
Common wrong answers

"We can guarantee exactly once." You cannot, and an interviewer who knows that has just learned something about the rest of your answers.

Generating the idempotency key inside the service. The second request gets a different key, so it is a different event, so it gets sent. The feature does nothing at all and it looks like it works.

Claiming the design has no problems. Every design in a 45 minute round has problems. Not naming them reads as not seeing them.

Follow-up questions

How long should an idempotency key be kept?

Long enough to cover every retry that could still arrive, and no longer, because the store is a cost that grows with traffic.

Work it out from the callers rather than picking a round number. If a caller gives up after four retries over 30 seconds, then anything arriving more than a minute or two later is not that caller retrying, it is a genuinely new request. Twenty four hours is a common default because it comfortably covers human scale retries, someone pressing a button again, or a batch job rerunning after an overnight failure.

The cost of too long is memory or storage, growing with every request forever. The cost of too short is worse and quieter: a late retry finds no key, gets treated as new, and the customer receives the message twice. Since duplicates are the exact thing the key exists to prevent, err long.

In our code there is no expiry at all, which is a real leak. The honest thing is to name it and say what you would use: a cache with a time based eviction if it stays in memory, or a column with a timestamp and a job that deletes old rows once it moves to a database.

Should the key be per caller, or global?

Per caller, and this is a small detail that shows real care.

A global key space means two unrelated services that both use "order-1234" collide. The second one silently has its notification swallowed as a duplicate, and the failure is invisible: nothing errored, the caller got success, and no message was sent. That is close to the worst kind of bug.

The fix is to make the stored key the caller identity plus the key they gave, so "billing:order-1234" and "shipping:order-1234" are different entries. Callers keep using whatever ids they already have, with no coordination between teams.

It also fixes a security problem worth mentioning if the service is public. With a global space, anyone who can guess another caller's key can suppress their notifications by claiming it first. Scoping the key to the authenticated caller removes that entirely.

How would you test this? There are threads everywhere.

Split it, and be specific about which part gets which kind of test. "I would write unit tests" is not an answer.

The parts with no threads get ordinary tests. The rate limiters take the clock as an argument, so you can feed them a timeline and assert exactly what was allowed with no sleeping and no flakiness. That is exactly what the demo in this episode does, and it is why the clock is a parameter rather than a call to System.currentTimeMillis(). The exception classes are simpler still: assert that worthRetrying returns what it should.

The channels get a fake. A test channel that records what it was asked to send and can be told to fail on demand. Then you can test the retry path by making it fail twice and succeed on the third attempt, and assert the notification arrived after three attempts.

The service gets tests that wait for an outcome, not for a duration. Submit, then wait until the fake channel has recorded what you expect or a timeout passes. Thread.sleep(500) and then asserting is the classic flaky test: too short and it fails on a slow machine, too long and the suite crawls. A latch or a poll with a deadline is the fix, and it is what drain does in the demo.

The honest limit: none of this proves there is no race. Concurrency bugs are timing dependent and a passing test only means it did not happen this time. Saying that, and saying you would run the concurrent tests many times and under load, is better than claiming coverage you do not have.

They ask you to add a scheduled notification. Send this tomorrow at 9am.

This is a common last question, and the trap is to reach for the retry scheduler that is already there. Do not, and be able to say why.

The retry scheduler holds pending work in memory for milliseconds to seconds. A notification scheduled for tomorrow morning would sit in memory for sixteen hours, so any restart or deploy in that time loses it. Deploys happen more often than that.

The right shape is that a scheduled notification is stored, not held. It becomes a row with a "send after" timestamp. A job runs regularly, asks for everything due, and submits those to the same service the immediate ones go through. The sending path does not change at all, which is the point worth making: scheduling is a source of work, not a new kind of sending.

Two details that show you have thought past the happy path. The job must claim rows as it takes them, or two instances will both pick up the same one and send twice. And if the job has been down for a while, it will find a pile of overdue notifications at once, so it needs a limit per run or it will flood the queue you just spent ten minutes bounding.

G Word list

Every term on this page that you might not already know.

at least once delivery
A promise that a message will arrive, accepting that it may arrive more than once. The only realistic option, which is why duplicates have to be made harmless.
backoff
Waiting longer before each retry, usually doubling the wait each time, so a struggling provider is not hit at the same rate.
bounded queue
A queue with a fixed maximum size. When it is full it refuses new work instead of growing until the process runs out of memory.
circuit breaker
Stopping calls to a provider entirely once too many have failed recently, then letting one through later to test whether it has recovered.

Where a message goes once you have given up delivering it, so the failure is recorded rather than silently dropped.
fixed window
A rate limiter that counts requests inside blocks of time and resets the count at each block boundary. The cheapest one, and the one that can let twice the limit through.
idempotency key
A value the caller supplies that identifies one real world event, so the same request arriving twice is only acted on once.
jitter
Adding randomness to a retry wait so that many clients who failed together do not all retry at the same instant.
listener
An object that is told when something happened, without the thing that happened knowing who is listening. Also called an observer.

An interview round of about an hour where you build one service in code: classes, interfaces and method signatures, not boxes and arrows.

A short code sent to prove someone controls a phone or an email address. Used here as the example of a notification that is worthless if it arrives late.

A map operation that writes a value only if the key is not there yet, as one indivisible step, so two threads cannot both think they were first.

Code that decides whether a request is allowed right now, to keep within a limit you or a provider set.

A rate limiter that keeps the time of every allowed request and counts the ones inside the last window. Exact, and the most memory hungry.

A rate limiter holding tokens that refill at a steady rate. Each request spends one. Capacity and refill rate are separate dials, so a controlled burst is allowed on purpose.

A marker on a field meaning every thread reads the latest value rather than a stale cached copy.

A thread that sits in a loop taking work off a queue and doing it.
