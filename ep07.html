Seven elements out of a million

A stream is not a loop and not a collection. It is a recipe that does nothing until you ask for an answer, then pulls elements through one at a time and stops the moment it can. Everything here was measured, including the case where going parallel made things four times slower.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 The pipeline

  • What are the three parts of a stream pipeline?
  • What is the difference between an intermediate and a terminal operation?
  • Why can you not reuse a stream?
  • How is a stream different from a collection?

Every stream has exactly three parts.

  1. A source: a collection, an array, a range, a file, a generator.
  2. Zero or more intermediate operations: filter, map, sorted, distinct, limit. Each returns another stream and does nothing on its own.
  3. Exactly one terminal operation: collect, toList, forEach, count, findFirst, reduce. This is what makes anything happen.

Measured: nothing runs until you ask

A pipeline with a counter in every stage, built but not finished:

pipeline built, elements touched: 0
after toList(),  elements touched: 6

Zero. The filter and map were written, and neither ran. Adding the terminal operation ran both across three elements, which is the six.

This is the single most useful sentence about streams. An intermediate operation is a description of work, not the work. Nothing executes until a terminal operation asks for a result. A pipeline with no terminal operation is dead code that compiles.

How a stream differs from a collection

CollectionStream
Holds the elementsyesno, it reads from a source
Can be walked more than onceyesno, one pass only

Measured: a stream is used once

first  use: [a, b]
second use: IllegalStateException - stream has already been operated upon or closed

A stream carries a flag saying whether it has been consumed. Using it twice fails immediately rather than quietly giving you the wrong answer. If you need two passes, either collect to a list first, or keep a Supplier that builds a fresh stream each time.

"Streams are a replacement for loops." They are a way of describing a transformation. For a simple loop over a few items with a side effect, an ordinary for loop is clearer and faster, and using a stream there is worse code.

"A stream stores its elements." It reads them from the source as needed. Change the source before the terminal operation runs and the stream sees the change.

Follow-up questions

What happens if you change the source while a stream is open?

Usually you get an exception, and the reason is worth knowing because it connects to how streams read their source.

Because a stream does not copy the elements, it reads from the collection when the terminal operation runs. Most collections detect being changed during that read and throw ConcurrentModificationException, the same mechanism as changing a list while looping over it.

The confusing part is when it happens. Building the pipeline is fine, changing the list is fine, and the failure appears at the terminal operation, which may be lines away from the change. Nothing is wrong with the line that throws.

There is one legitimate case: changing the source between building the pipeline and running the terminal operation is allowed and the stream simply sees the newer contents. It is legal and almost always a bug waiting to happen, because the code reads as though the stream was fixed at the moment it was written.

The habit that avoids all of it: build and finish the pipeline in one expression, and do not hold a stream in a variable.

Which operations are intermediate and which are terminal?

The reliable test is the return type rather than memorising lists. If it returns a stream, it is intermediate. If it returns anything else, it is terminal.

Intermediate: filter, map, flatMap, distinct, sorted, peek, limit, skip, takeWhile, dropWhile. All return a stream, all do nothing until asked.

Terminal: collect, toList, forEach, count, reduce, min, max, findFirst, findAny, anyMatch, allMatch, noneMatch, toArray. All return a value, a collection, an Optional, or nothing.

Two worth calling out. peek is intermediate and exists for looking, not for doing: because it is intermediate it may not run at all if nothing downstream needs that element, so using it for real side effects gives you results that depend on what the terminal operation happens to require. sorted is intermediate but cannot stream one element at a time, because it has to see everything before it can emit anything, which is covered in the next chapter.

02 Lazy, and stopping early

  • Do elements go through the pipeline one at a time or stage by stage?
  • What is short-circuiting, and which operations do it?
  • Which operations have to see everything before they can emit anything?
  • Why can you have an endless stream?

The intuition most people start with is that filter runs over the whole list, then map runs over what survived. That is not what happens.

Measured: the order the stages actually run

filter ann
  map ann
filter bob
  map bob
filter cat
  map cat

Each element goes all the way through the pipeline before the next one starts. There is no intermediate list between the stages, which is why a long pipeline does not allocate a collection per stage.

Watch it happen

Six numbers through a filter and a map. Step through and watch a single element travel down before the next one begins. Then switch the ending from toList to findFirst and watch it stop.

source
filter ran 0
map ran 0
result []
Press Next step. Watch one element go all the way down before the next starts.

Measured: how much of a million gets looked at

findFirst() gave 14
filter ran 7 times, map ran 1 time, out of 1,000,000

count() gave 142,857 and had to look at 1,000,000 elements

Seven out of a million. findFirst asked for elements until it had an answer and then stopped. The first multiple of seven is seven, so the filter ran seven times and the map ran once. That is short-circuiting, and it is only possible because nothing runs eagerly.

count cannot stop early here, because it has to test every element to know how many pass.

Which operations stop early

  • Stop as soon as they can: findFirst, findAny, anyMatch, allMatch, noneMatch, limit, takeWhile.
  • Must see everything: count when there is a filter, collect, forEach, reduce, min, max.

Note that allMatch stops at the first element that fails, and noneMatch at the first that passes. Both stop on the answer that settles the question.

Operations that have to buffer

sorted and distinct break the one at a time flow, and knowing this explains a lot of surprising behaviour.

sorted cannot emit anything until it has seen every element, because the smallest might be last. So a pipeline with sorted in it pulls everything through the earlier stages first, then sorts, then continues. Putting filter before sorted rather than after can therefore change the work enormously.

Why endless streams work

Stream.iterate(1, n -> n + 1)      // no end
      .filter(n -> n % 7 == 0)
      .limit(5)                    // now it has one
      .toList();

This finishes because nothing is produced until asked. The source generates a value only when the pipeline pulls one, and limit stops pulling after five. Written eagerly this could never terminate.

"filter runs over everything, then map runs over the rest." Measured false. Each element goes through every stage before the next one starts.

"peek is for debugging so it always runs." It is an intermediate operation, so it runs only for elements the terminal operation actually pulls. With findFirst on a million elements, a peek would print seven lines.

Follow-up questions

Does the order of filter and map matter?

Yes, and it is one of the few stream optimisations worth doing by hand.

Put filter first when you can. Every element that the filter removes is one the map never has to transform. Mapping first means doing the expensive work on elements you are about to throw away.

// maps a million, keeps a few
list.stream().map(this::expensive).filter(x -> x.isValid())

// filters a million cheaply, maps only what survives
list.stream().filter(x -> x.isValid()).map(this::expensive)

The compiler will not reorder these for you, because map can have side effects and changes the type, so swapping them is not always safe. You have to do it.

The much larger version of the same point is sorted. Sorting has to see everything, so filtering before it means sorting a smaller set. Filtering after means sorting elements you then discard. With a million elements and a filter that keeps a hundred, that is the difference between sorting a hundred things and sorting a million.

What is the difference between findFirst and findAny?

findFirst promises the first element in the stream's order. findAny promises only that it is some element that matched.

On a sequential stream they behave identically, because there is only one obvious element to return, and findAny gives you the first anyway.

The difference appears when you go parallel. findFirst has to work out which match came earliest in the original order, which means coordination between threads and possibly waiting for a thread working on earlier elements. findAny can return whatever any thread found first and stop everything immediately, which is genuinely faster.

So the rule: use findAny when you truly do not care which one, and findFirst when order is part of the answer. Choosing findFirst out of habit in a parallel stream quietly costs you the thing you went parallel for.

The same distinction shows up in forEach against forEachOrdered, for the same reason.

03 Collectors

  • What does groupingBy return, and how do you change the values?
  • What is the difference between groupingBy and partitioningBy?
  • What happens if toMap gets a duplicate key?
  • What is teeing for?

collect takes a recipe for building a container. The useful part is that recipes nest: a collector can take another collector to describe what happens to each group.

Measured output, from real data

Five people with a department and a salary:

groupingBy(dept)                 = 3 groups, keys [hr, sales, eng]
groupingBy + counting            = {hr=1, sales=2, eng=2}
groupingBy + mapping(name)       = {hr=[Eve], sales=[Cat, Dan], eng=[Ann, Bob]}
partitioningBy(salary >= 100)    = {false=[Cat, Dan, Eve], true=[Ann, Bob]}
toMap with a merge function      = {hr=80, sales=95, eng=120}
joining with prefix and suffix   = [Ann, Bob, Cat, Dan, Eve]
teeing(count, average)           = 5 people, average 97.0

The nesting is the point

// the default: values are Lists of the whole object
Map<String, List<Person>> byDept =
    people.stream().collect(groupingBy(Person::dept));

// second argument says what to do with each group instead
Map<String, Long> countByDept =
    people.stream().collect(groupingBy(Person::dept, counting()));

Map<String, List<String>> namesByDept =
    people.stream().collect(groupingBy(Person::dept,
                            mapping(Person::name, toList())));

That second argument is called the downstream collector, and it is what turns groupingBy from one trick into the answer to most grouping questions in an interview.

groupingBy against partitioningBy

They look similar and differ in one guarantee that catches people:

partitioningBy, where nobody matches:
{false=[Ann, Bob, Cat, Dan, Eve], true=[]}

partitioningBy always returns both keys, even when one side is empty. groupingBy simply has no entry for a group with no members. So with partitioning you can safely call get(true) and get an empty list; with grouping you get null.

Also: partitioning takes a condition and always gives exactly two groups. Grouping takes a function and gives as many groups as there are distinct results.

The toMap trap

// throws IllegalStateException the moment two people share a department
people.stream().collect(toMap(Person::dept, Person::salary));

// third argument says what to do about it
people.stream().collect(toMap(Person::dept, Person::salary, Math::max));

The two argument version has no way to combine values, so a duplicate key is an error. Real data has duplicate keys far more often than people expect, so the three argument version is usually what you want.

"toMap is the simple one." It is the one most likely to throw in production. Anything grouped by a non unique field needs the merge function.

"groupingBy gives me a count." It gives you lists. You get counts by adding counting() as the downstream collector.

Follow-up questions

What is teeing for?

Running two collectors over the same stream in a single pass and combining their results.

Without it, getting a count and an average means either two passes over the data, which needs collecting to a list first because a stream is single use, or writing a custom collector.

String summary = people.stream().collect(teeing(
        counting(),
        averagingInt(Person::salary),
        (count, avg) -> count + " people, average " + avg));
// 5 people, average 97.0

The three arguments are: the first collector, the second collector, and a function that takes both results and produces the final answer. Every element is fed to both collectors as it passes.

Where it genuinely earns its place is when the source is expensive or endless, so a second pass is not available. For an ordinary in memory list, collecting once and calling two methods is often clearer, and saying that shows judgement rather than just knowing the method exists.

Worth knowing it arrived in Java 12, so it is not part of the original Java 8 set that most stream questions are about.

How do you keep the order of a grouped result?

groupingBy returns a HashMap by default, so the keys come out in whatever order hashing produces. In the measured output above the keys came back as hr, sales, eng, which is neither insertion nor alphabetical order.

The fix is the three argument form, where the middle argument supplies the map:

// keys in the order first encountered
groupingBy(Person::dept, LinkedHashMap::new, toList())

// keys sorted
groupingBy(Person::dept, TreeMap::new, toList())

Note the argument order is map factory in the middle and downstream collector last, which is easy to get backwards.

The same applies to toMap, which takes the map factory as a fourth argument after the merge function.

A related gotcha: the values within each group keep the stream's encounter order, because they are collected into a list. So the values are ordered even when the keys are not, which is why this bug often goes unnoticed until someone displays the groups to a user.

04 reduce against collect

  • What is the difference between reduce and collect?
  • Why is building a String with reduce slow?
  • What are the three arguments to reduce?

reduce combines values by producing a new value each step. collect pours values into a container that is changed as it goes.

For numbers there is no practical difference. For anything you build up, the difference is enormous.

Measured: joining strings

ItemsreducecollectRatio
1,0000 ms0 ms4x
5,00011 ms0 ms58x
20,000115 ms0 ms322x
50,000626 ms1 ms510x

Look at the reduce column growing: 0, 11, 115, 626. Doubling and a half the items multiplies the time by far more than that. The work grows with the square of the item count.

Why. Strings cannot be changed once created. reduce("", (a, b) -> a + b) makes a brand new String at every step, copying everything accumulated so far. Joining 50,000 words means copying an ever growing string 50,000 times.

Collectors.joining() appends into one buffer that grows as needed, so each word is copied once.

The rule

Use reduce when combining produces a new value and that is cheap: adding numbers, taking a maximum, combining booleans.

Use collect when you are building something up: a String, a list, a map, anything with a container.

The three arguments to reduce

// 1. no starting value: might be nothing, so you get an Optional
Optional<Integer> total = nums.stream().reduce(Integer::sum);

// 2. with a starting value: always an answer
int total = nums.stream().reduce(0, Integer::sum);

// 3. with a combiner, for parallel streams where partial results must merge
int totalLength = words.stream()
    .reduce(0, (sum, w) -> sum + w.length(), Integer::sum);

The third argument exists because in a parallel stream each thread produces a partial result and something has to combine them. It is ignored on a sequential stream, which is why a wrong combiner can pass every test and then break the day someone adds .parallel().

"reduce and collect are two ways to write the same thing." Measured 510 times apart on the same task at 50,000 items.

"The starting value is just a default." With a parallel stream the starting value is used by each thread, so a non neutral starting value like 10 gets added once per thread rather than once overall.

Follow-up questions

What makes a reduce safe to run in parallel?

Three properties, and they are the actual answer to "why did my parallel reduce give a different number".

The starting value must be neutral. Combining it with anything must give that thing back: 0 for addition, 1 for multiplication, an empty string for joining. In a parallel stream each thread starts from it, so a starting value of 10 on four threads adds 40, not 10.

The operation must be associative. Grouping must not matter, so that (a op b) op c equals a op (b op c). Addition and maximum qualify. Subtraction and division do not, which is why a parallel subtracting reduce gives a different answer every run.

It must not depend on outside state. The function should use only its two arguments. Anything reading or writing a variable outside is a race, and it will usually appear to work in testing because sequential streams hide it.

The reason this bites so often: none of these are checked, and a sequential stream satisfies all of them by accident. The code is correct until somebody adds one word.

05 Parallel streams

  • When does going parallel actually help?
  • When does it make things slower?
  • Which pool do parallel streams use, and why does that matter?
  • Why is the source data structure relevant?

Adding .parallel() is one word, which is exactly the problem: it is far too easy to add somewhere it does not belong.

Measured, on a machine with 12 processors

WorkSequentialParallelVerdict
1,000 items, add them up24 us96 us4.0x SLOWER
2,000,000 items, add them up3,905 us1,064 us3.7x faster
20,000 items, real work on each26,277 us3,106 us8.5x faster
20,000 in a LinkedList, real work27,080 us3,478 us7.8x faster
1,000,000 in an ArrayList, add up2,758 us670 us4.1x faster
1,000,000 in a LinkedList, add up2,884 us3,186 usno gain at all

Three separate lessons in that table.

Row one: small collections lose. A thousand additions is so cheap that splitting the work, handing it to threads and merging the results costs four times more than just doing it.

Rows four and six: the source structure matters, but only sometimes. A LinkedList cannot be split cheaply, because finding the middle means walking to it. With expensive work per element that barely matters, and parallel still won 7.8 times. With cheap work the splitting cost is the whole cost, and parallel gained nothing while an ArrayList of the same size gained 4.1 times.

Rows two and three: the more work per element, the better it goes. Trivial work on two million items gave 3.7 times. Real work on twenty thousand gave 8.5 times, closer to the twelve processors available.

The thing to check before going parallel at all

2,000,000 boxed Integers       5,394 us
2,000,000 primitive ints         520 us   10.4x faster

Using a primitive stream beat going parallel in every row of the table above. A Stream<Integer> unwraps and rewraps a value at every step. An IntStream does not. So before reaching for .parallel(), check whether you are streaming boxed numbers, because that fix is free, keeps the code sequential, and here was worth more than twelve processors.

The pool nobody mentions

Parallel streams do not create threads. They use one pool shared by the whole application, sized to your processor count. Every parallel stream anywhere in your code, including in libraries, uses the same one.

So a slow parallel stream in one place delays parallel streams everywhere else. And anything that blocks inside a parallel stream, a network call or a database query, occupies a thread in that shared pool while doing nothing, which can starve the whole application.

The rule. Parallel streams are for work that keeps the processor busy, over a large amount of data, from a source that splits cheaply. Never put a blocking call inside one.

"parallel() makes it faster." Measured four times slower on a thousand items, and no better at all on a million in a LinkedList.

"It uses more threads so it scales." It uses one shared pool sized to your processors. Two parallel streams at once do not each get twelve threads, they share.

Follow-up questions

Why does the source data structure matter so much?

Because parallelism starts by splitting the data, and how cheaply that can be done depends entirely on the structure.

An ArrayList or an array knows its size and can be split by arithmetic: the middle is at index size over two, and both halves can be handed out immediately. That is why it parallelises well.

A LinkedList knows only where the first element is. Finding the middle means walking half the list, and each half has to be split the same way. The splitting itself is work proportional to the data.

The measurement shows exactly when that matters. With real work on each element, the splitting cost was small next to the work, and parallel still won 7.8 times. With cheap work, splitting was the cost: an ArrayList of a million gained 4.1 times, and a LinkedList of the same size gained nothing.

Worth naming the others: HashSet and HashMap split reasonably, Stream.iterate splits badly because it must produce values in order, and IntStream.range splits perfectly because it is only arithmetic.

How would you decide whether to use a parallel stream?

Answer it as a sequence of checks rather than a rule, because that is how it is actually decided.

Is there enough data? Thousands at least. Measured, a thousand items were four times slower in parallel.

Is there enough work per element? Trivial work gave 3.7 times on two million items; real work gave 8.5 times on twenty thousand.

Does the source split cheaply? Array backed or a numeric range, yes. Linked structures, often not worth it.

Does anything in the pipeline block? If yes, stop. That occupies the shared pool and affects the whole application.

Have you already removed the boxing? Measured, that was worth 10.4 times on its own and costs nothing.

Then measure it on your own data, because every row in the table above would have been a plausible guess and half of them would have been wrong.

The honest summary worth saying out loud: parallel streams are a narrow tool. Most code that calls .parallel() in a real service should not.

06 Optional

  • What is Optional actually for?
  • Why is calling get() discouraged?
  • Where should Optional not be used?
  • Difference between orElse and orElseGet?

Optional exists to make "there might be no answer" part of the method signature instead of a surprise at runtime.

A method returning User that sometimes returns null is lying to whoever calls it. A method returning Optional<User> tells the truth, and the compiler makes the caller acknowledge it.

Using it properly

// what people write first: the same null check with extra ceremony
Optional<User> u = find(id);
if (u.isPresent()) { send(u.get().email()); }

// what it is for
find(id).map(User::email).ifPresent(this::send);

// with a fallback
String email = find(id).map(User::email).orElse("unknown");

// or fail clearly
User user = find(id).orElseThrow(() -> new UserNotFound(id));

If your code has isPresent followed by get, you have written a null check with more typing. The value is in map, filter, ifPresent, orElse and orElseThrow.

orElse against orElseGet

// the argument is evaluated ALWAYS, even when the value is present
config.get(key).orElse(loadDefaultFromDisk());

// the function runs ONLY when the value is absent
config.get(key).orElseGet(() -> loadDefaultFromDisk());

This is the most common real bug with Optional. orElse takes a value, so whatever produces that value runs regardless. If it is a constant, that is fine. If it hits a disk, a database or throws, you are doing that work on every call including the ones that did not need it.

Where not to use it

  • Not as a field. It is not serialisable, and a field that might be absent is better expressed as a nullable field or a different type.
  • Not as a method parameter. The caller then has to wrap the value, and you have three cases instead of two: present, empty, and null Optional. Overload the method instead.
  • Not for collections. An empty list already means no results. Optional<List> gives two ways to say nothing.

Optional was designed for one job: a return type for something that may legitimately have no answer.

"Optional removes NullPointerException." Calling get() on an empty one throws NoSuchElementException. You have changed the name of the failure, not removed it, unless you use the methods that handle absence.

"Wrap everything in Optional to be safe." An Optional that is never empty is noise. Use it where absence is a real, expected outcome.

Follow-up questions

What is the difference between map and flatMap on Optional?

The same distinction as on a stream: whether your function returns a plain value or another wrapped one.

If getAddress() returns an Address, use map and you get Optional<Address>.

If getAddress() itself returns Optional<Address>, because the address may be missing, then map gives you Optional<Optional<Address>>, which is useless. flatMap flattens it back to one level.

findUser(id)
    .flatMap(User::getAddress)      // returns Optional<Address>
    .map(Address::city)             // returns String
    .orElse("unknown");

This chaining is where Optional earns its place. The same code with null checks needs a nested check at every step, and each one is a place to forget.

The practical tell: if you find yourself with an Optional of an Optional, you used map where you needed flatMap.
