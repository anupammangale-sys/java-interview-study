The answers, and the two that quietly give the wrong result

The problems a streams coding round actually sets, with solutions that were compiled and run rather than typed from memory. Two of the standard answers produce the wrong output, and you would not notice in a review.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 Grouping

  • Group employee names by department.
  • Count, total and average salary per department.
  • Find the highest paid person in each department, without an Optional in the result.
  • Which department has the highest average salary?

Every one of these is groupingBy with a different second argument. Learn that shape and most of the round is done.

record Employee(String name, String dept, int salary, int age) {}

Ann  eng   120     Dan  sales  90     Finn hr  80
Bob  eng   100     Eve  sales 110     Gita hr  95
Cara eng   140

Drill it

Pick a problem, work out your answer, then reveal. Every solution here was compiled and run, and the output shown is what it actually printed.

The shape to memorise

collect(groupingBy(classifier, downstream))

The classifier decides the key. The downstream collector decides what the value is. With no downstream you get a list of the whole objects, which is almost never what was asked for.

You wantDownstream collector
how manycounting()
just one fieldmapping(Employee::name, toList())
a totalsummingInt(Employee::salary)
an averageaveragingInt(Employee::salary)
the biggest onemaxBy(comparingInt(Employee::salary))
anything, then transform itcollectingAndThen(inner, fn)
count, min, max, average, total at oncesummarizingInt(Employee::salary)

The Optional problem, and the fix worth knowing. maxBy returns an Optional, so grouping with it gives you Map<String, Optional<Employee>>, which is awkward to use. collectingAndThen unwraps it as part of the collector:

groupingBy(Employee::dept,
    collectingAndThen(maxBy(comparingInt(Employee::salary)),
                      o -> o.map(Employee::name).orElse("none")))
// -> {hr=Gita, sales=Eve, eng=Cara}

Returning the whole object when they asked for names. groupingBy(Employee::dept) gives Map<String, List<Employee>>. Add mapping(Employee::name, toList()).

Assuming the keys come out in order. Real output was {hr=..., sales=..., eng=...}, which is neither insertion nor alphabetical, because groupingBy returns a HashMap.

Follow-up questions

How do you make the grouped keys come out in a sensible order?

Use the three argument form, where the map is supplied in the middle:

// keys in the order first encountered
groupingBy(Employee::dept, LinkedHashMap::new, toList())

// keys sorted
groupingBy(Employee::dept, TreeMap::new, toList())

The argument order catches people out: classifier, then map factory, then downstream collector. It reads as though the collector should come second because that is the two argument form.

The measured default was {hr=[Finn, Gita], sales=[Dan, Eve], eng=[Ann, Bob, Cara]}, so the keys arrived in an order that matches nothing about the input. If you print a grouped result to a user, or compare it in a test with a fixed expected string, that is a real bug.

Worth adding: the values inside each group do keep the stream's order, because they are collected into a list. So the values are ordered even when the keys are not, which is exactly why this goes unnoticed for a while.

How would you do this without streams, and when would you?

With a loop and computeIfAbsent, and it is genuinely fine:

Map<String, List<String>> byDept = new HashMap<>();
for (Employee e : staff) {
    byDept.computeIfAbsent(e.dept(), k -> new ArrayList<>()).add(e.name());
}

Saying this in an interview is a good sign rather than a bad one, as long as you can also write the stream version. It shows you know the stream is a choice, not an obligation.

The loop is better when you need several results in one pass without teeing, when the logic has early exits or side effects that read badly as a pipeline, or when someone will debug it at three in the morning.

The stream is better when the transformation is the whole point and the pipeline reads as a description of the answer, which grouping usually does.

What is not a good reason either way is performance. For a few thousand objects the difference is nothing, and if someone claims otherwise the correct response is to ask for the measurement.

02 Counting and duplicates

  • Find the duplicates in a list, two different ways.
  • Build a frequency map.
  • Find the first character that appears exactly once.
  • Check whether two words are anagrams.

Everything here is one collector: groupingBy(identity(), counting()). Then you filter or sort the result.

List<String> words = [apple, pear, apple, fig, pear, apple, plum];

words.stream().collect(groupingBy(identity(), counting()))
// -> {plum=1, apple=3, pear=2, fig=1}

Duplicates, and the version worth knowing

// the obvious way: count, then keep the ones above one
words.stream().collect(groupingBy(identity(), counting()))
     .entrySet().stream()
     .filter(e -> e.getValue() > 1)
     .map(Map.Entry::getKey)
     .toList();                              // -> [apple, pear]

// the neat one, using the fact that Set.add returns false for a repeat
Set<String> seen = new HashSet<>();
words.stream().filter(w -> !seen.add(w)).collect(toSet());   // -> [apple, pear]

The second is shorter and interviewers like it. Be ready for the follow-up: it uses state outside the stream, so it is not safe in parallel. Saying that unprompted turns a trick into understanding.

The one where the standard answer is wrong

First character appearing exactly once in "swiss cheese". The answer everyone writes:

text.chars().filter(Character::isLetter).mapToObj(c -> (char) c)
    .collect(groupingBy(identity(), counting()))
    .entrySet().stream()
    .filter(e -> e.getValue() == 1)
    .map(Map.Entry::getKey)
    .findFirst();

// -> c   which is wrong

The correct answer is w. The letters are s, w, i, s, s, c, h, e, e, s, e. The first one appearing exactly once is w. The code above returns c because groupingBy builds a HashMap, so "first" means first in hash order, not first in the string.

One word fixes it:

.collect(groupingBy(identity(), LinkedHashMap::new, counting()))
// -> w

This is worth remembering because it passes every casual review. The code looks right, runs without error, and returns a plausible letter.

Character counting

"swiss cheese".chars()
    .filter(Character::isLetter)
    .mapToObj(c -> (char) c)
    .collect(groupingBy(identity(), LinkedHashMap::new, counting()));
// -> {s=4, w=1, i=1, c=1, h=1, e=3}

String.chars() gives an IntStream, so the cast back to char is needed before grouping. Forgetting it gives you a map keyed by numbers, which is a common stumble under pressure.

Using findFirst on a HashMap result. Measured to give the wrong letter. Any question with "first" in it needs an ordered map or a different approach entirely.

Filtering a stream with an outside Set and then going parallel. The neat duplicates trick becomes a race.

Follow-up questions

Solve first non repeating without a map at all.

Worth having, because it sidesteps the ordering bug completely and shows you understand what the map was for.

String text = "swiss cheese";
text.chars()
    .filter(Character::isLetter)
    .filter(c -> text.indexOf(c) == text.lastIndexOf(c))
    .mapToObj(c -> String.valueOf((char) c))
    .findFirst()
    .orElse("none");

If a character's first and last position are the same, it appears exactly once. The stream keeps the string's order naturally, so "first" means what you expect.

Be honest about the trade if asked: this scans the string twice per character, so it is quadratic, while the map version is linear. For a word it does not matter, for a large document it does.

That is a good thing to volunteer. It shows you can produce the neat answer and still know when it is the wrong one, which is more convincing than either alone.

How do you check for anagrams?

Sort the characters of both and compare, which is the version to reach for first:

private static String sorted(String s) {
    return s.chars().sorted()
            .collect(StringBuilder::new, StringBuilder::appendCodePoint, StringBuilder::append)
            .toString();
}
sorted("listen").equals(sorted("silent"));   // -> true

The three argument collect is the awkward part and worth understanding rather than memorising: a supplier that makes the container, an accumulator that adds one element, and a combiner that merges two containers for the parallel case.

A cleaner alternative that avoids it entirely is to compare frequency maps, which also handles the follow-up "what about counting letters" in the same breath:

Map<Integer, Long> freq(String s) {
    return s.chars().boxed().collect(groupingBy(identity(), counting()));
}
freq("listen").equals(freq("silent"));       // -> true

Mention the real world caveats if the conversation allows: case, spaces and accented characters all need deciding before either version is correct.

03 Nth highest and top N

  • Find the second highest salary.
  • Why does distinct() matter in that answer?
  • Find the top two earners in each department.

Nth highest is three operations, and the middle one is the part people forget.

staff.stream()
     .map(Employee::salary)
     .distinct()                      // without this, duplicates shift the answer
     .sorted(Comparator.reverseOrder())
     .skip(1)                          // skip(n-1) for the nth
     .findFirst()
     .orElse(-1);                      // -> 120

Why distinct matters. With salaries 140, 140, 120, the second highest is 120, not 140. Without distinct() you skip one row rather than one value and return 140. Interviewers add a duplicate to the data specifically to see whether you noticed.

Top N per group

This one needs the group collected first, because you cannot sort within a group until you have the group.

staff.stream().collect(groupingBy(Employee::dept,
    collectingAndThen(toList(), list -> list.stream()
        .sorted(Comparator.comparingInt(Employee::salary).reversed())
        .limit(2)
        .map(Employee::name)
        .toList())));

// -> {hr=[Gita, Finn], sales=[Eve, Dan], eng=[Cara, Ann]}

collectingAndThen is doing the work: collect each group to a list, then run a second pipeline over that list. It is the standard shape whenever a per group answer needs sorting or limiting.

Highest average, not highest total

staff.stream()
     .collect(groupingBy(Employee::dept, averagingInt(Employee::salary)))
     .entrySet().stream()
     .max(Map.Entry.comparingByValue())
     .map(Map.Entry::getKey)
     .orElse("none");                  // -> eng

Map.Entry.comparingByValue() and comparingByKey() save writing a lambda and read better.

Forgetting distinct on Nth highest. The single most common way to fail this question.

Sorting the whole stream to get the top one. max() exists and is a single pass. Sorting to take one element is doing far more work than asked.

Follow-up questions

What if there is no second highest?

The pipeline handles it without special casing, which is the point worth making.

With one distinct salary, skip(1) leaves an empty stream and findFirst() returns an empty Optional. Nothing throws. What you do next is a design decision rather than a coding one:

.findFirst()                          // Optional<Integer>
.orElse(-1)                           // a sentinel, usually a bad idea
.orElseThrow(() -> new NoSuchElementException("no second salary"))

Returning the Optional is often the best answer, because the caller then has to decide, and the signature tells the truth. Returning -1 invites someone to treat it as a salary.

The interviewer is usually checking two things here: that you noticed the case exists, and that you did not reach for a null. Saying "I would return the Optional and let the caller decide" answers both.

A related trap: on an empty list the same pipeline is also fine, which is worth stating because the loop version needs an explicit guard.

04 Sorting

  • Sort by one field then another.
  • Sort descending by one field and ascending by the next.
  • What happens when a sort field is null?
  • Sort a map by value and keep the order.

The reversed() trap, measured

Sort by age descending, then by name ascending. Here are both versions and what they actually printed:

// reversed() applies to the WHOLE chain built so far
comparingInt(Person::age).thenComparing(Person::name).reversed()
// -> [34:Dan, 34:Ann, 29:Cara, 22:Eve]   names reversed too

// reverse the age comparator only, then add the name
comparingInt(Person::age).reversed().thenComparing(Person::name)
// -> [34:Ann, 34:Dan, 29:Cara, 22:Eve]   correct

Both compile, both run, and both look right at a glance. The difference only shows when two people share an age, which test data often avoids. Put reversed() immediately after the part you want reversed, not at the end.

Nulls

// throws NullPointerException the moment one age is null
.sorted(Comparator.comparing(Person::age))

// nulls at the end
.sorted(Comparator.comparing(Person::age, Comparator.nullsLast(naturalOrder())))
// -> [Eve=22, Cara=29, Ann=34, Dan=34, Bob=null]

// nulls at the front
.sorted(Comparator.comparing(Person::age, Comparator.nullsFirst(naturalOrder())))
// -> [Bob=null, Eve=22, Cara=29, Ann=34, Dan=34]

The two argument comparing takes the field getter and a comparator for that field, which is where nullsFirst or nullsLast goes. Wrapping the whole comparator instead is a common mistake and does not protect against a null field.

Sorting a map by value

scores.entrySet().stream()
      .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
      .collect(toMap(Map.Entry::getKey, Map.Entry::getValue,
                     (a, b) -> a, LinkedHashMap::new));
// -> {bob=9, cara=5, ann=3}

// the same without LinkedHashMap
// -> {ann=3, cara=5, bob=9}   the sort is thrown away

Sorting into a plain toMap discards the sort. You did the work and then poured it into a HashMap, which has no order. This is the second answer on this page that runs cleanly and gives the wrong result.

Note also the explicit type on Map.Entry.<String, Integer>comparingByValue(). Without it the compiler often cannot work out the types in a chained call.

reversed() at the end of a chain. It reverses everything before it, not just the last part.

toMap after sorting. Use the four argument form with LinkedHashMap::new, or you have sorted for nothing.

Follow-up questions

Is stream sorting stable, and why does that matter?

Yes for an ordered source, and it matters more than it sounds.

Stable means two elements the comparator considers equal keep the order they arrived in. So you can sort by one thing, then sort the result by another, and the first sort survives as the tie break.

That is why the reversed() bug above is subtle. In that example the names were already alphabetical in the source, so with a correct comparator the tie between the two 34 year olds resolved to Ann then Dan, and with the buggy one it flipped to Dan then Ann. If the source had been in a different order, the bug would have shown differently or not at all.

The practical rule: prefer one comparator with thenComparing over sorting twice. It states the intent in one place and does not depend on stability to be correct.

One caveat worth knowing: on a parallel stream, stability is preserved for sorted, but forEach does not keep encounter order at all. If you sorted and then printed with forEach in parallel, the output is unordered. forEachOrdered is the fix, and it gives back much of what parallel bought you.

05 Flattening

  • Turn a list of lists into one list.
  • Why does map not work for this?
  • Sum a quantity across nested objects.
  • What does Optional::stream do?

flatMap is for when each element expands into several. The function returns a stream, and all those streams are joined into one.

List<List<Integer>> nested = [[1, 2], [3, 4, 5], [], [6]];

nested.stream().flatMap(List::stream).toList();   // -> [1, 2, 3, 4, 5, 6]
nested.stream().map(List::stream).toList();       // -> 4 Stream objects, not the numbers

That second line is the whole reason flatMap exists. map gives you a stream of streams, which is almost never useful. Note also that the empty list simply contributes nothing, so no special case is needed.

Across nested objects

record Item(String sku, int qty) {}
record Order(String id, List<Item> items) {}

// every item across every order
orders.stream().flatMap(o -> o.items().stream()).map(Item::sku).toList();
// -> [a, b, a]

// total quantity per sku, sorted by sku
orders.stream()
      .flatMap(o -> o.items().stream())
      .collect(groupingBy(Item::sku, TreeMap::new, summingInt(Item::qty)));
// -> {a=7, b=1}

Once flattened, everything from the earlier chapters applies unchanged. Most nested data questions are one flatMap followed by a familiar collector.

Two smaller ones worth knowing

// splitting text into words
sentences.stream().flatMap(s -> Arrays.stream(s.split(" "))).distinct().sorted().toList();
// -> [cat, mat, on, sat, the]

// dropping the empty Optionals
List<Optional<String>> maybes = [Optional.of("x"), Optional.empty(), Optional.of("y")];
maybes.stream().flatMap(Optional::stream).toList();      // -> [x, y]

Optional::stream gives a stream of nothing or one thing, so flattening drops the empties. It reads better than filter(Optional::isPresent).map(Optional::get) and cannot throw.

Using map where you need flatMap. If you end up with a stream of streams, or a list of lists you did not want, that is the tell.

Special casing the empty inner list. An empty stream contributes nothing to the flattened result, so no check is needed.

Follow-up questions

How do you flatten something three levels deep?

Chain flatMap once per level, and keep each step small enough to read:

companies.stream()
    .flatMap(c -> c.departments().stream())
    .flatMap(d -> d.employees().stream())
    .map(Employee::name)
    .toList();

Each flatMap removes one level of nesting. Three levels of containers means two flatMap calls, which is the arithmetic people get wrong under pressure.

Once it gets deeper than that, the pipeline usually stops explaining itself and a named helper method reads better. That is a judgement worth voicing in an interview, because it shows you are optimising for the reader rather than for fitting everything into one expression.

A genuine gotcha at any depth: if an intermediate level can be null rather than an empty collection, flatMap will throw. Defend at the source by returning empty collections instead of null, which is the better fix anyway, or add a filter before each expansion.

06 Checked exceptions inside lambdas

  • Why does a method that throws a checked exception not compile inside map?
  • Give three ways to handle it.
  • Which one would you choose in real code?

This stops every stream coding round eventually, and the reason is simple once stated.

int parse(String s) throws Exception { ... }

words.stream().map(this::parse).toList();   // does not compile

map takes a Function, and Function.apply is not declared to throw anything checked. So no method that throws a checked exception can be used there. It is not a limitation of streams, it is what the interface says.

Three ways round it, all run

A. Catch inside the lambda and rethrow as something unchecked.

words.stream().map(s -> {
    try { return parse(s); }
    catch (Exception e) { throw new RuntimeException(e); }
}).toList();                                // -> [1, 2, 3]

Correct, and it ruins the readability that made you use a stream.

B. Extract that into a helper, so the pipeline stays clean.

interface ThrowingFunction<T, R> { R apply(T t) throws Exception; }

static <T, R> Function<T, R> unchecked(ThrowingFunction<T, R> f) {
    return t -> {
        try { return f.apply(t); }
        catch (Exception e) { throw new RuntimeException(e); }
    };
}

words.stream().map(unchecked(this::parse)).toList();   // -> [1, 2, 3]

Write it once, use it everywhere. This is the answer that shows you understand functional interfaces rather than just using them.

C. Do not throw at all. Separate what worked from what did not.

Map<Boolean, List<String>> split = mixed.stream().collect(partitioningBy(this::isNumber));
// -> valid [1, 3], invalid [oops]

split.get(true).stream().map(Integer::parseInt).toList();   // -> [1, 3]

Which to choose. For a batch where one bad row should not kill the job, C is usually right and it is the answer that sounds like production experience: you end up with the failures in hand rather than an exception and no idea which row caused it.

For code where a failure genuinely is fatal, B keeps the pipeline readable. What B costs you is visible in the measured output: the original becomes RuntimeException wrapping not a number: oops, so the checked exception is now wrapped one level deeper and anything catching it must unwrap the cause.

Catching and returning null. The nulls flow down the pipeline and fail somewhere else, usually in a collector, with a stack trace pointing nowhere near the cause.

Swallowing the exception with an empty catch. Elements disappear silently, which is Episode 5's DiscardPolicy in a different costume.

Follow-up questions

Why can a lambda not throw a checked exception in the first place?

Because a lambda is an implementation of an interface method, and it can only throw what that method declares.

Function.apply is declared with no throws clause. A lambda passed to map becomes an implementation of it, so it may not throw anything checked, exactly as an overriding method may not add checked exceptions its parent did not declare. There is nothing special about lambdas here.

The proof is that it works fine with an interface that does declare it. Callable.call throws Exception, so a lambda passed where a Callable is expected can throw whatever it likes. Same lambda syntax, different rule, because the interface is different.

So the real question behind the question is whether you understand that a lambda is just an interface implementation with less typing. Saying that gets you further than listing the workarounds.

Worth adding what the standard library actually does: it defines separate interfaces where throwing matters, such as Callable, rather than adding throws to Function, because that would force every caller everywhere to handle it.

G Word list

Every term on this page that you might not already know.

classifier
The function you give groupingBy that decides the key each element belongs under.
downstream collector
The second argument to groupingBy, deciding what each group's value is. Without it you get lists of whole objects.
collectingAndThen
Runs a collector, then applies a function to its result. How you unwrap an Optional or sort within a group.
identity()
Function.identity(), a function returning its input unchanged. Used as the classifier when grouping by the element itself.
summarizingInt
One collector giving count, sum, min, max and average together in a single pass.
naturalOrder
The default ordering of a comparable type. Needed as the inner comparator when wrapping with nullsFirst or nullsLast.
nullsFirst / nullsLast
Wraps a comparator so null values sort to one end instead of throwing.
stable sort
Elements the comparator calls equal keep the order they arrived in. Java's stream sort is stable for an ordered source.
flatMap
For when each element expands into several. The function returns a stream, and all of them are joined into one.
functional interface
An interface with one abstract method, which a lambda can implement. Function, Predicate, Callable.
checked exception
One the compiler forces you to handle or declare. Cannot be thrown from a lambda unless the interface declares it.
encounter order
The order elements arrive in the stream. Preserved by most operations, thrown away by collecting into a HashMap.
