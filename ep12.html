The proxy in the middle

Almost every Spring question people get wrong has the same answer behind it: the object you wrote is not the object anyone else is holding. Spring wrapped it. This episode runs a real Spring Boot 3.5.3 application, prints what is actually in the running context, and makes real HTTP calls to itself. The headline result is two identical methods where one returns 200 and the other returns 404, and a transaction that silently does nothing.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 The path of a request

  • Walk a GET request from the socket to your controller method and back.
  • What is the DispatcherServlet and what does it actually do?
  • What is the difference between a filter and an interceptor?
  • How does a Java object become JSON without any code from you?

The question. "A GET request arrives. Walk me through what happens." It sounds like a memory test and it is not. The interviewer wants to know whether you can debug a request that goes wrong, which means knowing where you can get in the way of it.

Everything below was read out of a running application by asking the context what beans it holds, so it is what your program really has, not a diagram.

Common wrong answers

"The request goes to the controller." True and it skips everything that matters. The question is what happens before and after, because that is where the problems live.

"Filters and interceptors are basically the same." They see different things. A filter sees a request that ends in a 404; an interceptor never runs for one.

"Jackson converts the object." Jackson does the writing, but only after Spring picked a converter by matching the client's Accept header against each converter's supported types. Knowing that step exists is what lets you debug a 406.

Follow-up questions

How does Spring decide to return JSON rather than XML?

Content negotiation, which is a matching exercise between two lists.

The client sends an Accept header saying what it can handle, for example application/json, or */* meaning anything. Spring takes the type your method returned and walks the converter list in order. The first converter that can write that type and produces a media type the client accepts is the one used.

Order matters, which is why the list above is worth knowing. Jackson sits above the XML converter, so when a client sends */* it gets JSON. If the XML converter were first, the same request would get XML and nothing in your code would have changed.

Two failure modes worth naming. A 406 Not Acceptable means no converter could produce anything the client asked for, usually a client asking for a type you do not support. A 415 Unsupported Media Type is the other direction: the client sent a body in a format no converter could read.

You can override the whole thing by putting produces on the mapping, for example @GetMapping(value = "/x", produces = "application/xml"), which forces the choice regardless of what the client asked for.

What is the DispatcherServlet actually for? Why not just call the controller?

Because "just call the controller" hides about eight decisions, and the DispatcherServlet is the thing that makes each of them replaceable.

It is a single servlet registered at / that receives every request, and its job is coordination rather than work. It asks the handler mappings which handler matches. It asks which adapter knows how to invoke that handler. It runs the interceptors before and after. It hands the result to a converter or a view resolver. When something throws, it asks the exception resolvers what to do.

Every one of those is an interface with several implementations, and that is the point. Your @RestController method, a functional route, and a plain old servlet-style handler are three completely different shapes, and the DispatcherServlet treats them the same because it only talks to HandlerMapping and HandlerAdapter. The running application above has six mappings and four adapters for exactly that reason.

The practical value: when a request does something you did not expect, you now know there are six mappings that could have claimed it, and you can find out which one did.

Where does the thread come from, and does that matter?

From Tomcat's thread pool, and it matters more than most people expect.

Tomcat keeps a pool, 200 threads by default in Spring Boot. One request occupies one thread for its entire life, including all the time it spends waiting for a database or another service. When all 200 are busy, further requests queue, and when the queue fills connections are refused. Note that the limit is not how fast your code is, it is how long each request holds a thread.

That is why a slow downstream service takes your service down with it. If a call that normally takes 50 milliseconds starts taking 5 seconds, each thread does a hundredth of the work, and 200 threads no longer cover the traffic. Nothing in your code changed.

Two things follow. First, a timeout on every outbound call is not optional, because without one a hung downstream holds your threads for ever. Second, this is exactly the workload virtual threads were added for: set spring.threads.virtual.enabled=true on Java 21 or later and each request gets a virtual thread instead, so waiting no longer occupies a platform thread.

One more detail worth having: request scoped beans and ThreadLocal values work because of this one thread per request rule. That is also why they quietly stop working the moment you hand work to another thread yourself.

How do I add something to every request without touching every controller?

There are four places, and picking the right one is the real answer.

A filter for anything that must see every request, including ones that end in a 404 or never reach a controller. Request logging, a request id, authentication. Extend OncePerRequestFilter rather than implementing Filter directly, because a request can be dispatched more than once internally and you rarely want your code running twice.

An interceptor when you need to know which handler was chosen. Per endpoint timing, or a check that depends on an annotation on the method.

A @ControllerAdvice for things that are about the controller layer itself: exception handling, adding a common attribute, binding rules. That is chapter five.

A HandlerMethodArgumentResolver when you want a custom parameter type in your method signature, so instead of every method reading a header, they can declare CurrentUser user and Spring supplies it.

The mistake to avoid is doing it in a base class that every controller extends. It works, it puts an inheritance chain in the middle of your web layer, and it stops working the moment somebody writes a controller that forgets to extend it.

02 The self call trap

  • Why does calling your own @Transactional method from the same class do nothing?
  • I caught the exception. Why did the whole thing still roll back?
  • What is the difference between REQUIRED and REQUIRES_NEW?
  • Which exceptions cause a rollback by default?

The mechanism behind almost every Spring surprise. When a bean has @Transactional on it, Spring does not give other beans your object. It builds a wrapper around it, a proxy, and gives everyone that instead. The wrapper starts a transaction, calls your method, then commits or rolls back.

So a method call only gets a transaction if it goes through the wrapper. A call from inside the same object never leaves the object, so the wrapper is not involved.

B. the same method, reached by a call from INSIDE the same bean
  outer: transaction active? false
  inside saveThenFail: transaction active? false
  rows left in the database: 1   NOT rolled back, the data survived

Same method. Same exception. Outside: 0 rows. Inside: 1 row. The transaction active? false line is printed from inside the annotated method itself, which is as direct as this gets: the annotation is there, and there is no transaction.

The worst part is that nothing fails. No error, no warning, no log line. The code looks correct, the annotation is right there, and the data quietly stops being protected. This is why it is asked so often.

The second trap: catching an exception does not undo a rollback.

inner method uses REQUIRED, the defaultreal output
  outer caught: inner failed, carrying on
  UnexpectedRollbackException: Transaction silently rolled back
  because it has been marked as rollback-only
  rows left: 0   the outer save is gone too

With REQUIRED, the inner method joins the transaction the caller already has. There is one transaction, not two. When the inner method throws, Spring marks that one shared transaction rollback only. Your catch block stops the exception travelling, and it cannot unmark the transaction, because the mark is on the transaction and not on the exception. So the commit at the end fails, and the outer save goes too.

With REQUIRES_NEW the inner method suspends the caller's transaction and runs in a genuinely separate one. That one rolls back, the outer one is untouched, and catching the exception works the way you expected. Real output: rows left: 1.

PropagationWhat it doesWhen you want it

REQUIRES_NEWSuspends the caller's transaction and runs in a new one.Work that must survive the caller failing. Writing an audit row, or recording that an attempt was made.

Common wrong answers

"@Transactional does not work on private methods." True, and it is only half the rule and it makes people think public is the fix. The real rule is that the call has to arrive from outside the object. A public method called with this. has exactly the same problem.

"Use REQUIRES_NEW to fix the self call." It changes nothing. The proxy is still not involved, so no propagation setting is ever read.

"Catching the exception prevents the rollback." Measured above: rows left 0, and an UnexpectedRollbackException at commit time.

Follow-up questions

So how do I actually fix a self call?

Four options, in the order you should reach for them.

Move the method to another bean. Almost always the right answer. If the inner work is a real unit of work it usually deserves its own class anyway, and the call then goes through that bean's proxy normally. This is the one to say first, because it treats the trap as a design signal rather than something to work around.

Inject the bean into itself. Take a constructor parameter of your own type, or an ObjectProvider of it, and call self.method() instead of this.method(). Now the call goes through the proxy. It works and it looks strange to anyone reading it, so it needs a comment saying why.

Use TransactionTemplate. Inject it and wrap the work in template.execute(status -> { ... }). No proxy, no annotation, the transaction is explicit in the code. Good when the boundary is genuinely inside a method rather than around one.

AopContext.currentProxy(). Gets the proxy from a thread local. Needs @EnableAspectJAutoProxy(exposeProxy = true) and it ties your code to Spring's AOP internals. It exists, it is worth naming so they know you have seen it, and it is the last one to pick.

Which exceptions roll back by default, and why does that catch people out?

By default Spring rolls back on RuntimeException and Error, and commits on checked exceptions. That last half is the one that surprises people, because it is the opposite of what most expect.

So a method that throws IOException, or your own checked InsufficientFundsException, will let the transaction commit. Everything written before the throw is saved. Nothing warns you.

The reason is historical rather than principled: the EJB convention was that checked exceptions are expected business outcomes and unchecked ones are failures, so Spring matched it. Whether or not you agree, that is the behaviour and you should say so.

The fix is one attribute: @Transactional(rollbackFor = Exception.class), which rolls back on everything. There is also noRollbackFor for the reverse. A reasonable house rule is to prefer unchecked exceptions for failures so the default is already right, and to set rollbackFor explicitly anywhere a checked exception can escape a transactional method.

Explain isolation levels with a real example of each problem.

Isolation is about what one transaction can see of another one that has not finished. Three problems, in increasing order of how hard they are to stop.

Dirty read. Transaction A updates a balance to 500 and has not committed. Transaction B reads 500. A then rolls back, so the 500 never existed and B acted on a number that was never real. READ_UNCOMMITTED allows this and almost nothing uses it.

Non repeatable read. Transaction A reads a balance and gets 100. Transaction B updates it to 50 and commits. A reads the same row again and gets 50. The same query gave two answers inside one transaction. READ_COMMITTED allows this, and it is the default in Postgres, Oracle and SQL Server.

Phantom read. Transaction A counts orders over 1000 rupees and gets 5. Transaction B inserts another one and commits. A runs the same count and gets 6. No row A read has changed, but the set it matched has grown. REPEATABLE_READ stops the first two, and this is the one it does not stop. It is MySQL's default.

SERIALIZABLE stops all three by making transactions behave as if they ran one after another. It is correct and it is the slowest, because it means more locking or more failed transactions that have to be retried.

The honest practical note, and a good thing to say: almost nobody changes this. The default is right nearly all the time, and the two places it comes up in real work are a report that must see a consistent picture, and a check then act sequence such as "is this seat free, if so book it", where the usual fix is not a higher isolation level but a database constraint or a lock on the specific row.

Does @Transactional on a read only method do anything useful?

Yes, and it is worth being specific rather than saying it is just a hint.

@Transactional(readOnly = true) does three things. Hibernate switches the flush mode to manual, so it stops checking your loaded entities for changes at the end, which is real work saved when a query loaded a lot of rows. It sets the JDBC connection read only, which some databases use to route the query to a replica. And it declares intent, so a later reader knows this method is not supposed to write.

What it does not do is stop you writing. On most setups a save inside a read only transaction will still go through, or will fail with a driver level error rather than a clean Spring one. It is not a safety mechanism.

The more useful reason to put it on read methods is that it gives them a transaction at all. Without one, a service method that runs three queries runs them in three separate transactions and can see the database in three different states. With one, all three see the same consistent snapshot. That is usually what you wanted, and it is a better answer than the performance one.

Step 9 is the one that explains the rest of this episode. postProcessAfterInitialization is allowed to return a different object from the one it was given. That is where Spring swaps your bean for a proxy. It is how @Transactional gets its wrapper, how @Cacheable gets its wrapper, and therefore why the self call in chapter two silently does nothing.

Scopes, and the trap between them. A singleton is one instance for the whole application. A prototype is a new one every time it is asked for. Both are simple until you put one inside the other:

The prototype was injected once, when the singleton was built, and the singleton then held that one instance for ever. The scope was not ignored: it was honoured exactly once and then never asked again. ObjectProvider fixes it because it is a handle to the factory rather than to an instance, so asking it produces a new object each time.

Common wrong answers

"@PostConstruct runs before the constructor." Nothing runs before the constructor. The order is measured above: constructor, injection, aware callbacks, then @PostConstruct.

"Singleton beans are thread safe." Spring guarantees one instance, not safe concurrent access. One instance shared by 200 Tomcat threads is the opposite of safe if it holds mutable state.

"Prototype beans are destroyed like singletons." Spring hands you a prototype and forgets it. No destroy callback ever runs on one, so anything holding a resource leaks unless you close it yourself.

Follow-up questions

Are singleton beans thread safe? What does that mean in practice?

Spring guarantees you get one instance. It guarantees nothing about what happens when several threads use it at once, and those are completely different promises.

In practice one @Service is shared by every Tomcat request thread, 200 of them by default. If the service has only final fields holding other beans, which is the normal shape, there is nothing to go wrong: nothing changes, so nothing can be seen half changed. That is why the usual advice, constructor injection into final fields, quietly solves this before it starts.

It goes wrong the moment somebody adds a field that changes. A counter, a cached last result, a SimpleDateFormat, a StringBuilder reused between calls. Now 200 threads share it and you have a data race that shows up as wrong numbers under load and never in testing.

If you genuinely need per request state, put it in a local variable, which is per thread by definition. If it has to be shared, use an atomic type or a concurrent collection rather than a lock, for the same reasons as anywhere else.

A good line to finish on: singleton is about how many objects exist, not about how many threads may touch them.

What is a BeanPostProcessor, and when would I write one?

An interface with two methods that Spring calls for every single bean, once before the init callbacks and once after. Both methods receive the bean and return a bean, and the returned one is what the rest of the application gets.

That return value is the whole point. postProcessAfterInitialization can hand back a completely different object, and that is how proxying works: Spring's own infrastructure returns a wrapper around your object when it sees @Transactional, @Cacheable, @Async or any aspect. So the answer to "how does an annotation change what my method does" is: a BeanPostProcessor replaced your object at step 9.

Writing one yourself is rare and legitimate for cross cutting setup that annotations cannot express: registering every bean that implements some interface with an external system, validating that no bean is missing configuration, adding instrumentation to a whole category of beans.

One real trap worth mentioning. A BeanPostProcessor has to exist before the beans it processes, so Spring creates them very early. If yours injects an ordinary bean, that bean gets created early too and can miss processing by other post processors, including proxying. The symptom is a bean whose @Transactional silently stops working. Depend on an ObjectProvider instead of the bean itself to avoid it.

What are request and session scope, and what is the proxy for?

@RequestScope gives one instance per HTTP request. @SessionScope gives one per user session. Both are useful for carrying something for the length of that unit, such as the current user or a request id.

They create the same problem as the prototype trap, only worse. Your @Service is a singleton, created at startup. A request scoped bean does not exist at startup, because there is no request. So injecting one directly cannot work.

Spring's answer is to inject a proxy instead. The singleton gets a stand in object that looks like the right type, and every method call on it looks up the real instance for whatever request is running on the current thread and forwards the call. That is what proxyMode = ScopedProxyMode.TARGET_CLASS means, and @RequestScope turns it on for you.

The catch follows directly from how it works: the lookup uses the current thread. Hand the work to another thread, an @Async method or a parallel stream, and the lookup finds no request and fails. This is the same reason ThreadLocal values and security context vanish across threads, and it is worth naming as one cause rather than three separate mysteries.

Constructor, setter or field injection? Defend the choice.

Constructor injection, and there are four concrete reasons rather than a preference.

The object cannot exist half built. Everything it needs is a constructor parameter, so there is no window where a field is still null. With field injection the object exists first and gets filled in afterwards.

The fields can be final. That makes the class immutable in the way that matters for the thread safety question above: nothing can change, so nothing can be seen half changed by 200 request threads.

It is testable without Spring. new OrderService(repo, mailer) in a plain test, no context, no reflection. Field injection forces you to start a Spring context or use reflection to get test doubles in, which is why those test suites are slow.

It tells you when the class has grown. A constructor with nine parameters is embarrassing and visible. Nine @Autowired fields look tidy and hide the same problem. Constructor injection reports a design issue that field injection conceals.

Two details that finish the answer. Since Spring 4.3 a class with a single constructor does not need @Autowired on it at all. And setter injection still has one real use: a genuinely optional dependency, or breaking a circular reference, which is itself a sign the design needs a look.

04 Controller, RestController, Component, Bean

  • What exactly does @RestController add over @Controller?
  • Two methods with identical bodies returned 200 and 404. Why?
  • When do you use @Bean instead of @Component?
  • Is there any difference between @Component, @Service and @Repository?

The definition first, because it is exact. @RestController is @Controller plus @ResponseBody, applied to every method. That is the entire difference, and it is enough to change a 200 into a 404.

Two methods, identical bodies, real HTTP calls to a running application:

both methods are: return "hello";real responses
// on a @RestController
/api/text                     200  text/plain          hello

// on a plain @Controller
/mvc/text                     404  application/json    {"status":404,"error":"Not Found"}

// the same @Controller method, with @ResponseBody added
/mvc/text-with-responsebody   200  text/plain          hello

Why the 404. Without @ResponseBody, Spring treats the returned String as the name of a view to render. It goes looking for a template called "hello", finds nothing, and the request ends as a 404. Nothing is broken; Spring did exactly what it was told. The word "hello" was an instruction, not content.

That is the whole reason @RestController exists. Before it, every method in an API controller needed @ResponseBody, and forgetting one gave you this exact confusing 404.

The rest of the real responses, which also show that returning a record is all it takes to get JSON:

same application, more callsreal responses
/api/json                200  application/json    {"message":"hello","count":3}
/api/order/A-77?count=4  200  application/json    {"message":"order A-77","count":4}

@Component versus @Bean. Both put an object in the context. The difference is who constructs it.

The rule of thumb: if you can put the annotation on the class, use @Component. If you cannot, because it is somebody else's class, or because building it takes more than a constructor call, use @Bean. A DataSource, an ObjectMapper with custom settings, a third party client: all @Bean.

Common wrong answers

"@Service is for business logic and @Repository is for data, and that is enforced." The first half is a naming convention. @Service is @Component with a different name and nothing else. @Repository is the one real exception, and it is worth knowing why.

"@RestController makes it faster." It changes how the return value is treated. Nothing else.

"@Bean and @Component are interchangeable." Only when the class is yours and construction is trivial. You cannot put @Component on a class from a jar.

Follow-up questions

Is @Repository really different, or is it just a name?

It is the one stereotype that does something real, and this is a good question to get right because most people say all three are identical.

@Repository makes the bean eligible for exception translation. Spring registers a post processor that wraps repository beans, catches the database specific exception that came out, and rethrows it as one of Spring's own DataAccessException types.

Concretely: a unique constraint violation arrives from the driver as a SQLIntegrityConstraintViolationException on MySQL, or a PSQLException with a state code on Postgres, or a Hibernate ConstraintViolationException. With @Repository your service sees DataIntegrityViolationException in every case. Your catch block stops depending on which database you are running.

All of Spring Data's repositories get this already, so if you use JpaRepository you have it without doing anything. It matters when you write a DAO by hand with JdbcTemplate or an EntityManager.

@Service and @Controller genuinely are just names, and the value of the names is real but human: they tell a reader which layer they are in, and they give you something to point aspects and component scan filters at.

Why does calling a @Bean method from another @Bean method not create two objects?

Because a @Configuration class is not a normal class. Spring subclasses it at runtime and intercepts every @Bean method call, which is the same proxy idea as chapter two showing up in a different place.

Write this:

@Bean A a() { return new A(b()); }
@Bean B b() { return new B(); }

The call to b() inside a() looks like an ordinary method call that would build a second B. It does not. The interception checks whether that bean already exists and returns the existing one, so there is exactly one B in the context and a gets it.

This is called full mode, and it is what @Configuration buys you. If you put @Bean methods on a plain @Component instead, you get lite mode: no subclass, no interception, and that same call really does build a second object. The symptom is two instances of something that was supposed to be shared, and it is genuinely hard to spot by reading.

You can turn it off deliberately with @Configuration(proxyBeanMethods = false), which is slightly faster at startup and is safe when no @Bean method calls another. Spring Boot's own autoconfiguration classes do this. The safer habit for your own code is to take the dependency as a method parameter, @Bean A a(B b), which works identically in both modes.

How does Spring find my components in the first place?

@SpringBootApplication includes @ComponentScan with no package argument, which means it scans the package the annotated class is in, and everything below it. That single default explains most "my bean is not being found" problems.

If your main class is in com.example.app and somebody adds a service in com.other.thing, it is never scanned, is never a bean, and every injection of it fails at startup. The fix is to move it under the main package, which is almost always the right answer, or to add the package explicitly to scanBasePackages.

The failure worth knowing about is the opposite one, and it cost time while building the demos for this episode. Put the main class in the default package, with no package declaration at all, and there is no base package to scan, so Spring scans everything on the classpath. Every library, every autoconfiguration. The application here failed at startup trying to configure a database driver nothing had asked for. The rule is simple: the main class always lives in a real package, and everything else lives under it.

Two beans of the same type. How does Spring choose?

By default it does not choose, it fails at startup with NoUniqueBeanDefinitionException listing the candidates. Failing loudly at startup rather than picking one at random is the right behaviour and worth saying.

Four ways to resolve it, roughly in order of preference.

@Primary on one of them. That one wins whenever nothing more specific is asked for. Right when there is a clear default and the others are special cases.

@Qualifier("name") at the injection point, matching a name on the bean. Explicit at both ends, and the right answer when neither bean is a natural default.

Match the parameter name to the bean name. If the beans are fast and slow, a parameter called slow resolves to that one. It works and it is invisible: renaming a parameter changes behaviour, which is a nasty property. Know it, avoid relying on it.

Inject all of them. Take a List<Handler> or a Map<String, Handler> and Spring gives you every implementation, the map keyed by bean name. This is often the real answer rather than a workaround: it is exactly the shape you want for a set of strategies, and adding a new one requires no change to the code that uses them.

05 One place for every error

  • How do you turn a domain exception into a proper HTTP response?
  • What is @ControllerAdvice and how wide does it reach?
  • What does an unhandled exception produce?
  • What should never appear in an error response?

The problem. A service throws OutOfStockException. Without anything, the client gets a 500 saying "Internal Server Error", which is both wrong and useless: nothing failed internally, the order simply cannot be fulfilled, and the caller has no way to tell those apart.

The fix is one class for the whole application. @RestControllerAdvice is @ControllerAdvice plus @ResponseBody, and its @ExceptionHandler methods apply to every controller:

demo-ep12/src/main/java/demo/web/ApiErrors.javathe whole class
@RestControllerAdvice
public class ApiErrors {

    @ExceptionHandler(OutOfStockException.class)
    public ProblemDetail outOfStock(OutOfStockException e) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.getMessage());
        p.setTitle("Out of stock");
        p.setProperty("sku", e.getSku());
        return p;
    }
}

/api/boom       409  application/problem+json
  {"type":"about:blank","title":"Out of stock","status":409,
   "detail":"out of stock: SKU-42","instance":"/api/boom","sku":"SKU-42"}

/api/unhandled  500  application/json
  {"status":500,"error":"Internal Server Error","path":"/api/unhandled"}

The handled one is a 409 with a meaningful title, the detail, and a custom sku field a client can act on. The unhandled one is a generic 500 that tells the caller nothing, and Spring writes the full stack trace into your logs.

ProblemDetail is worth knowing by name. It is Spring's built in implementation of RFC 7807, the standard shape for an HTTP error body: type, title, status, detail, instance, plus any properties you add. Using it means not inventing your own error format, and the content type comes out as application/problem+json so a client can tell it is a structured error.

What must never go in an error response. Stack traces, SQL, class names, internal host names, and anything from an exception message you did not write yourself. An exception message often contains the data that caused the failure, which can be somebody's email address or part of a query. The message goes in the log; the client gets the status and a sentence they can act on.

Common wrong answers

Try and catch in every controller method. It works and it puts the same eight lines in forty places, and the fortieth one will be slightly different.

Returning 200 with an error field in the body. Now every client has to read the body to find out whether the call worked, and no proxy, cache, retry policy or monitoring dashboard can tell either.

Putting the exception message straight into the response. The quickest way to leak a database error, a file path, or someone's data to a caller.

Follow-up questions

How wide does @ControllerAdvice reach, and can I narrow it?

By default it applies to every controller in the application, which is usually what you want and occasionally not.

You can narrow it three ways, all as arguments to the annotation. @RestControllerAdvice(basePackages = "com.example.api") limits it to controllers in a package. assignableTypes = {OrderController.class} limits it to named controllers. annotations = {PublicApi.class} limits it to controllers carrying an annotation of yours.

The real use for narrowing is having two of them: one for a public API that returns careful, sparse errors, and one for an internal or admin API that can afford to say more. Same application, two error policies, no if statements.

Two details that come up. You can have several advice classes at once, and @Order decides which is asked first. And when two handlers could both match an exception, Spring picks the most specific one by class hierarchy, so a handler for OutOfStockException wins over one for RuntimeException without you doing anything.

How do you handle validation failures cleanly?

Put @Valid on the request body parameter and constraints such as @NotBlank or @Min on the record or class. When it fails, Spring throws MethodArgumentNotValidException before your controller method runs at all.

Out of the box that becomes a 400 with a body containing every violation, which is already reasonable. The reason to handle it yourself is shape: the default body is verbose, includes some internals, and is not the same shape as your other errors, so clients end up parsing two formats.

So add a handler for it in the same advice class, walk e.getBindingResult().getFieldErrors(), and build a ProblemDetail with a map of field name to message. Now a validation failure and a business failure look the same to a client apart from the status code.

Two things worth knowing. A different exception, ConstraintViolationException, is thrown when constraints are on method parameters directly rather than on a body object, so a complete advice class usually handles both. And the messages in those violations come from your annotations, so writing @NotBlank(message = "order id is required") is what makes the response readable rather than mentioning a field path nobody outside your team recognises.

Which status code should I return? People argue about this.

The argument is usually about a handful of cases. The rest is settled and worth being crisp about.

400 when the request itself is malformed or fails validation: a missing field, a string where a number belongs. The caller can fix it by sending something different.

401 when we do not know who you are, 403 when we do and you are not allowed. Getting these the wrong way round is the most common status code mistake.

404 when the thing does not exist. Also the right answer when it exists but this caller must not know that, which is why some APIs return 404 rather than 403 for another user's record.

409 when the request is well formed and conflicts with the current state. Out of stock, already cancelled, version mismatch. This is the one people miss, and it is the right code for most business rule failures.

422 when the request is well formed and semantically wrong. The overlap with 400 and 409 is the actual argument; pick one convention for your API and apply it consistently, because a client cares far more about consistency than about which of the two you chose.

500 only when your code genuinely failed. If a 500 can be caused by a caller sending bad input, that is a bug in your error handling, because it makes real failures impossible to find in a dashboard.

Where do errors go that never reach a controller?

Not to your @ControllerAdvice, and this catches people out because the advice looks like it covers everything.

@ControllerAdvice is part of Spring MVC and only sees exceptions thrown by a handler that was found and invoked. Anything that fails earlier never reaches it.

That includes a request that matched no mapping, which is the 404 from chapter four. It includes an exception thrown inside a filter, because filters run outside the DispatcherServlet entirely. And it includes anything Spring Security rejects, since that is a filter, which is why authentication failures need their own AuthenticationEntryPoint and AccessDeniedHandler rather than an @ExceptionHandler.

Those all end up at the container's error page, which in Spring Boot is /error, handled by BasicErrorController. That is what produced the plain 404 and 500 bodies in the output above. If you want those to match your API's error shape, you replace or configure that controller, which is a separate job from writing an advice class.

The short version to say out loud: an advice class covers exceptions from your controllers, and everything before or around them goes to /error.

06 Caching, and what Redis changes

  • What does @Cacheable actually do, and what is it worth?
  • Why does @Cacheable have the same self call problem as @Transactional?
  • What changes when the cache moves to Redis?
  • What is the danger of caching the wrong thing?

What it is. Put @Cacheable("prices") on a method and Spring wraps the bean in a proxy. The proxy builds a key from the arguments, looks in the cache, and either returns what it finds or calls your method and stores the result. Your method body does not change and does not know.

What it was worth, measured on a method that takes 200 milliseconds:

demo-ep12, real timingssame argument each time
first call       203 ms   went and did the work
second call        0 ms   came from the cache
third call         0 ms
real lookups behind three calls: 1

after evict      200 ms   the work happened again
real lookups now: 2

Three calls, one real lookup. The counter is inside the method, so that is a count of how many times the body actually ran, not an inference from the timing.

It is the same proxy, so it has the same trap. Calling a @Cacheable method from inside the same bean skips the cache entirely, for exactly the reason chapter two showed for @Transactional: the call never leaves the object, so the wrapper is not involved. There is no error and no warning. The method simply runs every time and the cache stays empty.

This is why it is worth learning the mechanism once rather than the annotations separately. @Transactional, @Cacheable, @Async, @Retryable and every custom aspect all work the same way and all break the same way.

Common wrong answers

"Caching makes it faster." It makes a repeated call faster and every first call slightly slower. If the arguments are nearly always different, a cache is pure cost, and that is a real situation rather than a hypothetical.

"Just add @Cacheable and you are done." You have taken on a second copy of the truth. The question that matters is how it gets thrown away, and if the answer is "it does not", you have chosen to serve stale data for ever.

"Redis makes the cache faster." Redis makes it shared and durable. A local map is faster than Redis and always will be, because it does not touch the network.

Follow-up questions

How is the cache key built, and when does that go wrong?

By default Spring builds the key from all the method arguments. One argument becomes the key itself; several become a composite key of all of them; none becomes a single shared key for the method.

That default breaks in three ways worth knowing.

An argument that is not part of the identity. A method taking (String sku, Locale locale, TraceContext trace) gets a different key for every trace, so the cache never hits. Fix it with @Cacheable(value = "prices", key = "#sku") naming only what matters.

An object argument without equals and hashCode. Two equal-looking objects are different keys, so again nothing ever hits. Records get both for free, which is one more reason to use them.

A missing dimension. Caching a price by #sku when it depends on the customer's country means the first caller's price is served to everyone. This is the dangerous one, because unlike the others it does not look broken, it just returns the wrong answer to the wrong person.

Also worth naming: condition decides before the call whether to use the cache at all, and unless decides after it whether to store the result. unless = "#result == null" is the usual guard against caching nothing as if it were an answer.

How do you stop a cache serving stale data?

Three approaches, and the honest answer is that you pick one deliberately rather than hoping.

Expire it by time. Every entry lives for a fixed period. Simple, predictable, and it means you accept being wrong for up to that long. The real question is how long the business can tolerate, and for a lot of data the answer is far longer than people assume. A product description can be five minutes stale; a price during a flash sale cannot.

Evict on write. The code that changes the data also removes the cache entry, with @CacheEvict, or replaces it with @CachePut. Correct when every write goes through your application. It quietly fails the moment anything else writes to that database, such as a batch job, an admin tool or another service.

Do not cache it. The option people skip. If the data changes constantly, or being wrong is expensive, or you cannot say how it gets invalidated, the cache is a liability.

The two together are the usual real answer: evict on write for correctness when you control the writes, plus a time to live as a safety net for when you do not. And the sentence worth having ready is that a cache with no expiry and no eviction is not a cache, it is a second database that is always wrong and never checked.

What is a cache stampede, and does it happen here?

A popular key expires, and every request that wanted it misses at the same moment, so instead of one slow call to the database you get five hundred at once. The cache was the only thing protecting the database, and it stopped for a fraction of a second.

It happens with the in memory cache in this demo too. @Cacheable does not lock by default: a hundred threads calling the method with a cold key all miss, all run the body, and all store the same result.

sync = true on @Cacheable is the built in answer. It makes one thread compute the value while the others wait for it, so a cold key costs one call rather than five hundred. It is not on by default and most people do not know it exists. It only works for a single instance, though, because the lock is local.

Across instances you need the lock in the shared cache, which usually means a lock key in Redis. That is real work and is worth it only for the small number of keys that are hot enough to matter.

Two cheaper habits that help more than they sound like they should. Do not give every entry the same expiry, because entries created together then expire together; add a small random amount to each, which is jitter applied to expiry. And warm the few keys you know are hot at startup, rather than letting the first unlucky user pay for them.

When is @Cacheable the wrong tool?

Four situations, and being able to name them is more valuable than knowing the annotation.

The method is fast already. Caching a calculation that takes microseconds adds a key, a lookup and a copy of the answer to save nothing. Measure first: the 203 milliseconds above is what made caching obviously worth it here.

The arguments are nearly always different. A cache keyed by something close to unique, a full text search string or a user id in a system with millions of users, never hits and grows for ever. That is a memory leak with a helpful name.

The result must be current. An account balance, remaining stock during a sale, anything a person will act on immediately. Serving a value from a second ago is sometimes fine and sometimes a support ticket.

The method has side effects. A cached call does not run, so anything the method did besides returning a value, writing a row, sending a message, incrementing a counter, silently stops happening on the second call. @Cacheable assumes the method is a pure function of its arguments, and nothing checks that assumption for you.
