Why your service freezes for 20 milliseconds, over and over

Java cleans up memory for you. The cost is that sometimes it stops your program to do it. This episode is about where those stops come from, how to see them, how to choose between collectors, and why a 4 GB server can quietly give Java only 1 GB. Every number here came from running the code.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 How cleanup works

  • What are the young and old areas, and why are there two?
  • What is Eden and what are the survivor spaces?
  • What does promotion mean?
  • Why is a young collection cheap and an old collection expensive?
  • What is a stop-the-world pause?

Java frees memory for you. You never write code to delete an object. Something runs in the background, works out which objects nobody is pointing at any more, and reclaims that space.

The price is that sometimes it has to stop your program to do it. Every thread freezes, the cleanup happens, then everything resumes. That freeze is called a stop-the-world pause, and understanding where those pauses come from is the whole topic.

The one observation everything is built on

Most objects die almost immediately. In a typical program the overwhelming majority of objects become garbage within moments of being created. A temporary string, a list built inside a method, an object created to answer one request. A small minority live a long time: caches, configuration, connection pools.

Java takes advantage of this by splitting the heap into two areas and treating them completely differently.

What actually happens in a young collection

Eden fills up. Java stops your program and looks at everything in Eden. Almost all of it is garbage, so it does something clever: instead of deleting the garbage, it copies out the few survivors and then treats the entire Eden space as empty.

That is why it is so cheap. The work is proportional to how many objects survived, not how many were created. If you created a million objects and two survived, the cleanup handles two objects and then wipes the slate.

The survivors go into one of the two survivor spaces. Each time an object survives another collection, its age counter goes up. Once it has survived enough times, it gets promoted into the old area.

What happens in an old collection

The old area is full of objects that have already proven they survive. So the trick above does not work. You cannot assume everything is garbage, because most of it is not.

Cleaning it means walking through everything to find what is still reachable, then usually shuffling the survivors together to close up the gaps left behind. That is far more work, over far more data, and it is why old collections cause the long pauses.

"Garbage collection frees objects that are no longer used." Close, but the wrong word. It frees objects that are no longer reachable, meaning nothing points at them any more. An object you have finished with but are still holding a reference to will never be freed, no matter how unused it is. That is the whole subject of Episode 1.

"You can force cleanup with System.gc()." It is a suggestion that Java is free to ignore, and it cannot free anything you are still pointing at.

Follow-up questions

Why are there two survivor spaces instead of one?

Because of how the copying works. At any moment one survivor space is in use and the other is completely empty.

When a young collection runs, Java copies the survivors from Eden and from the currently used survivor space into the empty one. Then Eden and the space it just emptied are both considered free. Next time, the two survivor spaces swap roles.

The reason for copying into a fresh space rather than tidying in place is that it removes gaps automatically. Objects land packed together with no holes between them, so allocating the next object is just moving a pointer forward. There is no searching for a gap big enough.

That is also why allocation in Java is so fast, and it is a good detail to mention: creating an object is usually little more than incrementing a pointer, because the collector keeps the free space contiguous.

What decides when an object gets promoted?

Mainly an age counter. Every object carries a small count of how many collections it has survived. When that count crosses a threshold, the object is moved into the old area on the next collection.

There are two other ways an object gets there faster. If it is too big to fit in the young area at all, it is placed directly in the old area, because copying it around repeatedly would be wasteful. And if the survivor space is full, objects get promoted early regardless of age, simply because there is nowhere else to put them.

That second case matters in practice. If your survivor spaces are too small for your workload, objects are promoted before they have had a chance to die, so the old area fills with things that were about to become garbage anyway. That produces more old collections than you should be having, and the fix is giving the young area more room, not less.

This is called premature promotion, and it is a good thing to name in an interview because it shows you understand that a bigger old area is not always the answer.

Does everything stop during a collection, always?

Not always, and this is exactly what separates the collectors from one another.

Some work genuinely has to happen with the program stopped. Anything that moves objects in memory has to be sure no thread is reading them mid-move. So there is always some stop, even in the most advanced collectors.

But a large part of the work is just finding out what is still reachable, and modern collectors do most of that while your program keeps running. They track changes your program makes during the scan and account for them, rather than freezing everything for the whole job.

That is the difference between an older collector that stops the world for the entire collection and a newer one that stops it only for a few short moments. The measurements in the next chapter show exactly how big that difference is: on the same workload, the longest single freeze went from about 22 milliseconds down to 0.02 milliseconds.

02 The four collectors, measured

  • Name the four collectors and what each is built for.
  • Which is the default, and why?
  • What is the trade-off between total work done and worst freeze?
  • When would you actually choose each one?

Java ships with several collectors. They all do the same job and they make different trade-offs doing it. Rather than describe them, here is the same program run under each one.

The test. One program that creates a lot of short-lived objects and keeps about 135 MB of longer-lived ones, running in a 512 MB heap. Same code, same machine, same workload. The only thing changed is the collector.

ZGC10900.64 ms0.020 ms438 ms

Read that last row twice, because it looks like a mistake and is not.

ZGC stopped the program more often than any of the others, 109 times against G1's 34. But its total freeze time across the entire run was 0.64 milliseconds, and its worst single freeze was 0.020 milliseconds. G1's worst single freeze was 15.54 milliseconds, which is about 775 times longer.

How? ZGC does nearly all its work while your program keeps running. It stops everything only for a few tiny moments per cycle, to start and finish a phase. Everything in between happens alongside your code.

And the cost is in the last column. ZGC took 438 ms to finish the same work that G1 did in 378 ms. Doing cleanup alongside a running program is more expensive overall than doing it in one focused burst. ZGC bought a 775 times shorter worst pause by giving up about 16 percent of throughput.

The sentence that answers the interview question. "They trade total work against worst freeze. Parallel does the least total work but stops everything for the whole collection. ZGC does most of its work alongside the running program, so its worst pause is a fraction of a millisecond, but it costs some throughput. "ZGC is the best, it is the newest." It has the shortest pauses, which is not the same as best. It uses more memory and gives up throughput. For a batch job that nobody is waiting on, Parallel finishing sooner is genuinely the better outcome.

"Serial is obsolete." It is still the sensible choice for a small container with one processor. With only one core available there is nothing to run in parallel, and the coordination that the other collectors do is pure overhead.

Follow-up questions

Why did G1 have zero full collections when Serial had two?

Because G1 does work in advance to avoid ever reaching that point, and this is the clearest thing the measurements show.

Serial and Parallel wait until the old area is full and then deal with it, which means stopping the program and working through the whole old area at once. That is the 22 millisecond pause in the table.

G1 instead tracks which parts of the heap contain the most garbage, and cleans those parts a little at a time during ordinary collections, while the program is running. It aims to keep the old area from ever filling completely.

So G1 did not have shorter full collections than Serial. It had none at all, because it kept up. A full collection in G1 is a sign something went wrong, usually that the heap is too small or that objects are being created faster than it can keep pace with.

That is a genuinely useful production signal to mention: if you see full collections in G1 logs, do not treat them as normal. G1 is telling you it could not keep up.

What does "concurrent" actually mean here?

It means the collector is doing its work at the same time as your application threads are running, rather than while they are frozen.

That sounds straightforward and is genuinely difficult, because the program keeps changing the very thing the collector is examining. While the collector is deciding what is still reachable, your code is creating objects and changing references, potentially making something reachable that the collector already decided was garbage.

Collectors solve this by recording the changes the program makes during the scan and then accounting for them at the end. That bookkeeping is not free, and it is exactly where the throughput cost comes from. In the measurements, ZGC took 16 percent longer overall than G1, and this is where that went.

So the short freezes are not magic. They are bought by doing more total work, spread out, instead of less total work concentrated into a stop. Being able to say that trade-off out loud is what the question is really testing.

When would you actually change the collector?

Honest answer, and worth saying plainly: usually you would not. G1 is the default because it is a sensible choice for most services, and changing it without measuring first is guessing.

The cases where changing is genuinely justified:

  • Your pause times break a promise you have made. If you have a latency target and the logs show G1 pauses exceeding it, that is a real reason to try ZGC, and you should be able to point at the numbers.
  • It is a batch job nobody waits on. Overnight processing, report generation, data migration. Nobody experiences the pause, so optimise for finishing sooner: Parallel.
  • It is a tiny container with one processor. Serial, because there is no second core for anything else to use.
  • Your heap is very large. Beyond a few tens of gigabytes, the pause from walking the whole heap becomes hard for G1 to hide, and ZGC was designed for exactly that size.

The strongest thing to add: measure before and after on your own workload. The table on this page is one program on one machine, and a different allocation pattern can reorder those rows.

The pattern to look for

A single line tells you very little. The signal is in how the numbers change across many lines.

Here are the first three young collections from the same real run:

GC(0) Pause Young  48M->3M(256M)   1.737ms
GC(1) Pause Young 114M->7M(256M)   2.292ms
GC(2) Pause Young 132M->11M(256M)  2.733ms

Look only at the number after the arrow. That is how much was still in use once cleanup finished, and it is the single most useful number in the whole log.

  • Going up and down around a steady level: healthy. Objects are being created and cleaned up at a matching rate.
  • Climbing steadily and never coming back down: you are accumulating something. That is the shape of a memory leak, and the garbage collection log will show it days before anything crashes.

In the extract above it climbs from 3M to 7M to 11M, which looks alarming until you know the program deliberately builds up a set of long-lived objects at the start. That is why you compare after a full collection, when everything that can be cleaned has been.

The one number to alert on. Not heap usage, which always looks nearly full just before a collection. Alert on how much is still in use after a full collection. If that number climbs across days while your traffic stays flat, you have a leak, and you have found it before it became an outage.

Working out how fast you create objects

Two consecutive lines are enough. Take the amount in use after one collection, and the amount before the next one, and divide by the time between them.

GC(0) ... 48M->3M(256M) at 0.441s
GC(1) ... 114M->7M(256M) at 0.457s

created:  114M - 3M   = 111 MB
in time:  0.457 - 0.441 = 0.016 seconds
rate:     about 6.9 GB per second

That number is worth knowing because almost every pause problem is really an allocation problem. If you are producing garbage faster than the collector can keep up, no amount of collector tuning fixes it. You have to create less.

Follow-up questions

Is it safe to leave garbage collection logging on in production?

Yes, and you should. This is one of the few things in performance work that is close to free.

The collector already knows every number in those lines, because it just did the work. Writing them out is a handful of lines of text per collection, which is nothing next to the collection itself. There is no extra measurement being done to produce the log.

Two practical points. Write it to its own file rather than mixing it into application logs, so it stays readable and does not get filtered by log levels. And use rotation, so a long running service does not slowly fill the disk.

The reason this matters more than it sounds: memory problems are usually diagnosed after they happen. If logging was off, you have nothing, and you have to wait for it to happen again. Having it already on turns a week of waiting into a five minute investigation, which is exactly the point made about recording in Episode 2.

What does it mean if pauses are short but there are lots of them?

Usually that you are creating objects very fast, and it is a different problem from long pauses even though it hurts the same.

Each young collection may only take two milliseconds, but if one runs every thirty milliseconds, you are losing a noticeable share of your processing time to cleanup, plus the disruption of constantly stopping and restarting.

The number to work out is what share of wall clock time is going into collection. Under about 5 percent is generally fine. Much above that and it is worth attention.

The fixes, in the order worth trying:

  • Create less garbage. Look at what is being allocated in the hot path. Very often it is something avoidable, like building strings in a loop, or copying a collection that did not need copying.
  • Give the young area more room. More space means fewer collections, and because the cost depends on survivors rather than on space, bigger is often genuinely cheaper.
  • Only then consider the collector. Changing it does not reduce how much garbage you make.
What causes appear in the log, and which ones worry you?

The bracketed reason at the end of the line tells you why the collection happened, and some causes are routine while others are a warning.

Routine. An ordinary young collection because the young area filled up is the normal rhythm of a healthy program. Seeing thousands of these is expected.

Worth noticing. A collection caused by allocation failing means the program asked for memory and there was none, so cleanup had to happen right then rather than at a convenient moment. Occasional ones are normal. Frequent ones mean you are running close to the edge.

A real warning. A full collection under G1, for the reason in the earlier chapter: G1 is designed to avoid these, so one appearing means it could not keep up.

Suspicious. A collection triggered by code explicitly asking for one. That means something in your application, or a library you depend on, is calling for cleanup by hand. It is almost always wrong, and it can cause a full stop at an unpredictable moment. If you see this, find the caller.

04 The settings that matter

  • Which settings would you actually change, and in what order?
  • Why is setting the starting and maximum heap to the same value common?
  • What is wrong with copying tuning settings from a blog post?

There are hundreds of settings. Almost all of them are traps for people who have not measured anything. Here is the short list that earns its place.

SettingWhat it doesWhen to touch it
-XmxLargest the heap may growAlmost always worth setting deliberately. The single most important one.
-XmsSize the heap starts atSet it equal to the maximum on a server. See below.
-XX:MaxRAMPercentageHeap as a share of the container limitIn a container, use this instead of a fixed maximum.
-XX:+HeapDumpOnOutOfMemoryErrorWrite a snapshot when memory runs outAlways on. Free until it is needed.
-Xlog:gcLog collectionsAlways on.
-XX:MaxGCPauseMillisAsks G1 to aim for pauses under a targetOnly with a real latency requirement, and only after measuring.

Why the starting size and the maximum are usually the same

By default Java starts with a small heap and grows it as needed. On a desktop application that is polite, because it does not claim memory it may never use.

On a server it is just a slow start. The heap grows in steps, and every growth is work. Worse, the collector tunes itself based on the heap size it is working with, so while the heap is still growing it is tuning for a size that keeps changing.

-Xms2g -Xmx2g

Setting them equal means the heap is its final size immediately, and the collector settles into steady behaviour from the first request. On a container this is even clearer: the memory is reserved for your program anyway, so there is nothing to be gained by claiming it gradually.

The order to work in. Measure first, using the log. Then reduce how much garbage you create. Then size the heap correctly. Only then consider changing the collector. Almost everybody does this in reverse, starting with the collector, which is the step least likely to help.

Copying a list of settings from a blog post. Tuning is a response to a measurement on your workload. Settings that helped somebody else's service can easily make yours worse, and you will have no idea which one did it because they were applied together.

Setting a pause target and treating it as a promise. It is a goal, not a guarantee. Ask for something unrealistic and the collector will collect more often trying to reach it, which can leave you with worse throughput and still miss the target.

Follow-up questions

Is a bigger heap always better?

No, and the reason is a good answer because most people assume yes.

A bigger heap does give you fewer collections, because it takes longer to fill. That part is real and is often the right fix.

But it can also give you longer collections. Work in the old area depends on how much live data there is to walk through. A heap twice the size holding twice the live data takes longer to clean, so you have traded frequent short pauses for rare long ones. If your problem was the length of individual pauses, you just made it worse.

There is a second cost that catches people out in containers. The heap is not the whole memory your program uses. Thread stacks, class information and off-heap buffers all sit outside it. Give the heap almost everything and the total can exceed the container limit, at which point the system stops your program with no warning and no snapshot, which is the exit code 137 situation.

So the honest answer: bigger heap for collections that are too frequent, not for collections that are too long, and never so big that nothing is left for everything outside it.

How would you approach a service with pauses that are too long?

A specific order, and the order itself is the answer.

1. Measure what is actually happening. Turn on the log and find the real numbers: how long, how often, and which kind of collection. Very often the pauses turn out to be fine and the latency complaint is coming from somewhere else entirely, like a slow query.

2. Work out the share of time. If cleanup accounts for a small percentage of wall clock time, tuning it has very little headroom to give you, no matter what you do.

3. Look at what is being created. High allocation drives everything else. Finding one hot path making unnecessary objects usually beats every setting change combined.

4. Size the heap for the pattern. Frequent short pauses suggest the young area is too small. Long pauses suggest a lot of live data, which is a different problem and may be a leak.

5. Only now consider the collector, and only against a stated target: "requests must stay under 50 milliseconds, and pauses of 80 are breaking that".

What makes this a strong answer is that four of the five steps happen before you change anything. That is what separates someone who has tuned a real system from someone who has read a list of settings.

05 Java inside a container

  • You give a container 4 GB. How much heap does Java take by default?
  • Why use a percentage rather than a fixed heap size?
  • What has to fit in the memory the heap does not use?

This is where most real production surprises live, and it is asked constantly now because nearly everything runs in a container.

Measured on a real Java 24 installation: MaxRAMPercentage defaults to 25.0. Give your container 4 GB and Java will take about 1 GB of it for the heap, all by itself, without telling you.

Java reads the container's memory limit correctly. It then deliberately takes a quarter of it, because it knows the heap is not the only thing it needs memory for. That default is safe and far more cautious than most services need.

The arithmetic is exactly what you would expect, which is the point: there is nothing mysterious happening, people simply do not know the default is a quarter.

What lives in the memory the heap does not use

The leftover is not spare. It has to cover everything Java needs that is not the heap.

  • Thread stacks, roughly 1 MB per thread. Two hundred threads is 200 MB.
  • Class information, which grows with how many classes you load, and frameworks load a lot.
  • Translated code, the compiled versions of your hot methods.
  • Off-heap buffers, used heavily by networking libraries.
  • The collector's own bookkeeping, which for some collectors is a meaningful share.

That is why 90 percent is in the calculator and why choosing it warns you. Give the heap 90 percent of a small container and the remaining tenth cannot cover the rest, so the system stops your program for exceeding its total limit.

Why a percentage and not a fixed size

# fragile: breaks silently if the container limit is ever reduced
-Xmx3g

# adapts: same image works at any container size
-XX:MaxRAMPercentage=70.0

A fixed size is baked into the image. Someone reduces the container limit to 2 GB for cost reasons, your image still asks for a 3 GB heap, and it dies on startup or shortly after. Nobody connects the two changes because they were made by different people weeks apart.

"We gave the pod 4 GB so Java has 4 GB." It has about 1 GB unless you said otherwise, and the other 3 GB sits unused while your service struggles.

"Set the heap to the container limit." Then there is nothing left for threads, classes and buffers, and the system kills the container with no error message and no snapshot.

Follow-up questions

How do you know how much to leave for everything else?

Estimate first, then measure, and be willing to say you would check rather than quoting a number confidently.

A rough starting estimate: about 1 MB per thread you expect to run, a couple of hundred megabytes for class information on a typical framework application, and more if you use networking libraries that allocate outside the heap. For an ordinary service that tends to land somewhere around a quarter to a third of the container.

Then measure rather than trusting the estimate. Java can report a breakdown of where its memory is going, covering the heap, class information, thread stacks and internal structures. Run it under realistic load and you get real numbers instead of guesses.

The practical rule most teams settle on is 65 to 75 percent for the heap on a container running only Java. Below that you are wasting memory you paid for. Above it you are gambling that nothing outside the heap grows.

Worth adding: if the answer matters enough to argue about, it matters enough to measure, and it takes one run under load to find out.

Does the collector choice change how much memory you need?

Yes, and it is a good detail because it connects the two topics.

Collectors keep their own bookkeeping structures, and how much they need varies. The simpler ones need relatively little. The ones that do work alongside your running program need more, because tracking what changed during a scan takes space, and they need spare room to move objects into while the program is still using the originals.

That spare room is the part people miss. A collector that works alongside your program cannot wait for a convenient moment to compact memory, so it needs headroom to work in. Run it in a heap that is nearly full of live data and it cannot keep ahead of the program.

This showed up while producing the measurements on this page. Running ZGC in a 256 MB heap holding about 135 MB of live data caused it to stall and abort, because it had nowhere near enough working room. The same collector in a 512 MB heap ran comfortably.

So the rule: shorter pauses cost memory as well as throughput. If you switch to a collector for its pause behaviour, give it more heap at the same time, not less.

06 When cleanup gives up

  • What exactly does "GC overhead limit exceeded" mean?
  • Why is it better news than a plain out of memory error?
  • What would you do first when you see it?

This message is a safety net, and it is the most informative failure in this whole area because of what it tells you about the shape of the problem.

What it means precisely. Java spent more than 98 percent of its time collecting while recovering less than 2 percent of the heap, several times in a row. So it gave up and threw an error rather than continue.

Why this is different from simply running out

The heap is not quite full. Java could still create objects. Technically nothing has failed.

But almost everything in the heap is still being pointed at, so each collection walks through all of it and frees almost nothing. Then the program creates a little more, and it happens again. Your application is spending nearly all its time cleaning up and getting nothing back, which means it is doing essentially no real work.

Without this safety net you would not get an error at all. You would get a service that responds so slowly it looks frozen, with a processor pinned at 100 percent and no obvious cause, which is a much harder thing to diagnose.

Watch the difference

Go back to the simulator in Chapter 1 and switch it to "objects keep surviving". Same rate of creation, but nothing dies. Watch what happens to the total pause time as the old area fills up: collections become more frequent and recover less each time, until nearly all the time is spent collecting.

What it tells you to do

This is nearly always a leak, so treat it as one. That means the diagnosis from Episode 1 applies directly: take a memory snapshot, open it, find what is holding the most memory, and follow the chain back to what is pointing at it.

The tempting wrong move is to raise the heap. Occasionally that is right, when the application genuinely needs more room than it was given. Usually it just delays the same failure, because if live data grows without limit then no heap size is enough. A bigger heap turns a daily crash into a weekly one.

"Turn the safety net off." There is a setting to disable it and it is almost always the wrong move. It converts a clear early error that names the problem into a service that quietly grinds to a halt. You have removed the warning, not the fault.

"Increase the heap." Sometimes right, usually a delay. Confirm from the log whether live data is growing before deciding.

Telling the two apart from the log

# heap simply too small: recovers to the same level each time
Pause Full 480M->120M(512M)
Pause Full 490M->122M(512M)
Pause Full 485M->121M(512M)

# a leak: recovers less every time, and the baseline climbs
Pause Full 480M->300M(512M)
Pause Full 495M->380M(512M)
Pause Full 502M->450M(512M)

Look only at the number after the arrow across several full collections. Steady means the heap is undersized. Climbing means something is accumulating, and more memory will not save you.

Follow-up questions

Could you get this error without having a leak?

Yes, and being able to name the cases shows you are not just pattern matching.

The heap is genuinely too small for the work. An application legitimately holding 900 MB of live data in a 1 GB heap has almost no room to work in, so every collection walks nearly the whole heap and frees very little. Nothing is leaking, the sizing is simply wrong.

A large temporary workload. A report that loads a million rows at once might genuinely need that memory briefly. Nothing is leaked, it is released afterwards, but during the job the heap is full of live data.

A cache that is doing its job. A cache configured to hold far more than the heap can accommodate is not leaking, because it will evict eventually. It is just sized wrongly relative to the heap.

The way to tell them apart is what the log does over time. A leak shows the amount in use after each full collection climbing without limit. The cases above show a high but stable level, or a spike that returns to normal when the job finishes.

How is this connected to a service being slow rather than crashing?

They are usually the same problem seen at different stages, and joining them up is what makes an answer sound experienced.

A leak does not begin with a crash. It begins with the amount of live data creeping up. More live data means each collection has more to walk through, so pauses get longer. More live data also means less free space, so collections happen more often. Longer and more frequent at the same time.

Long before anything runs out, users start noticing. Response times get worse, especially the slowest requests, because those are the ones that happened to land during a pause. Someone reports the service is slow. Nobody suspects memory, because there is plenty free.

Then it reaches the point where nearly all the time is going into cleanup, and you get this error. So the error is the end of a story that started as a performance complaint days or weeks earlier.

The practical consequence, and the useful thing to say: when someone reports gradually worsening latency, check the garbage collection log early. Rising live data after full collections tells you it is a memory problem before it becomes a memory failure.

The part of the young area where every new object is first placed.
survivor space
Two small areas next to Eden. Objects that survive a collection are copied into one of them, and the two swap roles each time.
promotion
Moving an object from the young area into the old area, once it has survived enough collections.
premature promotion
Objects being moved to the old area too early, usually because the survivor space is full, so things that were about to become garbage end up in the expensive area.
concurrent
Collector work that happens at the same time as your program runs, rather than while it is frozen. Costs some overall speed, buys much shorter freezes.
throughput
How much real work your program gets done. A collector that maximises this finishes sooner but stops you for longer at a time.
latency
How long a single operation takes. A collector that optimises this keeps every freeze short, at some cost to overall speed.
allocation rate
How fast your program creates new objects, for example 6.9 GB per second. High rates drive everything else about collection behaviour.
G1
The default collector since Java 9. Splits the heap into many small parts and cleans the ones with the most garbage first, aiming to avoid ever needing a full collection.
ZGC
A collector built for very short pauses. Does nearly all its work alongside your running program. Measured here at a worst pause of 0.020 milliseconds.
evacuation
G1's word for copying the surviving objects out of a part of the heap so that whole part can be reused. When a real log line says "G1 Evacuation Pause", it just means an ordinary young collection.
full collection
A collection that covers the entire heap including the old area. The expensive kind. Under G1 it is a sign something is wrong.
MaxRAMPercentage
The share of the container's memory limit Java will use for the heap. Defaults to 25, which surprises almost everyone.
