Eight threads, four million increments, and the answer is wrong

Concurrency is where "it works on my machine" comes from, because broken concurrent code usually works. Everything on this page was produced by running it: a counter guarded six different ways, four lock types timed against each other, and a deadlock that no amount of extra threads can fix.

Revision mode is on. Explanations are hidden. Try to answer each prompt out loud before switching back.

01 How a count goes wrong

  • Why is count++ not safe when threads share it?
  • What exactly does volatile guarantee, and what does it not?
  • What does synchronized give you that volatile does not?
  • What is a happens-before relationship?

Start with the smallest possible broken program. Eight threads, each adding 1 to a shared counter half a million times. A correct counter ends at exactly 4,000,000.

Measured, six ways of holding that counter

How the counter is heldBest resultWorst resultBest msCorrect
long4,000,0001,124,7130no

synchronized4,000,0004,000,000185yes
ReentrantLock4,000,0004,000,00096yes
AtomicLong4,000,0004,000,00057yes
LongAdder4,000,0004,000,0005yes

Read the volatile row twice. It lost about seventy percent of the updates, it was never once correct, and it was slower than AtomicLong, which was always correct. Marking a counter volatile buys you nothing here except a false sense of safety.

Why the plain counter is the strangest row

The plain counter finished in 0 milliseconds and its results swung between 1.1 million and the full 4 million. Both of those are clues about the same thing.

When a field is not volatile, the compiler is allowed to assume no other thread is looking at it. So it can keep the value in a processor register, do all half a million additions there, and write back once at the end. That is why the time collapsed to nothing and why the answers are so wildly unpredictable: you are not measuring eight threads racing on memory, you are measuring whatever the optimiser decided to do that run.

This is worth saying in an interview because it explains why broken concurrent code so often passes your tests. The behaviour is not random in a helpful, reliably-fails way. It depends on the compiler, the processor, the load, and the timing.

Why one plus plus is three operations

count++ looks like one thing. It is three: read the current value, add one to it, write it back. Another thread can run in between any of them.

What each keyword actually promises

volatile promises visibility. A write by one thread will be seen by every other thread, immediately, rather than sitting in a register or a processor cache. It also stops the compiler reordering operations around it.

volatile does not promise atomicity. It makes each read and each write visible, but count++ is a read, a change and a write, and another thread can still act between them. That is exactly what the measurement shows.

synchronized promises both. Only one thread can be inside the block at a time, which gives you atomicity, and entering and leaving the block also flushes and refreshes memory, which gives you visibility.

The one line rule. Use volatile when one thread writes and others only read, for example a flag that tells workers to stop. Use synchronized, a lock, or an atomic class the moment a value is read and then written based on what was read.

"volatile makes it thread safe." The measurement above is the answer: still wrong every single run, and slower than the correct options.

"It worked when I tested it." Broken concurrent code usually works. The plain counter hit the correct answer on one of its five runs.

Follow-up questions

What is a happens-before relationship?

It is the rule that decides whether one thread is guaranteed to see what another thread did. If action A happens-before action B, then whatever A wrote is visible to B. If there is no such relationship, there is no guarantee at all, and you may see the new value, the old value, or in some cases a partly written one.

You do not create these by writing code in a particular order. They come from specific things:

  • Everything a thread does before start() is visible to the new thread.
  • Everything a thread does is visible to whoever successfully calls join() on it.
  • Releasing a lock happens-before the next acquisition of that same lock.
  • A write to a volatile field happens-before every later read of that same field.

The practical consequence is the interesting part. Two threads reading and writing an ordinary field with no lock and no volatile between them have no relationship, so the second thread is not merely likely to see stale data, it is allowed to see stale data forever. A loop reading a plain boolean flag can legally never notice it changed, and in practice sometimes does not.

Can you give a case where volatile alone is the right answer?

Yes, and being able to give one shows you understand the boundary rather than just avoiding the keyword.

The classic is a stop flag. One thread writes it once, many threads only read it:

private volatile boolean running = true;

public void shutdown() { running = false; }     // one writer

public void workLoop() {
    while (running) { doWork(); }                // many readers
}

This is safe because nobody reads the value and then writes a new one based on it. There is no read, change, write sequence to be interrupted. Every operation is a single whole read or a single whole write, which is exactly what volatile guarantees.

Without volatile this loop can genuinely hang forever, because the compiler may hoist the read out of the loop and test a cached copy. That is not a theoretical risk, it is a real and commonly seen bug.

The moment you write something like if (!running) running = true; you have a read followed by a write and volatile is no longer enough.

Is a plain long even safe to read and write?

Not necessarily, and this one surprises people.

Java guarantees that reads and writes of most types happen as one whole operation, so you never see half of an int. But long and double are 64 bits, and on some platforms the specification allows the runtime to treat them as two separate 32 bit operations.

That means another thread can in principle observe a value that is the top half of one write and the bottom half of another, a number that was never assigned by anybody. This is called word tearing.

Declaring the field volatile removes this: volatile reads and writes of long and double are always whole operations.

Honest caveat worth adding: on the 64 bit machines almost everyone runs today, this does not happen in practice. It matters as an answer because it shows you know what the specification guarantees rather than what your laptop happens to do, and that distinction is the whole subject.

02 Thread pools, queues and what gets thrown away

  • What are the three things a thread pool does with an arriving task?
  • Why is newFixedThreadPool risky in production?
  • Name the four rejection policies and what each does.
  • What is wrong with newCachedThreadPool?

A pool has threads, a queue, and a policy for what happens when both are full. Most people know the first two.

What happens to an arriving task

  1. If fewer threads exist than the core size, start a new thread for it, even if other threads are idle.
  2. Otherwise, put it in the queue.
  3. If the queue is full, start a new thread up to the maximum size.
  4. If that is not possible either, hand it to the rejection policy.

Step 3 is the one that catches people. With an unbounded queue, step 3 never happens, so the maximum pool size is never reached and is effectively ignored. That is exactly what the convenient factory methods give you.

Measured, what the four policies actually do

2 threads, a queue that holds 4, and 20 tasks submitted at once. So only 6 can be accepted at a time and 14 have to go somewhere.

Rejection policyRanRejectedRan on the callerWhat it means
AbortPolicy (default)6140throws at the caller, work lost unless you catch it
CallerRunsPolicy2005caller does the work, which slows the producer down
DiscardPolicy60014 tasks silently vanished, no error anywhere
DiscardOldestPolicy600drops the longest waiting task to make room

The row to be frightened of is DiscardPolicy. Zero rejected, zero errors, and fourteen tasks gone. Nothing in your logs, nothing thrown, no metric moves. If those were payments or emails, they simply did not happen and nobody found out.

The row to reach for is CallerRunsPolicy. All twenty tasks ran, five of them on the submitting thread. That is real backpressure: when the pool is overwhelmed the producer is forced to slow down, because it is busy doing the work itself.

Why the convenient factory methods are traps

// unlimited queue: tasks pile up until memory runs out
Executors.newFixedThreadPool(10);

// unlimited threads: creates a new one per task if none is free
Executors.newCachedThreadPool();

// what to write instead: every limit visible and chosen
new ThreadPoolExecutor(
    10, 10,                                // core and max threads
    60L, TimeUnit.SECONDS,                 // how long an idle thread lives
    new ArrayBlockingQueue<>(500),         // a queue with a limit
    new ThreadPoolExecutor.CallerRunsPolicy());

newFixedThreadPool uses a queue with no size limit. Under sustained overload the queue grows until the heap dies, which turns a throughput problem into an out of memory crash and buries the real cause.

newCachedThreadPool has no thread limit. A burst of ten thousand requests will try to create ten thousand threads, each needing about a megabyte of memory outside the heap.

"Bigger pool, better throughput." Only if threads come back. If they are all blocked on something slow, more threads means more blocked threads.

"An unbounded queue means we never drop work." It means you never drop work quickly. You accept everything, answer far too late, and eventually run out of memory instead.

Follow-up questions

How do you choose the pool size?

It depends entirely on what the threads spend their time doing, and saying that first is most of the answer.

Work that uses the processor, like parsing or calculating, wants roughly as many threads as you have cores. More than that does not finish the work faster, it just adds time spent switching between threads.

Work that waits, like calling a database or another service, can use many more threads than cores, because most are idle at any moment. The rough reasoning: if a call takes 100 milliseconds and you need to handle 200 per second, you need about 20 in flight at once, so a pool of 20 to 30 is sensible.

The more important point, and the one that separates a real answer from a formula: size the pool last. Set the timeouts first, so threads reliably come back. Give the queue a limit and decide what happens when it fills. Only then tune the number, using measurements from your own load rather than a rule of thumb.

And keep separate pools for separate jobs. If slow report generation shares a pool with fast customer requests, the reports will starve the customers.

What actually happens when you call shutdown?

There are two methods and they behave very differently, which is a common follow-up.

shutdown() is polite. It stops accepting new tasks, but everything already submitted, including everything sitting in the queue, still runs. It returns immediately without waiting.

shutdownNow() is abrupt. It stops accepting new work, tries to interrupt the threads currently running, and returns the list of tasks that were still queued and will now never run. Those returned tasks are your only record of what was lost, so ignoring the return value quietly loses work.

Neither of them waits. To actually wait you need awaitTermination with a timeout, and the usual correct pattern is: call shutdown(), wait a while, and if it has not finished call shutdownNow().

The catch worth mentioning: interrupting only works if your task cooperates. Code that ignores InterruptedException, or that is blocked on something which does not respond to interruption, will keep running regardless. That is why a task swallowing that exception is a genuine bug, not a style preference.

03 CompletableFuture

  • What problem does CompletableFuture solve that Future does not?
  • Difference between thenApply and thenCompose?
  • How do you run two calls at the same time and combine them?
  • How do you handle a failure in the middle of a chain?
  • What is the difference between join and get?

The old Future could only be asked "are you done yet". The only way to use the result was to block and wait for it, which throws away the point of doing the work in the background.

CompletableFuture lets you say what should happen when the result arrives, without waiting for it.

The methods worth knowing

MethodUse it when
supplyAsyncstarting work in the background that returns something
runAsyncstarting work in the background that returns nothing
thenApplytransforming the result with a plain method
thenComposethe next step is itself asynchronous and returns another future
thenCombinetwo independent futures, combine both results when both arrive
allOfwaiting for many futures to finish
exceptionallysupplying a fallback value if something failed
handlereacting to both outcomes in one place

thenApply against thenCompose

This is asked constantly and the answer is short: it is the difference between a value and another future.

// getName returns a String, so thenApply
cf.thenApply(user -> user.getName());              // CompletableFuture<String>

// loadOrders itself returns a CompletableFuture
cf.thenApply(user -> loadOrders(user));            // CompletableFuture<CompletableFuture<Orders>>  wrong
cf.thenCompose(user -> loadOrders(user));          // CompletableFuture<Orders>  right

Use thenApply when your function returns a plain value. Use thenCompose when it returns another future, so you get one future back instead of a future wrapped in a future.

Doing two things at once

CompletableFuture<User> user = supplyAsync(() -> loadUser(id), pool);
CompletableFuture<Cart> cart = supplyAsync(() -> loadCart(id), pool);

// both calls are already running; combine when both arrive
user.thenCombine(cart, (u, c) -> render(u, c))
    .exceptionally(err -> renderError(err))
    .thenAccept(this::send);

Both calls start immediately, so the total time is the slower of the two rather than the sum. Doing this sequentially with two blocking calls would take both.

The mistake that undoes all of it. Calling join() or get() in the middle of a chain to grab an intermediate result turns the whole thing back into blocking code, and on a shared pool it can stop the program entirely. That is the next chapter.

"CompletableFuture makes it non blocking." Only if you never block on it. The methods are non blocking, join and get are not.

"If I do not pass an executor it uses a new thread." It uses a shared pool built into Java, sized to your processor count, and shared with every other piece of code that does the same. Long or blocking work there affects everything else.

Follow-up questions

What is the difference between join and get?

Both wait for the result. The difference is how failures are reported.

get() is declared to throw checked exceptions, so the compiler forces you to handle or declare them. That makes it awkward inside a lambda, which cannot throw checked exceptions.

join() throws only unchecked exceptions, so it fits inside lambdas and chains without ceremony. That convenience is why it is used far more often in practice.

There is one genuine functional difference worth naming: get() has an overload taking a timeout, and join() does not. If you need to give up after a while, you need get(5, TimeUnit.SECONDS), or you can attach a timeout to the future itself with orTimeout.

The practical advice: prefer join for readability, but if you are waiting on anything that talks to another system, make sure a timeout exists somewhere, otherwise you have written a call that can wait forever.

How does exception handling work through a chain?

A failure travels down the chain and skips the normal steps until something handles it, in much the same way an exception unwinds a call stack.

If supplyAsync throws, every thenApply after it is skipped. The future is now in a failed state carrying that exception, and it stays that way until a handler is reached.

There are three handlers and they differ in what they can see and return:

  • exceptionally runs only on failure, and returns a replacement value. This is your fallback.
  • handle runs either way, receiving the result and the exception, one of which is null. Use it when you want one place that deals with both.
  • whenComplete also runs either way, but cannot change the outcome. Use it for logging or cleanup.

Two things that catch people. Placement matters: a handler only covers the steps above it, so one at the end of a long chain will not protect a later addition. And the exception you receive is usually wrapped in a CompletionException, so checking its type means looking at the cause rather than the exception itself.

04 The deadlock you cause yourself

  • Why can waiting for a task on the same pool stop everything?
  • Does a bigger pool fix it?
  • What is the actual fix?
  • Why is the default shared pool a bad place for blocking work?

This one is nasty because the code looks correct. It is async code, using CompletableFuture, on an ordinary pool. It still stops forever.

CompletableFuture.runAsync(() -> {
    // this inner task needs a thread from the same pool
    CompletableFuture<String> child = CompletableFuture.supplyAsync(() -> load(), pool);
    child.join();          // and this thread waits here until it runs
}, pool);

The outer task occupies a thread and then waits. The inner task needs a thread to run. If the outer tasks have taken every thread in the pool, the inner tasks can never start, so the outer tasks wait forever.

Measured, including the fix people try first

SetupResult
2 threads, 2 tasks, same poolstuck
4 threads, 2 tasks, same poolfinished
4 threads, 4 tasks, same poolstuck
8 threads, 8 tasks, same poolstuck
2 threads, 8 tasks, separate pool for the inner workfinished

Row two is the trap. Doubling the pool made it work, so the obvious conclusion is "we needed a bigger pool". Row three kills that: the same doubled pool with more tasks is stuck again. The pool was never too small, it was shared between work and the work it waits on.

The last row is the fix. Two threads, four times as many tasks, and it completes, because the inner work has somewhere else to run.

The three ways out

  1. Do not block inside a pooled task. Chain instead: thenCompose lets the inner work continue the pipeline without anybody sitting and waiting for it. This is the real fix and it needs no extra threads.
  2. Use a separate pool for the inner work, so waiting for it can never starve it.
  3. Put a timeout on the wait, so a mistake becomes a slow failure you can see rather than a permanent freeze.

"Increase the pool size." Measured above: it worked once by coincidence and failed as soon as the task count matched the pool size.

"Use the default pool, it is managed for you." That shared pool is sized to your processor count and used by parallel streams and everything else that does not pass an executor. Blocking on it affects unrelated code across your whole application.

Follow-up questions

How would you spot this in a live service?

Take a thread dump, and the shape is unmistakable once you know it.

You will see every thread from one pool, with the same name pattern such as pool-1-thread-*, all in WAITING, and all with the same stack trace ending in a wait on a future. Processor time on those threads will be near zero, because they are not doing anything, just waiting.

The distinguishing detail against ordinary slowness is that the queue keeps growing while every thread sits still. Nothing is progressing, but work keeps arriving. Memory and processor graphs both look completely healthy, which is why this gets misdiagnosed as a network problem.

Take three dumps about ten seconds apart. If those threads are on the identical line in all three, they are genuinely stuck rather than slow, and the line they are stuck on tells you which future they are waiting for.

The give-away in the code is then easy to find: look for a join() or get() inside a task that was itself submitted to a pool.

Why does the same code sometimes work?

Because whether it deadlocks depends on timing, and that makes it far more dangerous than a bug that always fails.

Pools create threads lazily. If an inner task happens to be submitted while the pool still has room to create another thread, it gets one and everything completes. Under light load, with a handful of requests, that is often what happens. The code passes review, passes tests, and works in staging.

Under real load every thread is already busy with outer tasks, no capacity is left, and it locks up. So the failure appears at exactly the moment you least want it: peak traffic.

This is worth calling out because it happened while producing the measurements on this page. The first version of the test showed "8 threads, 8 tasks" completing successfully, which contradicted the pattern. It was a race in thread creation. Only after forcing every outer task to start before any of them asked for an inner thread did the result become stable and repeatable.

The lesson generalises: if a concurrency test passes, ask whether it passed for the reason you think.

05 Which lock, and when

Follow-up questions

What does reentrant mean, and why does it matter?

It means a thread that already holds the lock can take it again without blocking on itself.

Consider a method that takes a lock and then calls another method on the same object which also takes that lock. Without reentrancy the thread would wait for a lock it is itself holding, which can never be released, so it would deadlock instantly with a single thread and no other party involved.

Both synchronized and ReentrantLock are reentrant, which is why this ordinary looking code works at all. The lock keeps a count: each acquisition increases it, each release decreases it, and only when it reaches zero is the lock actually free.

The practical consequence people miss is that with ReentrantLock you must unlock exactly as many times as you locked. Taking it twice and unlocking once leaves it held forever. That is one more reason the lock() and try/finally unlock() pattern is not optional.

Worth naming as a contrast: the read lock of a read write lock is not upgradable. Holding a read lock and then asking for the write lock deadlocks, because the write lock waits for all readers to leave, including you.

What is an optimistic read and when does it fail?

It is reading without taking a lock at all, then checking afterwards whether anybody wrote while you were reading. If nobody did, the read was valid and cost almost nothing. If somebody did, you throw the result away and read again properly.

long stamp = lock.tryOptimisticRead();   // no lock taken
long value = a + b;                      // read the fields
if (!lock.validate(stamp)) {             // did a writer get in?
    stamp = lock.readLock();             // yes, do it properly
    try { value = a + b; } finally { lock.unlockRead(stamp); }
}

That is where the 928 million reads per second came from: in the common case there is no lock, no waiting, and no writing to shared lock state.

It fails when writes are frequent. Every write invalidates readers in flight, so they all redo their work, and you pay for the optimistic attempt and the real read. With enough writers it becomes slower than simply taking the read lock.

Two rules that matter in practice. You must copy what you read into local variables and validate before acting on it, because the data can change underneath you mid-read. And StampedLock is not reentrant, so unlike the other locks here, asking for it twice on one thread deadlocks.

06 Atomics and compare-and-set

  • How does an atomic class work without a lock?
  • What is compare-and-set?
  • When is LongAdder better than AtomicLong, and when is it worse?
  • What is the ABA problem?

The atomic classes give you correct read, change and write without a lock. The trick is a single processor instruction that does all three at once.

Compare-and-set

The instruction says: if this memory location still holds the value I expect, replace it with this new value, and tell me whether it worked. The whole thing happens as one indivisible step, so nothing can slip in between.

// what incrementAndGet does underneath
while (true) {
    long current = value;                        // read
    long next = current + 1;                     // change
    if (compareAndSet(current, next)) return next; // write, only if unchanged
    // somebody beat us to it, so read again and retry
}

No thread ever waits. A thread that loses the race simply tries again with the new value. This is why atomics are often called lock free: threads are never blocked, though under heavy contention they can spend a lot of time retrying.

Measured, and this is where LongAdder appears

From the counter in chapter one, eight threads incrementing four million times:

HowBest msCompared to synchronized
synchronized185baseline
ReentrantLock96about 2 times faster
AtomicLong57about 3 times faster
LongAdder5about 37 times faster

Why LongAdder is so much faster. With eight threads hammering one AtomicLong, they are all competing for the same memory location, so most compare-and-set attempts fail and get retried. LongAdder gives each thread its own separate counter and only adds them together when you ask for the total. Threads stop fighting each other entirely.

The trade, and the reason AtomicLong still exists. LongAdder is much faster to write and slower to read, because reading means summing every internal counter. It also has no compare-and-set, so you cannot do conditional updates with it. Use it for counters and metrics that are written constantly and read occasionally. Use AtomicLong when you read often, or need the exact value at a moment, or need compare-and-set.

"Atomic classes are lock free so they are always faster." Under heavy contention they spend their time retrying. That is exactly why LongAdder was added and why it beat AtomicLong by 11 times here.

"AtomicInteger makes my whole class thread safe." Each operation on it is atomic. Two operations are not. Reading an atomic, deciding something, then writing it is still a race unless you use a single compare-and-set or an update method.

Follow-up questions

What is the ABA problem?

Compare-and-set asks "is the value still what I expect". It cannot tell the difference between a value that never changed and a value that changed away and came back.

Thread one reads A and prepares to swap it for C. Before it acts, thread two changes A to B and then back to A. Thread one's compare-and-set now succeeds, because the value it sees is still A, even though the world moved underneath it.

For a plain counter this does not matter: a number that returns to the same value is genuinely the same value. It matters when the value is a reference and the identity carries meaning, for example the head of a stack you are popping from. The node may have been removed, reused and pushed back, so your swap corrupts the structure while looking perfectly valid.

The fix is to give each change a version number, so the pair of value and version is compared rather than the value alone. Java provides AtomicStampedReference for exactly this, where the stamp is a counter you increment on every write.

Honest framing for an interview: you are unlikely to hit this unless you are writing lock free data structures by hand, which you probably should not be. Knowing it exists demonstrates you understand what compare-and-set actually promises, which is narrower than most people assume.

How would you safely update a value based on its current value?

Use the update methods rather than reading and writing separately, because the separate version is a race no matter how atomic each half is.

// broken: two atomic operations do not make one atomic operation
if (counter.get() < limit) counter.incrementAndGet();

// correct: one call, retried internally until it succeeds
counter.updateAndGet(v -> v < limit ? v + 1 : v);

updateAndGet and accumulateAndGet take your function and run the read, apply, compare-and-set loop for you. If another thread wins the race, your function is simply applied again to the new value.

That leads to the one rule that catches people: the function must have no side effects. It can be called several times for a single successful update, so logging, sending a message or mutating anything else inside it will happen more than once.

The same idea appears on maps. map.compute, computeIfAbsent and merge exist so that a read, decide and write on a concurrent map is one atomic operation rather than three separate calls with gaps between them.
